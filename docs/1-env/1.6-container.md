## 两条官方路线

| | Isaac Sim 的 NGC 镜像 | Isaac Lab 仓库的 `docker/` |
|---|---|---|
| 是什么 | 预装 Isaac Sim 的镜像 `nvcr.io/nvidia/isaac-sim:5.1.0`[^sim-container] | 以上述镜像为底，装上 Isaac Lab 的 Dockerfile 与 compose 配置[^lab-base] |
| 怎么起 | 一条 `docker run`，进容器后 `./runheadless.sh` | `./docker/container.py start / enter / copy / stop`[^lab-cli] |
| 运行用户 | 文档用 `-u 1234:1234`，容器以非 root 用户运行[^sim-container] | `USER root`，用户目录 `/root`[^lab-base][^lab-env] |
| 缓存与产物 | 宿主目录绑定挂载，事先 `chown 1234:1234` | 命名卷（named volume），源码目录绑定挂载 |
| 适合 | 只用 Isaac Sim、推流看画面、跑独立脚本 | 开发 Isaac Lab 任务：宿主上改代码，容器里跑 |

*表 1：两条官方路线（左列 2026-10-20 实测；右列未实测，依据见脚注）。*

本站的示例走第三条路：在 NGC 镜像上自己写一个最小的 Dockerfile，把 Isaac Lab 2.3.2 与主线项目一起装进去（见下文"自定义 Dockerfile"）。适合要把训练环境固定下来、在服务器或集群上反复使用的场合（[7.1](../7-infra/7.1-headless-remote.md#容器与集群)）。

### NGC 镜像：一条 `docker run`

```bash
# 本站实测（2026-10-20）：摘自 Isaac Sim 5.1.0 容器安装文档
docker pull nvcr.io/nvidia/isaac-sim:5.1.0
docker run --name isaac-sim --entrypoint bash -it --gpus all -e "ACCEPT_EULA=Y" --rm --network=host \
    -e "PRIVACY_CONSENT=Y" \
    -v ~/docker/isaac-sim/cache/main:/isaac-sim/.cache:rw \
    -v ~/docker/isaac-sim/cache/computecache:/isaac-sim/.nv/ComputeCache:rw \
    -v ~/docker/isaac-sim/logs:/isaac-sim/.nvidia-omniverse/logs:rw \
    -v ~/docker/isaac-sim/config:/isaac-sim/.nvidia-omniverse/config:rw \
    -v ~/docker/isaac-sim/data:/isaac-sim/.local/share/ov/data:rw \
    -v ~/docker/isaac-sim/pkg:/isaac-sim/.local/share/ov/pkg:rw \
    -u 1234:1234 \
    nvcr.io/nvidia/isaac-sim:5.1.0
```

| 参数 | 作用 |
|---|---|
| `--gpus all` | 把宿主的 GPU 交给容器（需要 NVIDIA Container Toolkit，下一节） |
| `-e ACCEPT_EULA=Y` | 接受 NVIDIA Omniverse 许可协议，不接受就不要加 |
| `-e PRIVACY_CONSENT=Y` | 同意收集使用数据，不同意就去掉 |
| `--network=host` | 与宿主共用网络，推流端口不用另外映射 |
| `-v …/cache/main:/isaac-sim/.cache` 等 | 着色器、计算缓存、日志、配置挂到宿主，删掉容器也保留，第二次启动快得多 |
| `-u 1234:1234` | 以 1234 用户运行，所以宿主上的这些目录要事先 `chown -R 1234:1234` |

*表 2：`docker run` 各参数（摘自官方文档[^sim-container]；2026-10-20 按原样运行通过）。*

`chown -R 1234:1234` 要 root 权限。不想用 `sudo` 的话，可以借一个临时容器来改，因为容器里默认是 root：`docker run --rm -v ~/docker/isaac-sim:/d ubuntu chown -R 1234:1234 /d`（本站实测）。改完以后，这些目录宿主用户就读不了，查看或清理也要照样借容器。

### Isaac Lab 的 `docker/`

`docker/.env.base` 定了底镜像与版本（`ISAACSIM_VERSION=5.1.0`）、容器里的 Isaac Lab 路径 `/workspace/isaaclab`、用户目录 `/root`[^lab-env]。`docker-compose.yaml` 做三件事[^lab-compose]（本节未实测）：

- 把 Isaac Sim 的各类缓存与日志挂成命名卷；
- 把宿主上的 `source/`、`scripts/` 等目录绑定挂载进容器，宿主改了代码，容器里立即生效；
- 用 `deploy.resources.reservations.devices` 申请全部 GPU，并使用宿主网络。

```bash
# 未验证（本站未实测）：摘自 Isaac Lab v2.3.2 Docker 指南
./docker/container.py start          # 构建并在后台启动 isaac-lab-base
./docker/container.py enter base     # 进入容器
./docker/container.py copy           # 把 logs、data_storage、docs/_build 拷到 docker/artifacts
./docker/container.py stop
```

## GPU 透传

容器里不装显卡驱动，驱动来自宿主。NVIDIA Container Toolkit 是中间那一层：Docker 启动要 GPU 的容器时，由它的运行时把宿主的 GPU 与驱动交给容器[^toolkit]。所以宿主要先装好驱动，再装 Toolkit，并用 `nvidia-ctk runtime configure --runtime=docker` 把它注册给 Docker、重启 Docker[^toolkit]。

```bash
# 本站实测（2026-10-20）：Isaac Sim 文档给的 Toolkit 自检
docker run --rm --runtime=nvidia --gpus all ubuntu nvidia-smi
```

本站输出的表头一行是 `NVIDIA-SMI 580.178.04  Driver Version: 580.178.04  CUDA Version: 13.0`，下面列出 RTX 5090。

- **`docker run`** 用 `--gpus all`；容器里看不到 GPU 时，Isaac Sim 文档建议再加 `--runtime=nvidia`[^sim-container]。
- **compose** 用 `deploy.resources.reservations.devices`（`driver: nvidia`、`capabilities: [gpu]`），Isaac Lab 的 compose 就是这样写的[^lab-compose]。
- **驱动版本**：容器沿用宿主驱动，所以宿主驱动仍要满足 Isaac Sim 5.1.0 的要求，测试过的 Linux 版本是 580.65.06（[1.3](1.3-hardware.md)）。镜像里 CUDA 运行库与宿主驱动的版本关系，遵循 CUDA 的兼容规则：同一大版本内，驱动足够新即可[^cuda-compat]。

## headless、推流与 GUI

- **headless 推流**：NGC 镜像里用 `./runheadless.sh -v` 启动，日志出现 "Isaac Sim Full Streaming App is loaded" 后，用 WebRTC 客户端连宿主 IP[^sim-container]。本站实测这一行在第一次启动 85 s 后出现，第二次 19 s；只把 `cache/main`、`cache/computecache` 换成空目录再启动，又回到 84 s，所以提速来自这两个宿主缓存目录。没有接客户端。端口与 7.1 相同，即 TCP 49100、UDP 47998（[7.1](../7-infra/7.1-headless-remote.md#livestream把画面传到本地)）。用了 `--network=host` 就不必映射端口；不用宿主网络时，要把这两个端口都映射出来（推断）。Isaac Sim 5.1.0 在 aarch64（如 DGX Spark）上不支持推流[^sim-container]。
- **Python 脚本**：Isaac Sim 文档说，容器里的 Python 应用与独立示例只支持 headless[^sim-container]。训练本来就用 headless，不受影响。
- **GUI**：Isaac Sim 的容器文档有一节"Container Deployment with GUI"，这一节最后有一条警告：一般不推荐在容器里跑带界面的 Isaac Sim，完整的界面体验请用工作站安装[^sim-container]。照这一节的做法：宿主上先 `xhost +local:`，在上面的 `docker run` 里加两项，进容器后用 `./runapp.sh` 启动。

  ```bash
  # 未验证（本站未实测）：摘自 Isaac Sim 5.1.0 容器文档 "Container Deployment with GUI"，只列出比上文多的两项
  xhost +local:
  docker run ... -v $HOME/.Xauthority:/isaac-sim/.Xauthority -e DISPLAY ... nvcr.io/nvidia/isaac-sim:5.1.0
  ```

  Isaac Lab 的 `container.py` 第一次 `start` 时会问要不要开 X11 转发，答案存在 `docker/.container.cfg`[^lab-docker-guide]。开了以后，它会把 `x11.yaml` 叠加进来，挂载 `/tmp/.X11-unix`，并传入 `DISPLAY`、`XAUTHORITY`[^lab-x11]。Wayland 下怎么转发，两份官方文档都没有说。

## 缓存与数据卷

| 内容 | Isaac Sim 镜像（`docker run`） | Isaac Lab compose（root） |
|---|---|---|
| Kit 缓存 | `/isaac-sim/.cache` | 卷 `isaac-cache-kit` → `/isaac-sim/kit/cache`；`isaac-cache-ov` → `/root/.cache/ov` |
| 计算缓存 | `/isaac-sim/.nv/ComputeCache` | `isaac-cache-compute` → `/root/.nv/ComputeCache` |
| 日志 | `/isaac-sim/.nvidia-omniverse/logs` | `isaac-logs` → `/root/.nvidia-omniverse/logs` |
| 训练产物 | 自行挂载 | `isaac-lab-logs` → `/workspace/isaaclab/logs`，用 `container.py copy` 取出 |

*表 3：缓存与产物挂在哪里（依据[^sim-container][^lab-compose]）。Isaac Sim 列 2026-10-20 实测，第一次启动后缓存、计算缓存、日志目录写入了内容，`config`、`pkg` 仍为空；Isaac Lab 列未实测，本站 `compose.yaml` 用了同样的卷路径，跑通了。两条路线的用户不同，用户目录也不同，所以同样的缓存落在不同路径。*

**文件属主**：容器以 root 运行时，写进绑定挂载目录的文件在宿主上属于 root。Isaac Lab 的 compose 注释写明，`logs`、`docs/_build` 改用命名卷，原因之一就是不让 root 写的文件涌进宿主目录[^lab-compose]。Isaac Sim 的路线则反过来：容器用 1234 用户，宿主目录事先改成这个属主[^sim-container]。

## 自定义 Dockerfile

`examples/isaaclab-2.3/1.6-container/Dockerfile` 只有四步（2026-10-20 实测构建与运行通过）：

1. `FROM nvcr.io/nvidia/isaac-sim:5.1.0`，切到 root，并设 `ACCEPT_EULA=Y`、`OMNI_KIT_ALLOW_ROOT=1`。用户与 Isaac Lab 的 `Dockerfile.base` 一致[^lab-base]。
2. 装 `git`、`build-essential` 等少数系统包，与 `Dockerfile.base` 相同。
3. 按 tag 克隆 Isaac Lab v2.3.2，把镜像里的 `/isaac-sim` 链接到 `_isaac_sim`（`isaaclab.sh` 靠它找 Python）。先关掉构建隔离装 `flatdict==4.0.1`（原因见坑五），再 `isaaclab.sh --install rsl_rl`，最后对 `isaaclab`、`isaaclab_rl`、`isaaclab_tasks` 逐个 `pip show`，缺一个就让构建失败。不能把三个包写在一条 `pip show` 里：它只要找到其中一个就返回 0（本站在镜像里核对，pip 24.3.1）。
4. 拷入主线项目的 `source/` 与 `scripts/`，用 `/isaac-sim/python.sh -m pip install -e` 装 `galbot_academy`，再按固定 commit 克隆 Galbot 描述仓库（6.1.1）。

USD 转换要用 GPU，而构建阶段拿不到 GPU，所以转换留到第一次运行时做，结果放在命名卷里。`run.sh` 依次执行：构建 → 转换 → 10 次迭代的冒烟训练 → 用临时容器把日志拷到宿主，属主改成 `1.6-container/` 目录的属主（读目录的属主而不用 `id -g` 的原因见坑四）。

与 pip 路线（1.4）比，Python 环境由镜像提供（`/isaac-sim/python.sh`），不用自己建 conda；`isaacsim` 不是 pip 装的，而是镜像自带的二进制版本。版本固定在镜像标签和 Isaac Lab 的 tag 上，换机器不用重装。代价是镜像大、首次拉取慢，GUI 也更麻烦。

## 常见坑

### 坑一：两条官方路线的用户不一样

Isaac Sim 文档的 `docker run` 用 1234 用户，缓存挂在 `/isaac-sim/.cache` 等路径下[^sim-container]；Isaac Lab 的镜像用 root，缓存在 `/root/...` 下[^lab-base][^lab-env]。照着一个文档的挂载路径去用另一个镜像，缓存就挂错了地方，每次启动都重新编译着色器。

### 坑二：容器里看不到 GPU

先在宿主上跑 Toolkit 自检命令。不通的话，按 Toolkit 文档检查是否执行了 `nvidia-ctk runtime configure` 并重启了 Docker[^toolkit]；Isaac Sim 文档还建议给 `docker run` 加 `--runtime=nvidia`[^sim-container]。

### 坑三：用 snap 装的 Docker

Isaac Lab 的 Docker 指南说，受 snap 的限制，Isaac Lab 目录要放在 `/home` 之下[^lab-docker-guide]。

### 坑四：宿主目录里多出 root 的文件

容器以 root 运行，又把宿主目录绑定挂载进去，日志、检查点就会在宿主上变成 root 所有。可以学 Isaac Lab 的做法，把产物放进命名卷再拷出来[^lab-compose]，或者像本站 `run.sh` 那样拷完后 `chown`。本站实测 `artifacts/logs` 拷出后属于当前用户。

`chown` 的目标最初写成 `$(id -u):$(id -g)`，实测得到的属组是 `docker`。这只发生在刚加入 `docker` 组、没有重新登录、用 `sg docker -c` 执行脚本时：`sg` 会把当前组换成 `docker`。重新登录后 `id -g` 就是自己的主组。现在的 `run.sh` 改为读本目录的属主属组（`stat -c %u:%g .`），两种情况都对。

### 坑五：构建"成功"了，容器里却 `No module named 'isaaclab'`

本站第一次构建没有报错，运行转换脚本时才失败。翻构建日志，`isaaclab.sh --install` 在装核心包 `source/isaaclab` 时出错，报 `ModuleNotFoundError: No module named 'pkg_resources'`，然后继续装别的包，构建照常完成。原因如下：

- Isaac Lab 2.3.2 固定依赖 `flatdict==4.0.1`[^lab-setup]，这个版本在 PyPI 上只有源码包[^flatdict]，安装时要现场构建；
- pip 默认在隔离环境里构建，隔离环境装的是 PyPI 上最新的 setuptools。构建当天在镜像里用 `pip download setuptools` 拿到的是 84.2.0，它的 wheel 里已没有 `pkg_resources`；镜像自带的是 78.1.1，还有。

修法就是先用镜像自带的 setuptools、关掉隔离把它装好：`/isaac-sim/python.sh -m pip install --no-build-isolation flatdict==4.0.1`。修改前后各构建一次，修改前失败，修改后通过。Isaac Lab 自带的 `Dockerfile.base` 同样调用 `isaaclab.sh --install`[^lab-base]，推断会遇到同一个问题（未实测）。教训是构建末尾逐个检查核心包（逐个 `pip show`），让缺包直接中止构建。
