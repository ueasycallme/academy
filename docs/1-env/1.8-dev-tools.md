:::{admonition} 验证方式
:class: note

本页以 VS Code 为例，配置文件可直接复制[^ex]。本机装有 VS Code 1.138.0，但本站没有在 VS Code 界面里操作，验证都在命令行下完成：

- **调试配置**：用 debugpy 自带的调试适配器验证。VS Code 的 Python Debugger 扩展用的也是 debugpy[^vsc-debug]，本站按 `launch.json` 的字段向适配器发请求，在 Isaac Lab 源码里打断点，确认能停住并取到调用栈。
- **代码补全与跳转**：用 pyright 命令行检查导入能否解析。Pylance 的类型检查基于 pyright[^pylance]；Pylance 本身的表现是推断。

## 解释器与代码补全

这一节回答：怎样让编辑器认出 Isaac Lab 的包？

第一步是在 VS Code 状态栏选中 1.4 建的环境作为解释器。选错了，所有导入都会报红，运行时也会用错 Python。

第二步是 `python.analysis.extraPaths`。本站用 pyright 1.1.414，在 1.4 的环境里检查了一组典型导入：

| 导入 | 不加 extraPaths | 加 Isaac Lab 的 `source/` 目录 | 再加 Kit 的模块目录 |
|---|---|---|---|
| `isaaclab.*`、`isaaclab_tasks.*`、`isaaclab_rl.*` | 无法解析 | 可解析 | 可解析 |
| `torch`、`warp`、`isaacsim` | 可解析 | 可解析 | 可解析 |
| `omni.usd`、`pxr`、`carb` | 无法解析 | 无法解析 | 可解析 |
| `isaacsim.core.api`、`isaacsim.core.utils.*` | 无法解析 | 无法解析 | 仍无法解析 |

*表 1：pyright 能否解析导入（本站实测，2026-10-09）。Kit 的模块目录指 `site-packages/isaacsim/` 下的 `extscache/omni.usd-*`、`extscache/omni.usd.libs-*` 与 `kit/kernel/py`。*

原因有两个：

- **Isaac Lab 是 editable 安装**。`isaaclab.sh` 用 pip 的 editable 模式装各个包[^lab-sh]，环境里留下的是 setuptools 的导入钩子（`__editable___isaaclab_*_finder.py`），运行时由钩子找到源码。pyright 不执行这些钩子，所以要把 `source/<包名>` 直接写进 extraPaths。pyright 的文档专门说明了这种情况[^pyright-editable]。
- **`isaacsim.core.*` 加了路径也解析不了**。这些模块在各个扩展的目录里，例如 `exts/isaacsim.core.api/isaacsim/core/api/`，其中的 `isaacsim/` 是没有 `__init__.py` 的命名空间目录。而 `site-packages/isaacsim/` 本身是带 `__init__.py` 的普通包，会把它们遮住。运行时也是这样：不启动 Kit，直接 `import isaacsim.core.api`，会报 `ModuleNotFoundError: No module named 'isaacsim.core'`（本站实测）。要等 Kit 启动并加载了这个扩展，才能导入。所以这一点推断是 Kit 加载扩展时把扩展目录加进了 `sys.path`（[2.6](../2-usd-kit/2.6-what-is-kit.md)）。

Isaac Lab 仓库自带 `.vscode/tools/setup_vscode.py`（`./isaaclab.sh -v` 调用它）[^setup-vscode]。它把模板里的 extraPaths 和解释器路径写进 `.vscode/settings.json`，并试图从 Isaac Sim 目录下的 `.vscode/settings.json` 合并 Kit 的路径。pip 安装下没有这个文件，脚本会打印一条 `[WARN] Could not find Isaac Sim VSCode settings`（本站实测），但模板里 `source/` 下的各个包仍会写进去。所以 pip 方式下运行它，`isaaclab.*` 的问题就解决了，Kit 的模块还要按表 1 手动补。本站的示例 `settings.json` 把这些都列了出来[^ex]。

## 运行与调试配置

这一节回答：怎样在 Isaac Lab 的源码里打断点？

示例 `launch.json` 有两项[^ex]：

- **直接启动**：`"request": "launch"`，`program` 指向项目里的 `scripts/zero_agent.py`，`args` 带上 `--headless` 与较少的环境数，`env` 里设 `OMNI_KIT_ACCEPT_EULA`。`justMyCode` 默认是 true，只调试"自己的代码"[^vsc-debug]。要在 Isaac Lab 或其他库的源码里停下，就写成 `"justMyCode": false`；本站验证时用的是 false。
- **attach**：`"request": "attach"`，`connect` 指向 `127.0.0.1:5678`。先在终端运行 `python scripts/debug_step.py --headless --debugpy`，它会在这个端口等待（[7.3](../7-infra/7.3-debugging.md)）。

两项都在 `isaaclab/envs/manager_based_rl_env.py` 第 356 行（`_reset_idx` 的第一行）打了断点，本站实测都能停住：

```text
launch：下发请求后 7.5 s 停在断点
  _reset_idx  isaaclab/envs/manager_based_rl_env.py:356
  reset       isaaclab/envs/manager_based_env.py:372
  reset       gymnasium/core.py:333
  ...
  main        scripts/zero_agent.py:54
attach：连上后 2.2 s 停在断点
  _reset_idx  isaaclab/envs/manager_based_rl_env.py:356
  reset       isaaclab/envs/manager_based_env.py:372
  main        scripts/debug_step.py:61
```

两点说明：

- **适配器在哪里**：`launch` 由编辑器启动一个调试适配器，再由适配器启动脚本；`attach` 不再启动适配器，因为 `debugpy.listen()` 已在脚本进程里起了一个，编辑器直接用 TCP 连上它。
- **`"console": "integratedTerminal"`**：VS Code 会在自己的终端里启动脚本，这要靠编辑器支持"在终端运行"请求。本站的命令行客户端不支持，验证时改用了 `internalConsole`，两者对断点没有影响（推断）。

Isaac Lab 自带的 `launch.template.json` 写的是 `"type": "python"`[^launch-tpl]，VS Code 文档已把这个写法标为弃用，现在用 `debugpy`[^vsc-debug]，本站示例用的就是后者。

## 远程开发

这一节回答：GPU 在另一台机器上，怎么用本地编辑器？

VS Code 的 Remote-SSH 扩展把语言服务、调试器都放在远程机器上运行，本地只负责界面[^remote-ssh]。用在 Isaac Lab 上，有三点要注意：

- **扩展装在远程端**：Python、Pylance 要在远程窗口里再装一次，extraPaths 写远程机器上的路径。
- **不要在远程开图形界面**：脚本一律加 `--headless`；要看画面，用 livestream 或录视频（[7.1](../7-infra/7.1-headless-remote.md)）。
- **端口转发**：TensorBoard、livestream 的端口用 SSH 转发回本地（[7.1](../7-infra/7.1-headless-remote.md)）。

本站只有一台机器，SSH 到本机模拟不可行（见 7.1），所以本节**未验证**，依据是 VS Code 官方文档。

## 日志与输出在哪

这一节回答：程序打印的东西去了哪里？

| 输出 | 位置（pip 安装） | 说明 |
|---|---|---|
| `print` | 终端（标准输出） | Kit 启动期间被 AppLauncher 暂时导到 `/dev/null`，加 `--info` 可看（[7.3](../7-infra/7.3-debugging.md)） |
| Kit 日志 | `<环境>/…/isaacsim/kit/logs/Kit/Isaac-Sim/5.1/` | 启动时终端打印 `Logging to file:` 与具体文件（[1.4](1.4-install-51-232.md) 表 1） |
| Isaac Lab 日志 | `/tmp/isaaclab/logs/` | 启动时终端打印具体文件名 |
| rsl_rl 训练输出 | `logs/rsl_rl/<实验名>/<时间戳>/` | TensorBoard 事件、checkpoint、配置快照 |
| 各类缓存 | 见 [1.7](1.7-install-methods.md) 表 4 | 着色器、纹理、资产下载缓存 |

*表 2：日志与输出的位置。*

## 其他工具

这一节回答：还有哪些工具值得知道？

- **ruff 与 pre-commit**：Isaac Lab 仓库的 `.pre-commit-config.yaml` 配了 ruff 检查（`--fix`）、ruff 格式化、codespell 与一组通用检查，`pyproject.toml` 把行宽定为 120[^precommit]。`./isaaclab.sh -f` 就是运行 pre-commit。自己的项目可以照抄这份配置。
- **`isaaclab.sh -p`**：用当前激活的 conda 或 venv 环境里的 `python` 运行脚本；都没有激活时，才用 `_isaac_sim/python.sh`[^lab-sh-p]。pip 方式下激活环境后直接 `python 脚本.py`，效果相同。
- **`isaaclab.sh -s`**：启动 Isaac Sim 图形界面，并把 Isaac Lab 的 `source/` 作为扩展目录加载。pip 方式下它改用 `isaacsim isaacsim.exp.full`[^lab-sh-s]。
- **Jupyter**：`isaacsim` 包在检测到 Jupyter（环境变量 `JPY_PARENT_PID`）时会设一个专用的环境变量[^jupyter]，说明官方考虑过在 Notebook 里用。但本站没有验证，也不推荐用 Notebook 跑训练。

## 常见坑

:::{admonition} 坑一：选错了解释器
:class: warning

VS Code 默认可能选系统 Python 或别的环境，这时所有 `isaaclab` 导入都报红，按 F5 运行则报 `ModuleNotFoundError`。两套环境并存时（[1.2](1.2-version-decision.md#两套并存)）尤其要看清状态栏里选的是哪个，3.0 的环境是 Python 3.12，5.1 的是 3.11。
:::

:::{admonition} 坑二：`isaacsim.core.*` 永远报"无法解析"
:class: warning

这不是配置写错了：`site-packages/isaacsim` 这个普通包遮住了各扩展目录里的同名命名空间，加 extraPaths 也没用（表 1）。只影响编辑器的补全与跳转，不影响运行。真要跳转，可以直接打开 `site-packages/isaacsim/exts/<扩展名>/` 下的源码。
:::

:::{admonition} 坑三：带界面时停在断点，整个窗口卡住
:class: warning

断点停住时，Kit 的主循环也停了，界面不再刷新。这是预期行为，不是程序死了，继续运行就恢复（[7.3](../7-infra/7.3-debugging.md)）。调试时尽量用 `--headless`。
:::

:::{admonition} 坑四：输出重定向到文件时，最后几行打印丢了
:class: warning

`simulation_app.close()` 会直接结束进程。标准输出被重定向到文件或管道时，Python 会缓冲输出，缓冲区里还没写出的内容就随进程一起丢了。本站在后台跑检查脚本时遇到过：结果行一行都没有，日志里也没有报错。解决办法是用 `python -u` 运行，或者在 `close()` 之前 `sys.stdout.flush()`。本站示例的退出三步就包含这一步（CONVENTIONS 第 5 节）。
:::

:::{admonition} 坑五：attach 时报 "Address already in use"
:class: warning

5678 端口还被上一次的 debugpy 适配器占着。强行结束被调试的进程（例如 `kill -9`）之后，适配器进程有时会留下来。先用 `ss -ltnp | grep 5678` 看是哪个进程占着端口，结束它再重试；也可以换一个端口（脚本里 `debugpy.listen` 与 `launch.json` 的 `port` 要一起改）。这个现象是校验方在强行结束目标进程后遇到的，本站只见过一次。
:::
