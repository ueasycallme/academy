# 场景组装与 Cloner

:::{admonition} 学习目标
:class: lead-goals

- 说清"一个环境 → 几千个环境"在 USD、PhysX、Fabric 三层各发生了什么

- 知道 `replicate_physics`、`use_fabric`、`clone_in_fabric`、Stage in Memory 各影响启动、每步耗时、显存中的哪一项
:::

4.5 讲了克隆怎么用：写 `{ENV_REGEX_NS}`、给 `num_envs`。本页往下一层，看克隆在 USD、PhysX、Fabric 里分别做了什么，以及各个开关的代价。示例代码在 `examples/isaaclab-2.3/3.7-cloner/`。

## 三层分工

这一节回答：克隆出来的几千个环境，分别"住"在哪一层？

```{mermaid}
%%{init: {"flowchart": {"rankSpacing": 26, "nodeSpacing": 30, "padding": 6}}}%%
flowchart TB
    LAB["Isaac Lab 资产的 data<br/>（torch 张量，N 个环境一批）"]
    TENS["PhysX 张量视图<br/>（GPU 缓冲，按环境批量读写）"]
    FAB["Fabric<br/>（位姿交给渲染器；use_fabric）"]
    PHYSX["PhysX 场景<br/>解析 env_0，复制出其余 N−1 份（replicate_physics）"]
    USD["USD Stage<br/>env_0 + env_1…env_N−1（继承 env_0）"]
    LAB --> TENS
    TENS --> PHYSX
    FAB --> PHYSX
    PHYSX --> USD
```

*图 1：克隆后的三层（箭头表示"构建在……之上"，D-010）。USD 层只放 Prim 和属性；PhysX 层是真正参与计算的刚体与关节；训练代码读写的是 PhysX 的 GPU 缓冲，渲染器的位姿走 Fabric。*

## Cloner：USD 层的复制

这一节回答：`env_1` 到 `env_N−1` 是怎么出现在 Stage 上的？

`isaacsim.core.cloner` 提供 `Cloner` 与它的子类 `GridCloner`。常用的四步[^cloner]：

1. `define_base_env("/World/envs")`：建一个 Scope，所有环境都放在它下面；
2. `generate_paths("/World/envs/env", N)`：只是生成路径字符串 `env_0`…`env_{N−1}`；
3. 在 `env_0` 下摆好资产；
4. `clone(source_prim_path, prim_paths, ...)`：在其余路径上生成克隆，`GridCloner` 按 `spacing` 把它们排成近似正方形的网格[^grid]。

`clone()` 的两个关键参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `copy_from_source` | False | False：克隆在 USD 里**继承**（inherits）`env_0`，改 `env_0` 会反映到所有克隆；True：逐个**复制**规格，彼此独立，更慢 |
| `replicate_physics` | False | True：向 PhysX 注册一个复制器（replicator），物理只解析 `env_0`，其余直接复制（下一节） |

*表 1：`Cloner.clone()` 的两个关键参数（Isaac Sim 5.1.0 源码[^clone-src]）。*

继承是 USD 的组合弧之一（[2.3](../2-usd-kit/2.3-layers-composition.md)）：克隆在根层只写了位置、姿态，以及"继承 `env_0`"这一条；它下面的机器人、方块都是组合出来的。本站用 `clone_bench.py` 检查 `env_1`：它的 inherits 列表是 `[/World/envs/env_0]`，`env_1/Cube` 存在，但在根层没有自己的规格；`replicate_physics=False` 时 inherits 为空，`env_1/Cube` 在根层有自己的规格，是逐个复制出来的（下一节）。

## replicate_physics：PhysX 只解析一次

这一节回答：为什么几千个环境的启动不是几千倍慢？

PhysX 拿到 Stage 后要"解析"：把 USD 里的刚体、碰撞体、关节变成内部对象，Prim 越多越慢。`replicate_physics=True` 时，Cloner 向 `omni.physx` 注册一个复制器：解析时跳过 `/World/envs` 下的克隆，只解析 `env_0`，再在 PhysX 内部复制 N−1 份[^replicate]。

Isaac Lab 的 `InteractiveScene` 按 `replicate_physics` 走两条路[^scene]：

- **True（默认）**：先只在 `env_0` 下生成资产，再整体克隆 `env_0`（继承），并注册复制器；
- **False**：先克隆空的环境 Xform，资产生成时由 spawner 在每个环境里各放一份，PhysX 逐个解析。各环境的资产可以不同（如不同尺寸的物体），代价是启动更慢。

代价是：复制出来的环境在物理上与 `env_0` 一模一样。要在 USD 层面让各环境不同（缩放尺寸、换材质），必须 `replicate_physics=False`（[4.12](../4-isaaclab/4.12-event-randomization.md)、[6.4.2](../6-galbot/4-task/6.4.2-domain-randomization.md)）；直接改 PhysX 参数的随机化（质量、摩擦）不受影响。

**环境之间的碰撞**：`filter_collisions=True`（默认）且在 GPU 上时，Isaac Lab 把 `enable_env_ids=True` 传给复制器，PhysX 按环境编号自动过滤克隆之间的碰撞[^replicate]；否则退回到 `scene.filter_collisions()` 建碰撞组。所以 [6.2.1](../6-galbot/2-scene/6.2.1-workbench-scene.md) 里选 `env_spacing` 主要是为了画面不重叠，而不是防止互相碰撞（对照实验见坑二）。

## Fabric、clone_in_fabric 与 Stage in Memory

这一节回答：还有哪些开关能省时间？

- **`use_fabric`**（`SimulationCfg`，默认 True[^simcfg]）：仿真结果不写回 USD，位姿经 Fabric 交给渲染器。它省的是**每步**的同步开销；后果是 USD 属性不随仿真更新，见 [4.4](../4-isaaclab/4.4-simulation-context.md) 表 3。
- **`clone_in_fabric`**（`InteractiveSceneCfg`，默认 False）：克隆直接写进 Fabric，不在 USD Stage 上生成 `env_1`…，建场景更快；之后只能用 USDRT 访问这些环境[^scene-cfg]。
- **Stage in Memory**（`SimulationCfg.create_stage_in_memory`，默认 False）：先在内存里建 Stage（`Usd.Stage.CreateInMemory()`），建完再挂到 USD 上下文。官方说明它省的是建场景时的开销，但"挂上去"这一步可能很慢，抵消收益；不能与 `clone_in_fabric` 同时开[^opt]。

## 实测

这一节回答：各个开关实际省了多少？

示例场景：每个环境一台 Cartpole 加一个小方块；物理步 1/120 s，不渲染。用时都在脚本里测，显存、主机内存按进程测（CONVENTIONS 第 5 节）。

```bash
python clone_bench.py --headless --num_envs 4096
python clone_bench.py --headless --num_envs 4096 --no_replicate
```

| 环境数 | 克隆 | reset（PhysX 解析） | 每个物理步 | 按进程显存 | 主机 RSS |
|---|---|---|---|---|---|
| 16 | 0.00 s | 0.41 s | 1.56 ms | 2315 MiB | 3.0 GB |
| 256 | 0.06 s | 0.42 s | 1.66 ms | 2315 MiB | 3.1 GB |
| 1024 | 0.12 s | 0.46 s | 1.66 ms | 2445 MiB | 3.1 GB |
| 4096 | 0.43 s | 0.66 s | 1.91 ms | 2903 MiB | 3.4 GB |

*表 2：默认设置下环境数与开销（本站实测，RTX 5070 12 GB，2026-10-09；每档 3 次取平均，reset 与每步耗时在 3 次之间相差 ≤ 5%）。"克隆"是 `Cloner.clone()` 的累计用时（脚本给它套了计时器）。*

| 设置（1024 个环境，另注者除外） | 克隆 | reset | 每个物理步 |
|---|---|---|---|
| 默认 | 0.12 s | 0.46 s | 1.66 ms |
| `replicate_physics=False` | 0.29 s | 0.78 s | 1.72 ms |
| 默认，4096 个环境 | 0.43 s | 0.66 s | 1.91 ms |
| `replicate_physics=False`，4096 个环境 | 1.18 s | 2.13 s | 1.94 ms |
| `use_fabric=False` | 0.12 s | 0.44 s | 1.67 ms |
| `clone_in_fabric=True` | 0.41 s（两档，见下） | 0.47 s | 1.69 ms |
| `create_stage_in_memory=True` | 0.12 s | 0.20 s | 1.67 ms |

*表 3：单因素对照（本站实测，条件同表 2，每组 3 次取平均）。各组显存与同环境数的默认设置相同，主机 RSS 相差不到 2%。*

观察到的结论（单因素对照，只对这个场景成立）：

- **克隆本身很便宜**：4096 个环境也只要 0.43 s。整个"建场景"的用时波动很大（本站与校验方各跑一批，在 1.7–5.5 s 之间，同一设置多次之间相差可近 2 倍），大头不在克隆，而在生成 `env_0` 的资产等其他步骤（推断：脚本只给克隆计了时）。
- **`replicate_physics` 省的是启动**：关掉后，4096 个环境的 reset 从 0.66 s 变成 2.13 s，克隆也慢了约 2.7 倍；每步耗时与显存不变，因为运行时 PhysX 里的东西是一样的。
- **每步耗时几乎不随环境数增长**：16 到 4096 个环境，每步只从 1.56 ms 涨到 1.91 ms。Cartpole 太轻，GPU 远没有喂饱。
- **`use_fabric=False` 在这里没有差别**：GPU 管线下仿真结果本来就不写回 USD（[4.4](../4-isaaclab/4.4-simulation-context.md) 表 3），无头、不渲染时也没有位姿要交给渲染器。
- **`clone_in_fabric` 在这里没有收益**：克隆反而慢了（0.41 s 对 0.12 s）。它的克隆用时呈两档：本站与校验方共 9 次中，7 次在 0.36–0.42 s，2 次在 0.74–0.80 s，原因未查。官方基准的收益出现在开渲染、4000 台 ShadowHand 时的"Fabric 挂接"一步[^opt]，本例无头运行，没有这一步。
- **Stage in Memory 让 reset 从 0.46 s 降到 0.20 s**，建场景没有明显变化。

## 常见坑

:::{admonition} 坑一：以为改 env_0 只影响 env_0
:class: warning

`replicate_physics=True`（默认）时，克隆继承 `env_0`。用 USD 把 `env_0/Cube` 的质量改成 2 kg，reset 后 8 个环境的 PhysX 质量全是 2.0；reset 之后再改成 5 kg，步进 10 步后也全变成 5.0（本站实测）。`replicate_physics=False` 时只有 `env_0` 变。所以要逐环境改参数，用事件项（[4.12](../4-isaaclab/4.12-event-randomization.md)）而不是改 `env_0` 的 USD。
:::

:::{admonition} 坑二：关掉 filter_collisions 后环境相互碰撞
:class: warning

把 `env_spacing` 设为 0，8 个方块落在同一点：`filter_collisions=True` 时它们互相穿过，1.5 s 后水平位置完全重合；设为 False 时它们互相挤开，最远被弹出 9.4 m（本站实测）。默认是 True，一般不要关。
:::

:::{admonition} 坑三：手写场景用 Stage in Memory，reset 时找不到 Prim
:class: warning

官方示例只把建场景包进了 `use_stage(sim.get_initial_stage())`[^opt]。本站照做后，`sim.reset()` 抛出 `RuntimeError: Failed to find prim for expression: '/World/envs/env_.*/Robot'`：资产初始化按当前 Stage 找 Prim，而那时的当前 Stage 是空的 USD 上下文。`sim.reset()` 也要包进去，`ManagerBasedEnv` 就是这样做的[^env-stage]。
:::

:::{admonition} 坑四：clone_in_fabric 后用 USD API 找不到 env_1
:class: warning

打开 `clone_in_fabric` 后，USD Stage 上只有 `env_0`，其余环境只在 Fabric 里（本站实测：`GetPrimAtPath("/World/envs/env_1")` 无效），要用 USDRT 访问[^scene-cfg]。
:::
