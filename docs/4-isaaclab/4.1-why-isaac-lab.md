## 只用 Isaac Sim，要自己做哪四件事

这一节回答：Isaac Lab 省掉了什么？

训练一个机器人策略，需要几千个环境同时跑，每一步把观测交给算法、把动作写回仿真。只用 Isaac Sim，下面四件事都得自己写：

| 重复劳动 | 只用 Isaac Sim 时 | Isaac Lab 的解决方式 |
|---|---|---|
| 并行环境的克隆与路径管理 | 自己建 `/World/envs/env_0`，调用 Cloner 复制 N 份，记住每份的路径 | `InteractiveScene`：场景写成配置，自动克隆，路径用 `{ENV_REGEX_NS}` 表示（[4.5](4.5-interactive-scene.md)） |
| GPU 张量数据的读写 | 自己建张量视图，处理索引、设备、坐标系 | `Articulation`、`RigidObject` 等资产类，状态放在 `data` 中（[4.6](4.6-assets.md)） |
| 任务定义的组织 | 观测、动作、奖励、终止、重置散落在一个大脚本里 | Manager 体系，每一项是一个可替换的 Term（[4.9](4.9-manager-based-env.md)） |
| 与 RL 库对接 | 自己把环境包装成 rsl_rl、skrl 等要求的接口 | `isaaclab_rl` 中的适配层（[4.16](4.16-rl-wrappers.md)） |

*表 1：Isaac Lab 省掉的四件事。*

## 同一件小事的两种写法

这一节回答：差别具体在哪？

任务：让 N 个 Cartpole 并行，读出所有关节位置。片段只展示关键调用，不是完整脚本。

**只用 Isaac Sim**（`isaacsim.core.cloner`、`isaacsim.core.prims`）[^sim-cloner][^sim-art]：

```python
cloner = GridCloner(spacing=4.0)
cloner.define_base_env("/World/envs")
add_reference_to_stage(CARTPOLE_USD, "/World/envs/env_0/Cartpole")   # 先建第一份
paths = cloner.generate_paths("/World/envs/env", N)
cloner.clone(source_prim_path="/World/envs/env_0", prim_paths=paths)  # 再复制 N 份
cartpoles = Articulation(prim_paths_expr="/World/envs/env_.*/Cartpole")
world.reset()                                                          # 初始化物理视图
q = cartpoles.get_joint_positions()                                    # (N, 关节数)
```

**用 Isaac Lab**（`isaaclab.scene`、`isaaclab.assets`）[^lab-cartpole-scene][^lab-scene]：

```python
@configclass
class CartpoleSceneCfg(InteractiveSceneCfg):
    robot: ArticulationCfg = CARTPOLE_CFG.replace(prim_path="{ENV_REGEX_NS}/Robot")

scene = InteractiveScene(CartpoleSceneCfg(num_envs=N, env_spacing=4.0))
sim.reset()
q = scene["robot"].data.joint_pos                                      # (N, 关节数)
```

后者没有路径拼接、没有手动克隆，场景是一份可以复用、可以覆盖参数的配置（[4.3 configclass](4.3-configclass.md)）。代价是多了一层抽象，要知道配置最终落到了哪个 Isaac Sim 调用上，这正是本部分要讲清的。

## 两种环境写法

这一节回答：写一个任务有哪几种方式？

- **Manager-based**：任务的每一部分（观测、奖励……）写成配置中的一项，由对应的 Manager 调用，适合模块化、便于复用和对比实验（[4.9](4.9-manager-based-env.md)）。
- **Direct**：自己写一个环境类，在方法里直接算观测和奖励，更接近传统 RL 环境的写法，代码更集中（[4.14](4.14-direct-env.md)）。

Cartpole 两种写法都有，分别在 `isaaclab_tasks` 的 `manager_based/classic/cartpole/` 与 `direct/cartpole/` 下[^lab-cartpole-dirs]。

## Isaac Lab 不做什么

这一节回答：哪些事要找别的工具？

- **不是仿真器**：物理、渲染、USD 都由 Isaac Sim 完成，Isaac Lab 只决定何时调用（见 [0.5](../0-map/0.5-sim-lab-boundary.md)、第 3 部分）。
- **不是 RL 算法库**：PPO 等算法来自 rsl_rl、skrl、rl_games 等外部库，Isaac Lab 只提供适配层（[4.16](4.16-rl-wrappers.md)；算法入门见 [5.3 PPO](../5-rl/5.3-ppo.md)）[^lab-eco]。
- **不含真机部署**：导出策略、接 ROS 2、上真机需要另外的工作（[6.7.1 策略导出](../6-galbot/7-deploy/6.7.1-policy-export.md)、[6.7.3 sim2real 清单](../6-galbot/7-deploy/6.7.3-sim2real-checklist.md)）。

## 常见误解

:::{admonition} 误解一：学会 Isaac Lab 就不用管 Isaac Sim
:class: warning

Isaac Lab 的配置最终都落到 Isaac Sim 与 USD 上。资产导入、物理参数、仿真循环出问题时，要回到第 2、3 部分的知识去排查。
:::

:::{admonition} 误解二：Isaac Lab 自带训练算法
:class: warning

`isaaclab_rl` 里只有适配层，训练用的是 rsl_rl 等外部库[^lab-eco]。换算法就是换适配层和对应的库。
:::

:::{admonition} 误解三：Manager-based 比 Direct 更"高级"
:class: warning

两者只是组织代码的方式不同，底层用的是同一套场景与资产。Manager-based 便于组合和复用，Direct 便于写一次性、逻辑紧凑的任务；官方的很多任务两种写法都有。
:::
