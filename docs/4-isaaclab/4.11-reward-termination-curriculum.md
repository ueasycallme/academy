## Reward Manager

这一节回答：总奖励是怎么算出来的？

奖励项用 `RewardTermCfg` 配置：`func(env, **params)` 返回形状为 (num_envs,) 的张量，`weight` 是权重[^term-cfg]。每个环境步，Reward Manager 把各项加权求和，**并乘以环境步长**[^reward]：

$$
r_t = \sum_{i} w_i \, f_i(s_t) \, \Delta t
$$

- $r_t$：第 $t$ 步返回给策略的总奖励，形状 (num_envs,)。
- $f_i$：第 $i$ 个奖励项的函数值。
- $w_i$：该项的 `weight`；权重为 0 的项直接跳过，不调用函数。
- $\Delta t$：环境步长 `step_dt` = `decimation` × `sim.dt`（Cartpole 为 1/60 s）。

乘 $\Delta t$ 的效果是：同一套权重下，一秒内得到的奖励总量与控制频率无关。本站示例实测第 1 步 env 0：各项 $w_i f_i$ 之和乘 $\Delta t$ 为 0.012269，与环境返回的奖励完全相等。

**日志**：每个环境重置时，Reward Manager 把该项本回合的累计值（已乘 $\Delta t$）对重置的环境取平均，**再除以 `episode_length_s`**，记为 `Episode_Reward/<项名>`[^reward-log]。所以一个跑满全程、每步都得 1 的存活项，记为 1.0；回合提前结束，这个数就按比例变小。

## 常用奖励函数

这一节回答：`mdp` 里有哪些现成的奖励？

| 类别 | 函数 | 输出 | 权重通常 |
|---|---|---|---|
| 任务目标 | `track_lin_vel_xy_exp` / `track_ang_vel_z_exp` | $\exp(-e^2/\sigma^2)$，$e$ 为速度跟踪误差，范围 (0, 1] | 正 |
| 任务目标 | `joint_pos_target_l2`（Cartpole 任务自带） | 关节位置与目标差的平方和 | 负 |
| 正则惩罚 | `action_rate_l2` | 相邻两步动作差的平方和 | 负 |
| 正则惩罚 | `joint_torques_l2` / `joint_acc_l2` | 关节力矩 / 加速度的平方和 | 负 |
| 正则惩罚 | `joint_vel_l1` | 关节速度绝对值之和 | 负 |
| 存活 | `is_alive` | 未失败为 1，否则为 0 | 正 |
| 存活 | `is_terminated` | 失败为 1（**不含超时**），否则为 0 | 负 |

*表 1：`isaaclab.envs.mdp` 中的典型奖励函数（v2.3.2）[^rewards-fn]。所有函数都返回 (num_envs,)，符号由权重决定。*

## Termination Manager

这一节回答：失败和超时有什么区别？

终止项用 `TerminationTermCfg` 配置：`func` 返回形状为 (num_envs,) 的布尔张量，`time_out` 标明它是否算超时[^term-cfg]。每步计算时，`time_out=True` 的项汇入 **truncated**（截断），其余汇入 **terminated**（失败）[^termination]，分别作为 `step()` 返回值的第 3、4 项，与 Gymnasium 的 `step()` 接口一致[^gym]。任一项为真，该环境就重置。

**为什么要分开**：失败意味着回合真正结束，之后没有奖励；超时只是人为截断，如果继续跑，本来还有奖励。计算回报时，前者后续价值取 0，后者应该用价值网络估计的后续价值补上（称为自举，bootstrapping）。RSL-RL 的做法是：适配层把 truncated 放进 `extras["time_outs"]`（`is_finite_horizon=False` 时，默认如此）[^wrapper]，PPO 在超时的那一步把奖励加上 $\gamma V(s_t)$[^rslrl]：

$$
\tilde r_t = r_t + \gamma \, V(s_t) \cdot \mathbb{1}[\text{超时}]
$$

- $\tilde r_t$：用于计算回报的奖励。
- $\gamma$：折扣因子。
- $V(s_t)$：价值网络对该步状态的估计。
- $\mathbb{1}[\text{超时}]$：该环境本步超时为 1，否则为 0。

常用的终止函数有 `time_out`（超时）、`joint_pos_out_of_manual_limit`（关节超出给定范围）、`root_height_below_minimum`（根部过低）、`bad_orientation`（姿态倾斜过大）、`illegal_contact`（指定部位接触力超阈值，需要接触传感器）[^terminations-fn]。

**回合长度**：`episode_length_s` 按环境步长换算成步数，向上取整：`max_episode_length = ceil(episode_length_s / step_dt)`[^max-len]。Cartpole 为 ceil(5 / (1/60)) = 300 步。`time_out` 的判断是 `episode_length_buf >= max_episode_length`。

## Curriculum Manager

这一节回答：怎么让任务随训练变难？

课程项用 `CurriculumTermCfg` 配置：`func(env, env_ids, **params)`，返回值作为状态写进日志 `Curriculum/<项名>`[^term-cfg][^curriculum]。它在 `_reset_idx` 的第一步被调用，`env_ids` 是本步要重置的环境（见 [4.9](4.9-manager-based-env.md#执行顺序)），所以只在有环境重置时才运行。官方任务中的三种典型用法：

- **按进度改奖励权重**：`modify_reward_weight`。Lift 任务在 `common_step_counter` 超过 10000 后，把 `action_rate`、`joint_vel` 的权重改为 −0.1[^lift]。
- **改地形等级**：`terrain_levels_vel`。运动任务中，走得够远的机器人升到更难的地形，走不到要求距离一半的降级[^terrain]。
- **改其他配置**：`modify_term_cfg` / `modify_env_param` 按点号路径修改任意参数。Dexsuite 用它逐步放宽观测噪声的范围[^dexsuite]。

## 读训练日志

这一节回答：训练输出里的分项怎么看？

RSL-RL 每次迭代打印 `Mean reward`、`Mean episode length`，以及环境重置时产生的各项日志。本站实测 Cartpole 训练的输出片段：

```text
               Mean episode length: 14.00
              Episode_Reward/alive: 0.0723
           Episode_Reward/pole_pos: -0.0404
      Episode_Termination/time_out: 0.0967
Episode_Termination/cart_out_of_bounds: 0.0000
```

- **`Episode_Reward/<项名>`**：见上文，是除以 `episode_length_s` 后的平均值。拿各项互相比较，能看出哪一项主导了总奖励。
- **`Episode_Termination/<项名>`**：所有环境中，最近一个回合因该项结束的比例[^termination-log]。失败项比例下降、`time_out` 比例上升，通常说明策略在变好。
- **`Curriculum/<项名>`**：课程项的当前状态，如地形等级或权重。
- 训练开始时，`train.py` 会把各环境的回合计数随机初始化（`init_at_random_ep_len=True`）[^train]，所以最初几次迭代就有超时，平均回合长度也偏短，不代表策略已经学会。

PPO 的输出指标见 [5.3](../5-rl/5.3-ppo.md)，主线任务的日志解读见 [6.5.1](../6-galbot/5-train/6.5.1-train-reach-rsl-rl.md)。

## 示例

本站示例 `examples/isaaclab-2.3/4.11-reward-termination/reward_termination_demo.py` 继承官方 Cartpole，加三处：

- 奖励 `action_rate`（`action_rate_l2`，权重 −0.01）；
- 终止 `pole_fallen`（摆杆超出 ±90°）；
- 课程：环境步计数超过 100 后，把 `action_rate` 的权重改为 −0.1。

运行 320 步，打印分项奖励与最近一次重置时的日志。本站实测（16 个环境，种子 42，每次约 8 秒，两次运行输出一致）：

| 运行方式 | 失败 / 超时次数 | `Episode_Reward/alive` | `Episode_Termination` |
|---|---|---|---|
| 随机动作，含 `pole_fallen` | 148 / 0 | 0.1633 | `pole_fallen` 1.0 |
| `--zero_action --no_pole_fallen` | 0 / 16 | 1.0000 | `time_out` 1.0 |

*表 2：示例输出。第一行存活项 0.1633 ≈ 49 步 × 1/60 s ÷ 5 s，回合平均只有约 49 步。两行中 `action_rate` 的权重最后都是 −0.1（课程已生效）。第二行 `Episode_Reward/pole_pos` 为 −5.54，远大于存活项的 1.0：零动作时摆杆倒下，该项主导了总奖励。*

## 常见坑

:::{admonition} 坑一：权重符号写反
:class: warning

惩罚项的函数通常返回非负值（平方和、绝对值），要靠负权重变成惩罚。写成正权重，策略会去"追求"大力矩、大动作。检查启动时打印的 Reward 表，并看 `Episode_Reward/*` 的符号是否符合预期。
:::

:::{admonition} 坑二：把超时当失败
:class: warning

超时项忘了写 `time_out=True`，就会被当作失败：`is_terminated` 惩罚会作用于跑满全程的好回合，价值自举也不会发生。反过来，把真正的失败标成超时，策略学不到"避免失败"。
:::

:::{admonition} 坑三：各项奖励的尺度相差几个数量级
:class: warning

权重要抵消各项原始量级的差异：官方运动任务中，`track_lin_vel_xy_exp` 权重为 1.0，`joint_acc_l2` 为 −2.5e-7[^loco]。某一项过大就会淹没其余各项（示例第二行的 `pole_pos`）。先用 `Episode_Reward/*` 看各项量级，再调整权重。
:::

:::{admonition} 坑四：课程的 `num_steps` 按环境步计
:class: warning

`modify_reward_weight` 比较的是 `common_step_counter`，即环境步数，不是训练迭代数。以 RSL-RL 每次迭代每个环境采 24 步计，Lift 的 10000 步约为 417 次迭代。
:::
