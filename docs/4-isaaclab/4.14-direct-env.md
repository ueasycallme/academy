# Direct 环境

:::{admonition} 学习目标
:class: lead-goals

- 知道 `DirectRLEnv` 要实现哪些方法，以及它们在 `step()` 里的位置
- 能把 Manager-based 写法的每一块对应到 Direct 写法
- 能按自己的任务判断选哪种写法
:::

:::{admonition} 前置知识
:class: lead-prereq

- [4.9 Manager-based 环境：总览](4.9-manager-based-env.md)
- [0.6 一个 RL step 里发生了什么](../0-map/0.6-one-step.md)
:::

[0.6 锚点图](../0-map/0.6-one-step.md) 的图注提到：Direct 环境把 Action Manager 与其他 Manager 换成子类方法。本页展开这一点。**Direct 环境**不用 Manager，所有逻辑写在一个继承 `DirectRLEnv` 的类里[^workflows]。

## 要实现的方法与调用位置

这一节回答：Direct 环境的 `step()` 里依次调用了什么？

`DirectRLEnv.step()` 的骨架与 `ManagerBasedRLEnv` 相同，只是在每个位置调用子类方法[^step]：

| 步骤 | Manager-based | Direct（子类实现） |
|---|---|---|
| 处理动作（每个环境步一次） | `action_manager.process_action` | `_pre_physics_step(actions)` |
| 写入动作（每个物理步一次） | `action_manager.apply_action` | `_apply_action()` |
| 判断终止 | `termination_manager.compute` | `_get_dones()` → (terminated, time_out) |
| 计算奖励 | `reward_manager.compute(dt)` | `_get_rewards()` |
| 重置 | `_reset_idx`：课程、场景、事件、各 Manager | `_reset_idx(env_ids)`，**须先调用 `super()._reset_idx`** |
| 定时事件 | `event_manager.apply("interval")` | 同左（配置了 `events` 时） |
| 计算观测 | `observation_manager.compute` | `_get_observations()` → `{"policy": …}` |
| 建场景（构造时一次） | `InteractiveScene(cfg.scene)` | 同左，另调用 `_setup_scene()` 自行添加资产 |

*表 1：`step()` 各步骤在两种写法中的对应（v2.3.2）[^step][^rlenv]。decimation 循环、`scene.write_data_to_sim`、`sim.step`、`scene.update` 都由基类完成，两种写法相同。*

`_pre_physics_step`、`_apply_action`、`_get_observations`、`_get_rewards`、`_get_dones` 是抽象方法，必须实现；`_setup_scene` 默认为空[^abstract]。基类的 `_reset_idx` 负责 `scene.reset`、reset 事件、噪声模型重置和回合计数清零[^reset]；子类在调用它之后，再写入自己的初始状态。

## 配置：`DirectRLEnvCfg`

这一节回答：Direct 环境的配置里有什么？

| 字段 | 说明 |
|---|---|
| `observation_space` / `action_space` | 必填。整数表示一维张量的维度，也可以是 Gymnasium 空间 |
| `state_space` | 可选，非对称 actor-critic 中 critic 的输入（见 [4.10](4.10-observation-action.md)），默认 None |
| `decimation` / `episode_length_s` / `scene` | 必填，含义同 Manager-based |
| `sim` / `viewer` / `seed` / `is_finite_horizon` | 同 Manager-based |
| `events` | 可选。设置后基类会创建 Event Manager，四种 mode 都可用（[4.12](4.12-event-randomization.md)） |
| `observation_noise_model` / `action_noise_model` | 可选。对 `policy` 观测、对动作整体加噪声 |

*表 2：`DirectRLEnvCfg` 的主要字段（v2.3.2）[^cfg]。任务自己的参数（如奖励系数）直接写成配置类的字段。*

## 并排对照：官方 Cartpole

这一节回答：同一个任务，两种写法各写在哪、写了多少？

| 关注点 | Manager-based（写在哪） | 行数 | Direct（写在哪） | 行数 |
|---|---|---|---|---|
| 场景 | `CartpoleSceneCfg` | 11 | `_setup_scene` | 9 |
| 动作 | `ActionsCfg` | 3 | `_pre_physics_step` + `_apply_action` | 4 |
| 观测 | `ObservationsCfg` | 10 | `_get_observations` | 12 |
| 重置 | `EventCfg` | 20 | `_reset_idx` | 19 |
| 奖励 | `RewardsCfg` + `joint_pos_target_l2` | 23 | `_get_rewards` + `compute_rewards` | 34 |
| 终止 | `TerminationsCfg` | 7 | `_get_dones` | 7 |
| 总配置 | `CartpoleEnvCfg` | 14 | `CartpoleEnvCfg` + `__init__` | 29 |
| 文件合计（含 import） | 2 个文件 | 110 | 1 个文件 | 129 |

*表 3：代码行数（不含空行、注释与 docstring），由本站脚本 `examples/isaaclab-2.3/4.14-direct-env/count_lines.py` 对 tag v2.3.2 统计[^cartpole-m][^cartpole-d]。Manager-based 的函数体大多在 `isaaclab.envs.mdp` 库里，不计入。*

行数相近，差别在组织方式：Manager-based 每一项是一行配置，逻辑在库函数里；Direct 的逻辑都在自己的类里，一眼能看到全部计算。

**两个版本并不等价**，对比时要注意[^cartpole-m][^cartpole-d]：

- **奖励**：Direct 版不乘 `dt`，数值是 Manager 版的 60 倍（1 / step_dt）。
- **终止**：Direct 版还在摆杆超过 90° 时终止；超时判断为 `>= max_episode_length - 1`，比 Manager 版早一步。
- **重置**：Direct 版只随机化摆杆角度；Manager 版还随机化小车位置与两个速度。
- **观测**：Direct 版的顺序是摆杆角、摆杆角速度、小车位置、小车速度；Manager 版按关节顺序排列，先小车后摆杆，位置在前、速度在后。

## 怎么选

这一节回答：我的任务该用哪种写法？

| 维度 | Manager-based | Direct | 依据 |
|---|---|---|---|
| 模块化与复用 | 每一项可单独替换，适合多人分工 | 逻辑集中在一个类里 | 官方文档 |
| 精细控制 | 受 Manager 流程约束 | 完全自由，适合难拆分的复杂逻辑 | 官方文档 |
| 性能优化空间 | 逐项调用 | 可把计算集中起来用 Torch JIT 或 Warp 优化 | 官方文档（"may"） |
| 从 IsaacGymEnvs 迁移 | 需要拆成配置项 | 结构最接近 | 官方文档 |
| 调试 | 启动时打印各项表格，日志自动带分项奖励 | 要自己打印、自己写 `extras["log"]` | 源码与经验 |
| 改配置 | 命令行可覆盖任一项的参数 | 只能覆盖配置类的字段 | 经验 |

*表 4：两种写法的取舍[^workflows]。"依据"列标明哪些是官方说法、哪些是本站经验。*

**建议**（经验）：新任务、需要反复调奖励和随机化的任务，以及多人协作的任务，用 Manager-based；逻辑高度耦合（如多阶段装配）、从 IsaacGymEnvs 迁移，或已确认环境计算是瓶颈时，用 Direct。本站主线的 Galbot 任务用 Manager-based（[6.4.1](../6-galbot/4-task/6.4.1-reach.md)），另有一版 Direct 写法对照（[6.4.4](../6-galbot/4-task/6.4.4-reach-direct.md)）。

## 性能

这一节回答：Direct 真的更快吗？

官方文档只说 Direct "may" 带来性能优势，没有给出基准数据[^workflows]。本站实测两个 Cartpole 在相同环境数下的步进速度，示例为 `examples/isaaclab-2.3/4.14-direct-env/bench_cartpole.py`：headless、随机动作，先预热 100 步，再计时 1000 步，每种各跑 3 次。

| 环境数 | 写法 | 实现方 3 次（环境步/s） | 校验方 3 次（环境步/s） |
|---|---|---|---|
| 1024 | Manager-based | 294,092–303,087 | 300,906–305,477 |
| 1024 | Direct | 309,897–318,982 | 285,609–322,831 |
| 64 | Manager-based | 22,535–23,461 | 22,118–22,935 |
| 64 | Direct | 21,523–21,870 | 22,047–22,217 |

*表 5：本站实测（RTX 5070，2026-09-30）。测量条件：官方 `Isaac-Cartpole-v0` 与 `Isaac-Cartpole-Direct-v0`，headless，随机动作，预热 100 步后计时 1000 步；每种配置由两个独立会话各跑 3 次。两种写法的差距在运行波动之内：同一配置的 6 次之间最多相差 13%（1024 个环境的 Direct），两个会话各自算出的两种写法均值差为 0.7%–6%，而且哪种更快并不稳定。*

结论：对 Cartpole 这样简单的任务，两种写法的速度在 ±6% 以内，且快慢随环境数变化。两个版本的终止与重置逻辑本就不同（上一节），这点差异不能归因于写法本身。时间主要花在物理仿真和基类流程上；Direct 的性能优势要在环境计算本身很重、并做了专门优化时才可能体现（推断）。

## 在 Direct 里用现成组件

这一节回答：Direct 环境能不能用 Manager 那套组件？

可以部分使用：

- **事件**：配置 `events` 后，Event Manager 与四种 mode 照常工作。事件参数里的 `SceneEntityCfg` 由 Event Manager 解析，官方 Direct 任务 ANYmal-C、Shadow Hand、FORGE 都这样用[^events-direct]。
- **噪声**：`observation_noise_model` 与 `action_noise_model` 由基类在 `step()` 中施加；注意观测噪声只加在 `policy` 上，不加在 `critic` 上[^step]。
- **非对称 actor-critic**：设 `state_space`，并在 `_get_observations()` 的返回值里自己加上 `"critic"` 键。基类不会调用 `_get_states()`；官方 Direct 任务（如 Factory、Shadow Hand 视觉版）都是在 `_get_observations` 中直接返回 `{"policy": …, "critic": …}`[^critic]。

## 常见坑

:::{admonition} 坑一：重写 `_reset_idx` 时没有先调用 `super()._reset_idx`
:class: warning

基类的 `_reset_idx` 负责 `scene.reset`、reset 事件和 `episode_length_buf` 清零[^reset]。漏掉这一步，回合计数不会归零，超时判断会一直为真，环境每步都在重置。
:::

:::{admonition} 坑二：把两个 Cartpole 的奖励当成可比的
:class: warning

Direct 的 `_get_rewards` 返回什么就是什么，基类不乘 `dt`；Manager-based 会乘。从一种写法改写成另一种时，奖励尺度会差 1 / step_dt 倍，需要相应调整权重或 PPO 的超参数。
:::

:::{admonition} 坑三：定义了 `_get_states` 却没有生效
:class: warning

`state_space` 只声明观测空间；基类不会调用 `_get_states()`。要让 critic 拿到特权信息，需要在 `_get_observations` 中返回 `"critic"` 键[^critic]。
:::

:::{admonition} 坑四：以为 Direct 写法一定更快
:class: warning

见表 5：简单任务上几乎没有差别。先用 Manager-based 把任务做对；确认环境计算是瓶颈后，再考虑改写成 Direct 并做 JIT 或 Warp 优化。
:::
