## 设备抽象

所有设备都继承 `DeviceBase`[^base]，对外只有三个方法：`reset()` 清空内部状态，`add_callback(key, func)` 给某个按键或手势挂回调，`advance()` 返回当前命令。`advance()` 的默认实现先调 `_get_raw_data()` 取原始数据，再依次交给配置里的 retargeter，把各自的输出拼接起来；键盘这类简单设备直接重写 `advance()`。

| 类 | 输入来源 | 额外依赖 | `advance()` 输出 | 本站 |
|---|---|---|---|---|
| `Se3Keyboard` | Kit 窗口的键盘事件（`carb.input`） | 无 | 6 维 Δ位姿 + 1 维夹爪 | 实测（脚本注入按键） |
| `Se3Gamepad` | Kit 的手柄事件（`carb.input`） | 无 | 同上 | 未验证 |
| `Se3SpaceMouse` | USB HID 设备 | `hid`（hidapi） | 同上 | 未验证 |
| `HaplyDevice` | Haply SDK 的 WebSocket（默认 `ws://localhost:10001`） | `websockets` | 10 维：绝对位置、四元数（xyzw 顺序）与 3 个按钮 | 未验证 |
| `OpenXRDevice`、`ManusVive` | OpenXR 运行时（头显（headset）、手部追踪） | Kit 的 XR 扩展（`omni.kit.xr.core`），`--xr` 启动 | 原始追踪数据，交给 retargeter | 未验证 |

*表 1：Isaac Lab 2.3.2 的设备类[^devices]。`Se2Keyboard`、`Se2Gamepad`、`Se2SpaceMouse` 是给移动底盘用的，输出平面速度（vx、vy、ωz），本页不展开。*

键盘的按键约定：W/S、A/D、Q/E 沿 x、y、z 平移，Z/X、T/G、C/V 绕 x、y、z 转，K 切换夹爪开合，L 清零。按下时把对应轴加上灵敏度，松开时减掉，所以 `advance()` 给出的是"按住期间每一步的增量"，而不是累计位姿[^kbd]。

设备怎样创建有两条路。环境配置里写了 `teleop_devices`（一个"名字 → 设备配置"的字典），就由 `create_teleop_device(name, ...)` 按配置的 `class_type` 构造，并顺带构造 retargeter[^factory]。例如官方 Franka 堆方块任务 `Isaac-Stack-Cube-Franka-IK-Rel-v0` 配了 `"handtracking"`（OpenXR）和 `"keyboard"` 两个设备[^stack]。没写这个字段的任务，`teleop_se3_agent.py` 按 `--teleop_device` 自己 new 一个设备作后备，键盘的灵敏度是 0.05 × `--sensitivity`[^agent-fallback]。

## retargeter：把手的姿态变成末端命令

键盘和手柄的输出本身就是"末端往哪动多少"。VR 给的却是手的 26 个关节点位姿，需要一层翻译，这就是 retargeter[^rt]。它只有一个方法 `retarget(data)`，并通过 `get_requirements()` 声明自己需要手部、头部还是控制器数据，设备就只采集这些。机械臂常用的两个是：`Se3RelRetargeter` 取手腕（或拇指与食指中点）相邻两帧的位姿差，乘上比例系数，作为末端增量；`GripperRetargeter` 按拇指尖与食指尖的距离决定开合，并带滞回（hysteresis），避免来回跳[^rt-manip]。人形机器人（GR1-T2、G1）另有整手重定向到灵巧手关节的 retargeter，见 [4.19](4.19-mimic.md)。

## 从设备到动作

`teleop_se3_agent.py` 只支持 manager-based 环境。主循环很短[^agent-loop]：

1. `action = teleop_interface.advance()`，得到 7 维命令；
2. `actions = action.repeat(env.num_envs, 1)`，复制给每个环境；
3. `env.step(actions)`；按 R 时重置环境和设备。

能把 7 维命令直接喂进 `env.step()`，是因为任务的动作空间正好是 7 维：`Isaac-Lift-Cube-Franka-IK-Rel-v0` 的 `arm_action` 是相对模式（relative mode）的微分 IK（`DifferentialInverseKinematicsActionCfg`，`use_relative_mode=True`，`scale=0.5`），`gripper_action` 是二值夹爪[^ik-cfg]。每个控制步，IK 动作项先把 6 维增量乘 0.5，加到末端**当前**位姿上，得到目标位姿；再在每个物理子步用雅可比（Jacobian）求关节目标[^ik-act]。

为什么遥操作任务用 IK 动作而不用关节动作？人想的是"手往前一点"，不是"第 2、4 关节各转多少"。设备天然给出笛卡尔空间的增量，换成关节量这件事交给 IK。同一个任务的关节位置版本 `Isaac-Lift-Cube-Franka-v0` 动作是 8 维关节目标，键盘的 7 维命令喂不进去。

## 实测：用脚本"按键"

本站只有键盘，而且实现方无法操作桌面窗口，所以用脚本代替手指：`keyboard_teleop_probe.py` 经 `carb.input` 的 InputProvider 把"按下 / 松开"事件放进输入缓冲并立即分发。这走的是 `Se3Keyboard` 自己订阅的回调，只绕过了键盘硬件和窗口焦点。

```bash
python examples/isaaclab-2.3/4.20-teleop/keyboard_teleop_probe.py --headless --enable_appwindow
```

脚本照 `teleop_se3_agent.py` 的后备设置建键盘（灵敏度 0.05），在 `Isaac-Lift-Cube-Franka-IK-Rel-v0` 上每个键按住 25 步（0.5 s）再松开、等 25 步。末端指 IK 跟踪的点（`panda_hand` 沿 z 偏移 0.107 m），在机器人根坐标系下测量：

| 键 | 按住时 `advance()` | 末端位移（根坐标系） | 末端转动 | 指关节位置 |
|---|---|---|---|---|
| W | [0.05, 0, 0, 0, 0, 0, 1] | [+5.9, 0, 0] cm | 0.001 rad | 0.04 m |
| Q | [0, 0, 0.05, 0, 0, 0, 1] | [0, 0, +6.0] cm | 0.001 rad | 0.04 m |
| A | [0, 0.05, 0, 0, 0, 0, 1] | [0, +5.9, 0] cm | 0.000 rad | 0.04 m |
| C | [0, 0, 0, 0, 0, 0.05, 1] | [0, +0.3, 0] cm | 0.059 rad，转轴 [0, 0, +1.00] | 0.04 m |
| K（按一下） | […, −1] | 0 | 0.001 rad | 0.0001 m |

*表 2：脚本按键的结果（2026-10-10 实测，RTX 5070；进程显存 1433 MiB，主机内存 3.1 GB，用时 12 s）。`--enable_appwindow` 的原因见坑一，运行说明见示例目录的 README。松开后 `advance()` 回到全 0，夹爪位保持上一次的状态。*

三点可以读出来：

- **链路是通的。** 每个键只动对应的那一个轴，另外两个轴的位移都在 0.1 cm 以内（表中记为 0）；K 让两个指关节从 0.04 m 合到 0.0001 m。
- **增量是"目标往前挪一点"，不是"走这么远"。** 每步命令 0.05，乘动作项的 `scale` 0.5，目标比当前位置远 2.5 cm。25 步若全部走到，应该是 62.5 cm，实际只走了约 6 cm：每一步都从**当前**位置重新算目标，手臂跟不上，目标就一直只领先 2.5 cm。所以手感是"按住匀速走"，速度由 IK 与关节 PD 的跟踪能力决定，本例按住 0.5 s 走约 6 cm，约 12 cm/s。
- **方向在根坐标系里。** C 键的转轴是根坐标系的 +z。Franka 默认姿态下手爪朝下，手自身的 z 轴大致指向根坐标系的 −z；若转动是在手的坐标系里施加的，转轴应接近 [0, 0, −1]（推断，本页没有打印手的姿态）。这与源码一致：位置增量直接加在根坐标系的末端位置上，转动增量左乘在当前姿态上[^ik-act]。

## 录制示范

`scripts/tools/record_demos.py` 在同样的遥操作循环上，挂一个录制管理器（recorder manager），把每一步写进 HDF5[^rec]：

```bash
./isaaclab.sh -p scripts/tools/record_demos.py --task Isaac-Stack-Cube-Franka-IK-Rel-v0 \
    --teleop_device keyboard --dataset_file ./datasets/dataset.hdf5 --num_demos 10
```

它对环境配置做了几处改动：强制 1 个环境；把 `terminations.success` 取出来，在主循环里自己判断，连续 `--num_success_steps`（默认 10）步成功才算一条示范；关掉超时；观测不拼接；导出方式固定为"只导出成功的回合"；按 `--step_hz`（默认 30）限速。按 R 会丢弃当前这条，重来。

`record_probe.py` 照搬这些改动，在 `Isaac-Stack-Cube-Franka-IK-Rel-v0` 上用脚本按键录了 66 步。由于没有完成堆叠，它把导出方式改成"全部导出"，好让这一条落盘。导出的结构如下（`data/demo_0/` 下）：

| 组 / 数据集 | 形状 | 内容 |
|---|---|---|
| `actions` | (66, 7) | 每步送进 `env.step()` 的动作，就是 `advance()` 的输出 |
| `processed_actions` | (66, 8) | 动作项处理后的值：IK 增量 × 0.5（6 维），夹爪换算成两个指关节目标（2 维） |
| `obs/` | 每项 (66, n) | policy 组的各观测项，不拼接：`eef_pos`、`eef_quat`、`cube_positions`、`joint_pos`、`gripper_pos` 等 9 项 |
| `states/` | 每项 (66, n) | 每步之后的场景状态：机器人关节位置 / 速度、根位姿，三个方块的根位姿 / 速度 |
| `initial_state/` | 每项 (1, n) | 回合开始时的同一组状态，回放时用来复原场景 |

*表 3：录制结果的 HDF5 结构（2026-10-10 实测）。`demo_0` 的属性是 `num_samples=66`、`success=False`；`data` 的属性 `env_args` 记了任务名与 `dt` 0.01、`decimation` 5。*

`states` 与 `initial_state` 足以把场景逐步复原，这是 `replay_demos.py` 回放、[4.19](4.19-mimic.md) Mimic 生成新数据的基础；`obs` 与 `actions` 则直接用于行为克隆。

## 常见坑

### 坑一：headless 下键盘设备建不起来

`--headless` 启动时没有加载 `omni.appwindow` 扩展。`Se3Keyboard` 在构造函数里要取默认窗口的键盘，于是直接报错 `AttributeError: module 'omni' has no attribute 'appwindow'`（本站实测）。`teleop_se3_agent.py` 会捕获这个异常，打印 "Failed to create teleop device" 后退出（L227–L231；本站没有单独跑这一步，推断）。手动启用扩展后可以创建，但拿到的是名为 `offscreen` 的虚拟键盘，没有窗口可以聚焦，真键盘的事件进不来。所以用真键盘遥操作必须开窗口；headless 只适合本页这种脚本注入。

### 坑二：按键方向以机器人根坐标系为准

W 是根坐标系的 +x，不是"屏幕里往前"，也不是"手指的方向"；转动也绕根坐标系的轴（表 2 的 C 键）。机器人底座转了 90°，W 的方向就跟着转。在视口里操作时，先看清机器人底座的朝向。

### 坑三：任务没有 `success` 项，就录不下来

`record_demos.py` 只导出成功的回合，而成功由 `terminations.success` 判断。lift 任务只有 `time_out` 与 `object_dropping`，没有 `success`，脚本只给一句警告（L213–L221），`process_success_condition()` 在没有 success 项时直接返回"未成功"（L335–L352），于是一条也不会导出[^rec]。stack 任务有 success 项，只是表 3 那一段没有完成堆叠；把 `record_probe.py` 换成"只导出成功"模式重跑这一段，同样得到 `data` 下 0 个回合。录 lift 类任务前，先给任务加一个 `success` 终止项；官方 stack 任务已经有了（`cubes_stacked`）。

### 坑四：`teleop_se3_agent.py` 不限速

它的主循环里没有限速，仿真能跑多快就跑多快；`record_demos.py` 则按 `--step_hz` 限速。本页的脚本同样没有限速，在空闲主机上 headless 跑 3 次，都是 113–114 步/s，约为 lift 任务实时速度（50 步/s）的 2.3 倍。开着窗口渲染时会慢得多。按住同一个键同样长的时间，两个脚本里手臂走的距离可能不同。
