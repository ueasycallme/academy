:::

:::{admonition} 前置知识

- [4.2 代码仓库地图](4.2-repo-map.md)
- Python 的 `dataclass` 基础

Isaac Lab 里几乎所有东西都先写成一份配置：场景、资产、传感器、观测、奖励、仿真参数，乃至 RL 算法参数。本页讲这些配置的共同底座 [`configclass`](../0-map/0.8-glossary.md#term-configclass)。

## 它是什么

这一节回答：`@configclass` 比 `@dataclass` 多了什么？

`configclass` 是对 Python `dataclass` 的封装[^cc-doc]。它解决的主要是原生 dataclass 用于配置时的不便：

| 功能 | 说明 | 源码位置[^cc] |
|---|---|---|
| 免写类型注解 | 没写注解的字段按默认值推断类型 | `_add_annotation_types`，L182 起 |
| 可变默认值 | 可以直接写 `gains: list = [1.0, 2.0]`，每个实例各有一份深拷贝 | `_process_mutable_types` L303 起；`_custom_post_init` L385 起 |
| `MISSING` | 必填字段，调用 `validate()` 时检查 | `_validate`，L246 起 |
| `to_dict()` / `from_dict()` | 与字典互转，命令行覆盖就是靠 `from_dict` | L116、L128 起 |
| `replace(**kw)` | 复制一份并改部分字段，原对象不变 | L145 起 |
| `copy()` | 深拷贝 | L172 起 |

*表 1：`configclass` 附加的功能（`isaaclab/utils/configclass.py`，v2.3.2）。这些方法在装饰时通过 `setattr` 挂到类上（L98–L102）。*

本站示例 `examples/isaaclab-2.3/4.3-configclass/configclass_demo.py` 逐项演示了这些行为，实测输出节选：

```text
a.gains = [1.0, 2.0, 3.0], b.gains = [1.0, 2.0]      ← 两个实例不共享同一个列表
c.name = c, a.name = a                               ← replace 返回新对象
TypeError: Missing values detected in object DemoCfg for the following fields:
  - name                                             ← validate 发现未填的 MISSING 字段
```

## "配置 + 类"的成对约定

这一节回答：一份配置是怎么变成真正的对象或行为的？

Isaac Lab 的配置大多与一个实现成对出现，配置里有一个字段指向实现：

- **`class_type` 指向类**：`ArticulationCfg.class_type = Articulation`[^art-cfg]。场景根据配置创建资产时，就是用这个字段实例化 `Articulation`（见 [4.6](4.6-assets.md)）。
- **`func` 指向函数**：所有 Manager 的配置项都继承自 `ManagerTermBaseCfg`，其中 `func` 是必填字段（`MISSING`）[^term-cfg]。例如 Cartpole 的奖励项 `pole_pos = RewTerm(func=mdp.joint_pos_target_l2, weight=-1.0, …)`，`RewTerm` 即 `RewardTermCfg`[^cartpole]。生成 Prim 的 spawner 配置也用 `func` 指向具体的生成函数。

所以读配置时，看到 `class_type` 或 `func`，就知道真正干活的代码在哪。

## 读懂一个真实配置：Cartpole

这一节回答：官方任务的配置长什么样？

Cartpole 的环境配置 `CartpoleEnvCfg` 继承自 `ManagerBasedRLEnvCfg`，示例脚本打印出它嵌套的配置类（前三层，节选）：

```text
CartpoleEnvCfg
├── sim: SimulationCfg            physx、physics_material、render
├── scene: CartpoleSceneCfg
│   ├── robot: ArticulationCfg    spawn（UsdFileCfg）、init_state
│   ├── ground / dome_light: AssetBaseCfg
├── observations: ObservationsCfg
│   └── policy: PolicyCfg         joint_pos_rel、joint_vel_rel（ObservationTermCfg）
├── actions: ActionsCfg           joint_effort（JointEffortActionCfg）
├── events: EventCfg              reset_cart_position、reset_pole_position
├── rewards: RewardsCfg           alive、terminating、pole_pos、cart_vel、pole_vel
└── terminations: TerminationsCfg time_out、cart_out_of_bounds
```

*Cartpole 环境配置的嵌套结构（本站示例实测输出整理）[^cartpole]。另有 `viewer`、`recorders` 两项从略。*

每一层都是一个 configclass，每个叶子要么是数值，要么是带 `func` 或 `class_type` 的配置项。第 4 部分后面各页就是逐层展开这棵树：场景见 [4.5](4.5-interactive-scene.md)，观测与动作见 [4.10](4.10-observation-action.md)，奖励与终止见 [4.11](4.11-reward-termination-curriculum.md)，事件见 [4.12](4.12-event-randomization.md)。

## 三种改配置的方式

这一节回答：想改出一个变体，写在哪？

| 方式 | 写法 | 适合 | 官方实例 |
|---|---|---|---|
| 继承后在 `__post_init__` 里改 | `class My(CartpoleEnvCfg): def __post_init__(self): super().__post_init__(); self.episode_length_s = 10` | 做一个长期存在的新任务变体 | Cartpole 相机版 `CartpoleRGBCameraEnvCfg` 继承 `CartpoleEnvCfg`，在 `__post_init__` 中先调用父类再修改[^cartpole-cam] |
| `.replace(...)` | `CARTPOLE_CFG.replace(prim_path="{ENV_REGEX_NS}/Robot")` | 复用一份预置配置，只改几个字段 | Cartpole、Ant、Humanoid 的场景都这样引用机器人配置[^cartpole] |
| 实例化后直接赋值 | `env_cfg.scene.num_envs = 64` | 脚本运行时按参数调整 | `train.py` 按 `--num_envs`、`--device` 修改环境配置[^train] |

*表 2：三种修改方式。*

## `MISSING`：必须由使用者填写的字段

这一节回答：`MISSING` 什么时候会报错？

字段默认值写成 `dataclasses.MISSING`，表示没有合理的默认，必须由使用者填写。实例化时并不检查；要等调用 `validate()` 才报错。Isaac Lab 在资产基类和各环境基类的构造函数里都会调用 `cfg.validate()`[^validate]，所以漏填的字段会在创建资产或环境时报出 `TypeError: Missing values detected …`，并列出字段路径。

## 命令行覆盖：Hydra

这一节回答：不改代码，怎么从命令行改配置？

训练脚本用 `@hydra_task_config(task, agent_cfg_entry_point)` 装饰 `main()`[^train]。它先按任务 ID 实例化环境配置与算法配置，用 `to_dict()` 转成字典注册给 Hydra；Hydra 合并命令行中的覆盖项后，再用 `from_dict()` 写回配置对象[^hydra]。覆盖项的写法是 `env.<路径>=值` 与 `agent.<路径>=值`。本站实测：

```bash
./isaaclab.sh -p scripts/reinforcement_learning/rsl_rl/train.py --task Isaac-Cartpole-v0 --headless \
    env.scene.num_envs=64 env.rewards.pole_pos.weight=-2.0 \
    agent.max_iterations=5 agent.num_steps_per_env=8
```

约 10 秒跑完 5 次迭代，返回码 0。训练目录中 `params/env.yaml` 与 `params/agent.yaml` 记录的值分别为 `num_envs: 64`、`pole_pos` 的 `weight: -2.0`、`max_iterations: 5`、`num_steps_per_env: 8`，原值分别是 4096、−1.0、150、16。

## 常见坑

:::{admonition} 坑一：可变默认值被多个实例共享
:class: warning

原生 `@dataclass` 不允许直接写列表、字典等可变默认值，而早期常见的绕法（在类外建一个对象再赋给多个配置）会让多个实例共享同一个对象。`@configclass` 会把可变默认值包成 `default_factory`，并在初始化后深拷贝一次[^cc]，因此在 configclass 里直接写 `[1.0, 2.0]` 是安全的。但如果漏写了装饰器，得到的就是普通类或 dataclass，没有这层保护。
:::

:::{admonition} 坑二：在类体里写逻辑
:class: warning

类体中的语句只在定义类（导入模块）时执行一次，无法访问实例的其他字段。依赖其他字段计算出的值，要写在 `__post_init__` 里，例如 Cartpole 的 `self.sim.render_interval = self.decimation`[^cartpole]。
:::

:::{admonition} 坑三：`__post_init__` 的顺序
:class: warning

- 子类的 `__post_init__` 要**先**调用 `super().__post_init__()` 再改，否则父类的设置（如 decimation、dt）会丢失，或把子类的修改覆盖回去[^cartpole-cam]。
- configclass 会把你的 `__post_init__` 与它自己的深拷贝步骤串起来，先执行你的，再执行它的[^cc]。
- 命令行覆盖发生在 `__post_init__` **之后**。在 `__post_init__` 中由其他字段算出的值不会跟着更新：本站实测，把 Cartpole 的 `decimation` 用 `from_dict` 改成 4 后，`sim.render_interval` 仍是 2。改一个字段时，要同时覆盖由它派生出来的字段。
:::
