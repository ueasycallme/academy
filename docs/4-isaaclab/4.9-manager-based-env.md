## 两层环境类与配置

这一节回答：环境类有哪两层，配置里有哪些块？

- **`ManagerBasedEnv`**：只有场景、动作、观测、事件，没有奖励与回合的概念，适合做控制、数据采集。
- **`ManagerBasedRLEnv`**：在前者之上加奖励、终止、课程、指令与回合长度，用于强化学习[^env][^rlenv]。

| 字段 | 所属 | 说明 |
|---|---|---|
| `scene` | Env | 场景配置（[4.5](4.5-interactive-scene.md)），必填 |
| `observations` | Env | 观测组与观测项（[4.10](4.10-observation-action.md)），必填 |
| `actions` | Env | 动作项（[4.10](4.10-observation-action.md)），必填 |
| `events` | Env | 启动、重置、定时触发的事件（[4.12](4.12-event-randomization.md)），默认只含一个重置场景到默认状态的事件 |
| `decimation` | Env | 一个环境步包含的物理步数，必填 |
| `sim` / `viewer` | Env | 仿真参数（[4.4](4.4-simulation-context.md)）/ GUI 相机 |
| `recorders` | Env | 数据记录（示教等），默认为空 |
| `seed` | Env | 随机种子 |
| `rewards` / `terminations` | RLEnv | 奖励项与终止项（[4.11](4.11-reward-termination-curriculum.md)），必填 |
| `curriculum` / `commands` | RLEnv | 课程项与指令项（[4.11](4.11-reward-termination-curriculum.md)、[4.13](4.13-command-manager.md)），可选 |
| `episode_length_s` | RLEnv | 回合时长（秒），必填 |
| `is_finite_horizon` | RLEnv | 超时是否视为有限视界的终止，默认 False |

*表 1：环境配置的主要字段（v2.3.2）[^env-cfg][^rlenv-cfg]。另有 `rerender_on_reset`、`xr`、`teleop_devices`、`export_io_descriptors` 等较少用的字段。*

## Manager 与 Term

这一节回答：每个 Manager 管什么，Term 又是什么？

每个 Manager 管一类事，内部由若干 **Term** 组成。Term 就是配置中的一项：一个函数（或类）加上参数，以及该 Manager 特有的字段（权重、噪声、触发模式……）[^term-cfg]。

| Manager | 管什么 | Term 配置 | Term 的形式 | 输出 |
|---|---|---|---|---|
| Action | 把策略动作换算成关节目标 | `ActionTermCfg` | 类（`class_type`） | 写入资产目标 |
| Observation | 计算观测 | `ObservationTermCfg` | 函数 `f(env, **params)` | (N, 维度)，按组拼接 |
| Event | 启动、重置、定时事件 | `EventTermCfg` | 函数 `f(env, env_ids, **params)` | 无，直接改仿真 |
| Command | 生成目标指令（速度、位姿…） | `CommandTermCfg` | 类 | (N, 维度) |
| Reward | 计算奖励 | `RewardTermCfg` | 函数 `f(env, **params)` | (N,)，乘权重与 dt 后求和 |
| Termination | 判断终止与超时 | `TerminationTermCfg` | 函数 `f(env, **params)` | (N,) 布尔 |
| Curriculum | 按训练进度调整难度 | `CurriculumTermCfg` | 函数 `f(env, env_ids, **params)` | 用于日志的状态 |
| Recorder | 记录数据 | `RecorderTermCfg` | 类 | 写文件 |

*表 2：Manager 一览（v2.3.2）[^term-cfg][^reward]。*

Term 函数集中在 `isaaclab.envs.mdp` 中，这是一个通用的 Term 函数库；任务目录下的 `mdp/` 再补充任务专用的函数（见 [4.2](4.2-repo-map.md)）。

**加一个自定义 Term**：写一个签名符合表 2 的函数，再在配置里加一项。本站示例中的奖励项[^example]：

```python
def cart_distance_from_center(env, asset_cfg: SceneEntityCfg) -> torch.Tensor:
    asset = env.scene[asset_cfg.name]
    return torch.abs(asset.data.joint_pos[:, asset_cfg.joint_ids]).sum(dim=1)   # (num_envs,)

# 在配置里：
self.rewards.cart_center = RewTerm(func=cart_distance_from_center, weight=-0.1,
    params={"asset_cfg": SceneEntityCfg("robot", joint_names=["slider_to_cart"])})
```

`asset_cfg` 在环境初始化时已由 Manager 解析，`joint_ids` 可直接用于切片（见 [4.5](4.5-interactive-scene.md)）。

## 执行顺序

这一节回答：一次 `step()` 里，各 Manager 按什么顺序被调用？

```{mermaid}
sequenceDiagram
    participant E as ManagerBasedRLEnv
    participant A as Action
    participant S as 场景 / 仿真
    participant M as 其他 Manager
    E->>A: process_action
    loop decimation 次
        E->>A: apply_action
        E->>S: 写入 → step → update
    end
    E->>M: termination.compute
    E->>M: reward.compute(dt)
    E->>S: _reset_idx（需重置的环境）
    E->>M: command.compute；interval 事件
    E->>M: observation.compute
```

*图 1：`ManagerBasedRLEnv.step()` 中各 Manager 的调用顺序，时序自上而下[^step]。“写入 → step → update”即 `scene.write_data_to_sim` → `sim.step` → `scene.update`；Recorder 的调用与渲染从略；物理步内部的细节见 [0.6](../0-map/0.6-one-step.md)。*

重置分支 `_reset_idx(env_ids)` 的顺序是：Curriculum 计算 → `scene.reset` → Event 的 `reset` 模式 → 各 Manager 依次 `reset(env_ids)`（Observation、Action、Reward、Curriculum、Command、Event、Termination、Recorder），并把它们返回的统计写入 `extras["log"]`[^reset]。所以奖励与终止是在重置**之前**按旧状态算的，观测是在重置**之后**算的，重置的环境拿到的是新回合的初始观测（与 0.6 一致）。

**构建顺序**：Event Manager 在环境构造时最先创建（启动事件要在仿真开始前执行）；随后 `load_managers()` 依次创建 Command → Recorder → Action → Observation → Termination → Reward → Curriculum[^load]。启动时终端打印的各 Manager 表，也是按 Command、Event、Recorder、Action、Observation、Termination、Reward、Curriculum 的顺序出现（本站实测）。

## 读懂 Cartpole

这一节回答：官方任务的每一项分别是什么？

| Manager | Term | 函数 / 类 | 参数 |
|---|---|---|---|
| Action | `joint_effort` | `JointEffortActionCfg` | 关节 `slider_to_cart`，scale 100 |
| Observation（`policy` 组） | `joint_pos_rel`、`joint_vel_rel` | `mdp.joint_pos_rel`、`mdp.joint_vel_rel` | 所有关节；拼接成 4 维 |
| Event（`reset`） | `reset_cart_position` | `mdp.reset_joints_by_offset` | 小车：位置 ±1.0 m，速度 ±0.5 |
| Event（`reset`） | `reset_pole_position` | 同上 | 摆杆：角度与角速度 ±0.25π |
| Reward | `alive` / `terminating` | `mdp.is_alive` / `mdp.is_terminated` | 权重 1.0 / −2.0 |
| Reward | `pole_pos` | `mdp.joint_pos_target_l2` | 摆杆，目标 0，权重 −1.0 |
| Reward | `cart_vel` / `pole_vel` | `mdp.joint_vel_l1` | 权重 −0.01 / −0.005 |
| Termination | `time_out` | `mdp.time_out` | 超时，`time_out=True` |
| Termination | `cart_out_of_bounds` | `mdp.joint_pos_out_of_manual_limit` | 小车超出 ±3.0 m |

*表 3：Cartpole（manager-based）的 Term[^cartpole]。其余：`decimation=2`，`episode_length_s=5`，`sim.dt=1/120`。*

## 动手

这一节回答：怎么跑起来、怎么改？

1. **跑官方任务**：`./isaaclab.sh -p scripts/environments/random_agent.py --task Isaac-Cartpole-v0 --num_envs 16 --headless`。启动时打印各 Manager 的 Term 表，然后一直用随机动作运行（需要手动结束）。本站实测正常。
2. **命令行覆盖**（Hydra）：在训练命令后加 `env.rewards.pole_pos.weight=-2.0`、`env.scene.num_envs=64` 等（完整示例见 [4.3](4.3-configclass.md#命令行覆盖hydra)）。注意：覆盖发生在 `__post_init__` 之后，由其他字段派生的值不会跟着变。本站实测：覆盖 `env.decimation=4` 后，`render_interval` 仍为 2，终端打印 `The render interval (2) is smaller than the decimation (4)` 警告，需要同时覆盖 `env.sim.render_interval=4`（见 [4.3 常见坑三](4.3-configclass.md#常见坑)）。
3. **继承官方配置**：本站示例 `examples/isaaclab-2.3/4.9-manager-based-env/custom_cartpole.py` 继承 `CartpoleEnvCfg`，在 `__post_init__` 中先调用父类，再把 `pole_pos` 权重改为 −2.0，并加上上文的 `cart_center` 奖励；用随机动作运行 100 步。本站实测（16 个环境，约 8 秒，返回码 0）：Reward Manager 的表中出现 6 个 Term，`cart_center` 的权重为 −0.1。

## 调试入口

这一节回答：想看某一项的数值，从哪里看？

- **启动时的 Term 表**：每个 Manager 打印一张表，列出 Term 名称、权重、形状等，先确认配置是否如预期（本站示例的 Reward 表即如此）。
- **`env.unwrapped`**：通过 `gym.make` 创建的环境外面包着 Gym 包装器，用 `env.unwrapped` 取到 `ManagerBasedRLEnv` 本体，再访问各 Manager。
- **各 Manager 的接口**：`active_terms` 列出 Term 名；`get_active_iterable_terms(env_idx)` 给出某个环境本步的各项数值；`observation_manager.group_obs_dim` 给出各观测组的维度；`action_manager.total_action_dim` 给出动作维度[^mgr]。注意奖励的逐项值是 func × weight，没有乘 dt，计入总奖励时才乘 dt[^reward]。
- **`extras["log"]`**：重置时各 Manager 返回的统计（如各奖励项的回合累计），训练日志中的 `Episode_Reward/…` 就来自这里。

## 常见坑

:::{admonition} 坑一：子类的 `__post_init__` 没先调用父类
:class: warning

父类在 `__post_init__` 里设了 decimation、dt 等；子类不先调用 `super().__post_init__()`，这些设置就会缺失或被覆盖（见 [4.3 常见坑三](4.3-configclass.md#常见坑)）。
:::

:::{admonition} 坑二：命令行改了 decimation，渲染间隔没跟着变
:class: warning

`render_interval` 通常在 `__post_init__` 中由 decimation 算出，覆盖不会重新计算（本站实测会打印警告，见"动手"第 2 条）。
:::

:::{admonition} 坑三：自定义 Term 的输出形状不对
:class: warning

奖励与终止 Term 必须返回形状为 (num_envs,) 的张量，观测 Term 返回 (num_envs, 维度)[^term-cfg]。多返回一维（如 (N, 1)）会在求和或拼接时出错或被意外广播。
:::

:::{admonition} 坑四：以为奖励权重就是每步奖励的大小
:class: warning

每一步的奖励是 func × weight × dt，与步长有关[^reward]。改动 `decimation` 或 `sim.dt` 会同时改变奖励的尺度。
:::
