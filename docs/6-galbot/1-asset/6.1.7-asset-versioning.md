**本页在项目中新增**：`scripts/asset_manifest.py`（写 / 校验清单，不需要 Isaac Sim）；`assets/conversion.py`（转换参数从 `convert_galbot.py` 移来）、`assets/manifest.py`。`convert_galbot.py` 转换完会写清单；`assets/galbot.py` 被导入时（也就是建环境时）校验清单，不一致只警告。转换结果不变：本站重新转换后，25 个输出文件的 sha256 与改动前完全相同。

本项目从 6.1.1 起就在用一套资产策略：描述仓库固定 commit，生成的 USD 不提交，修改全部写在转换脚本里。本页把它讲成可复用的规则，并补上缺的一环：清单。

## 三种做法

| 做法 | 仓库里放什么 | 适合 | 代价 |
|---|---|---|---|
| Git LFS | 指针文件；内容在 LFS 服务器上[^lfs] | 资产手工编辑过、无法由脚本重新生成；团队小，文件量不大 | 托管平台有配额：GitHub 免费账户存储与带宽各 10 GiB，超了要付费；预算设为 $0 时，当月不能再用 LFS[^gh-lfs] |
| DVC 等外部存储 | `.dvc` 元数据文件（含 MD5）；数据推到 S3、SSH 等远端[^dvc] | 数据量大、要多版本并存，团队已有对象存储；也能把"生成"写成流水线 | 多一套工具和一份远端存储要维护 |
| 只提交来源 + 转换脚本（本项目） | 上游仓库地址与 commit、转换脚本与参数 | 资产能由脚本完整生成；CI 要从零构建；不能或不便分发上游文件 | 每台机器都要转换一次（本项目约 20 s，含启动 Isaac Sim）；转换器升级可能改变输出 |

*表 1：三种做法的对照。"适合"一列是本站的经验判断。*

本项目选第三种，理由有三条：Galbot 资产全部能从 URDF 生成；生成的 USD 有 12 MB，还会随参数反复变化；上游仓库有自己的许可，不宜把派生文件混进本站仓库（T-6-common）。Omniverse 的 Nucleus 是另一条路，见 [2.8](../../2-usd-kit/2.8-nucleus.md)。

## 清单：这份 USD 是怎么来的

第三种做法有个缺口：手里的 `generated/galbot_fixed_base/` 是哪天、用哪组参数生成的，目录里看不出来。Isaac Lab 的转换器自己会写一个 `.asset_hash`，但它只哈希转换器配置（去掉路径）和 URDF 文件本身[^asset-hash]。URDF 引用的网格、转换后脚本对 USD 的修改、Isaac Sim 的版本，都不在里面。

所以本项目加了一份清单 `MANIFEST.json`，由 `convert_galbot.py` 在转换末尾写出：

| 字段 | 内容 |
|---|---|
| `source` | 描述仓库地址、实际检出的 commit、固定的 commit、工作区是否有改动 |
| `toolchain` | Python、`isaacsim`、`isaaclab` 的包版本（Isaac Lab 2.3.2 的 pip 包版本号是 0.54.2） |
| `params` | `assets/conversion.py` 里的全部参数：转换器选项、驱动增益、mimic 约束 1000 / 1.0、7 对自碰撞过滤对、是否固定根 |
| `files` | 输出目录下每个文件的 sha256 与大小（`config.yaml` 除外：转换器每次都写入生成时间与绝对路径） |

*表 2：清单的字段。*

```bash
python scripts/asset_manifest.py verify     # 一致时退出码 0
python scripts/asset_manifest.py write      # 给已有的生成目录补写清单
```

校验时，"现在的"来源、工具链、代码里的参数和文件逐项与清单比。本站实测三种情况：

```text
[manifest] 一致：来源、工具链、参数、文件都与清单相同
# 把 conversion.py 里的 MIMIC_NATURAL_FREQUENCY 改成 500，不重新转换：
  参数 post_processing.mimic_natural_frequency：1000.0 → 500.0
# 在 configuration/galbot_sensor.usd 末尾加一个字节：
  文件 configuration/galbot_sensor.usd：sha256 09ee9dd03354 → 18eb9ec48e5f，大小 655 → 656
```

建环境时同样的差异以 `UserWarning: [资产清单] …` 打印出来，训练照常进行。

**为什么 sha256 要和参数一起看**：两者回答的问题不同。sha256 只说明"文件变没变"。本站把同一组参数连转两次，又与前一天的产物比，25 个文件逐字节相同，转换是确定的。所以 sha256 一致加上参数一致，才能说明"这份 USD 就是当前代码会生成的那份"。只有 sha256 时，改了参数却忘了重新转换，文件没变，校验照样通过；只有参数时，有人在 GUI 里改了 USD 并保存，参数没变，也发现不了。

## 手工修改放在哪一层

转换后的修改落在哪里，本站读了生成的 `galbot.usd`：它是入口文件，通过三个变体集（Physics、Sensor、Robot）组织 `configuration/` 下转换器生成的各层。脚本的修改以 `over` 写在入口文件的根层里，落在 17 个 prim 上：10 个 mimic 关节的两个属性、7 个连杆上的过滤对（连同外层的 `joints` 与根，根层共 19 个 prim spec）。根层意见最强（2.3"强度顺序"），所以压得住转换器写的默认值。

两种放法：

- **本项目的做法：脚本里改，重新转换时再改一遍。** 所有修改都在代码里，评审看的是 Python diff，清单记录参数，转换可复现。缺点是，在 GUI 里手调的东西必须翻译成脚本才能留下。`force_usd_conversion=True` 时入口文件会整个重写，手工保存进去的修改会丢。
- **单独一层：手工修改存成自己的 `.usda`，由一个包装文件把它叠在生成的 USD 之上。** 环境指向包装文件，重新生成只覆盖下层，手工层不动。适合美术或调参人员在 GUI 里改、改的东西难以写成脚本的场合。代价是：底层 prim 改名或删除后，手工层里的 `over` 会悄悄失效，不报错（与 2.3 坑三"变体选项名写错，不报错"是同一类问题）。

本项目没有手工修改，所以用第一种；以后若要接 GUI 调参，再加第二种，并把手工层（文本格式）提交进仓库。

## 常见坑

### 坑一：二进制 USD 的 diff 看不出改了什么

生成的 `galbot.usd` 与 `configuration/*.usd` 都是二进制格式（文件头 `PXR-USDC`），git 只会说"Binary files differ"。要看内容，用 `usdcat` 或 `Sdf.Layer.ExportToString()` 转成文本再比。这也是本项目把修改留在脚本里的原因之一：评审看脚本的 diff 就够了。

### 坑二：转换器升级，输出变了，commit 没变

描述仓库的 commit 只固定了输入。Isaac Sim 或 Isaac Lab 升级后，同样的 URDF 与参数可能转出不同的 USD，`.asset_hash` 也不会变（它不含版本号）。清单的 `toolchain` 一栏就是为此记的：版本变了，`verify` 会报出来，这时重新转换并比对行为（6.1.2 的检查脚本）。

### 坑三：LFS 的配额与克隆

LFS 文件每次被下载都计入带宽。GitHub 免费账户超过 10 GiB 配额、且预算设为 $0 时，当月不能再用 LFS；没有付款方式时，克隆只拿到指针文件[^gh-lfs]。CI 每次从零克隆，最容易先把带宽用完。

### 坑四：绝对路径

转换器写的 `config.yaml` 里有 URDF 与输出目录的绝对路径（本机路径），所以清单不哈希它。USD 本身用的是相对路径：本站在生成的 5 个 `.usd` 文件里查过，没有本机路径，整个目录可以挪动。自己写脚本往 USD 里加引用时，也要用相对路径，否则换一台机器就找不到文件。
