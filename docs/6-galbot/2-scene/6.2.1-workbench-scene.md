# 搭建工作台场景

:::{admonition} 学习目标
:class: lead-goals

- 为 reach 写出场景配置 `GalbotReachSceneCfg`，并行出 N 个环境
- 确定末端坐标系（TCP），估算手臂的可达范围，为任务的目标采样提供依据
- 根据机器人的占地选 `env_spacing`，知道环境之间的碰撞是怎么隔开的
- 测出场景规模与吞吐、显存的关系
:::

## 场景配置

这一节回答：场景里放什么，各放在哪条路径下？

```python
@configclass
class GalbotReachSceneCfg(InteractiveSceneCfg):
    ground = AssetBaseCfg(prim_path="/World/ground", spawn=sim_utils.GroundPlaneCfg())
    light = AssetBaseCfg(prim_path="/World/light", spawn=sim_utils.DomeLightCfg(intensity=2000.0, color=(0.9, 0.9, 0.9)))
    robot: ArticulationCfg = GALBOT_ONE_GOLF_CFG.replace(prim_path="{ENV_REGEX_NS}/Robot")
```

地面和灯光所有环境共用，写绝对路径；机器人每个环境一份，写在 `{ENV_REGEX_NS}` 下（[4.5](../../4-isaaclab/4.5-interactive-scene.md)）。`num_envs` 与 `env_spacing` 不写死，由任务配置给出。机器人根固定在 z = 0 处，与地面同高：固定底座版的底盘碰撞体同样低于地面，实测稳定（原因的推断见 [6.1.2](../1-asset/6.1.2-import-urdf.md)）。

## 要不要桌子

这一节回答：reach 需要桌面吗？

reach 只要求末端到达空中的目标点，不和任何物体接触，所以 `GalbotReachSceneCfg` 不放桌子。项目另给了一个带桌面的子类 `GalbotReachTableSceneCfg`：一块 0.6 m × 1.0 m 的静态长方体，上表面高 0.95 m，放在机器人右前方。它的用处有两个：一是给画面一个参照；二是为 lift（[6.4.3](../4-task/6.4.3-lift.md)）留扩展点，物体放在桌上，场景从这个子类继承即可。

桌面带碰撞体，手臂碰到会被挡住。这对 reach 是额外约束：目标若靠近桌面，策略还要学会绕开它。下文建议的目标范围最低点在 1.10 m，离桌面 15 cm。实测加桌面后，默认姿态的保持误差与不加时相同（0.0527 rad），说明桌面没有和机器人发生初始穿透。

## 末端坐标系

这一节回答：任务里"末端到哪了"用哪个坐标系？

Galbot 描述仓库为夹爪定义了标准化的工具中心点（TCP）`right_gripper_tcp_link`：在夹爪底座前方 0.13996 m，绕 x 转 −π/2；仓库 README 说明这个变换在 xacro、URDF、MJCF、USD 中一致[^tcp]。但 6.1.2 转换时合并了固定关节，这个连杆并进了 `right_arm_link7`，USD 里已经没有它。

所以本项目用"刚体 + 固定偏移"表示 TCP：刚体 `right_arm_link7`，偏移位置 (−0.25572, 0, 0) m，姿态为绕 y 转 180°，即四元数 (w, x, y, z) = (0, 0, 1, 0)。这个偏移由 URDF 中 `right_arm_link7` 到 TCP 的四个固定关节依次相乘得到，与厂商 USD 里两个 Prim 的相对位姿逐位一致（本站用 usd-core 核对）。默认姿态下，TCP 在根前方 0.67 m、高 1.46 m（只算运动学）；在重力下保持 2 s 后下垂到约 1.41 m。

任务里怎么用这个偏移，留给 [6.4.1](../4-task/6.4.1-reach.md)：可以在奖励、观测函数里用 `combine_frame_transforms` 把偏移加到刚体位姿上，也可以用 `FrameTransformer` 直接给出 TCP 位姿（[6.2.2](6.2.2-wrist-camera.md)）。

## 可达范围

这一节回答：目标该在哪个范围里采样？

```bash
python scripts/workspace.py --headless --batches 64 --voxel 0.1 --min_count 10
```

脚本放 1024 台机器人，其余关节保持默认姿态，右臂 7 个关节在限位内均匀采样 64 批，共 65536 组，按运动学算 TCP 位置（相对机器人根）：

| 轴 | 5% 分位 | 中位数 | 95% 分位 | 范围 |
|---|---|---|---|---|
| x（前） | −0.635 | +0.011 | +0.657 | −0.947 … +0.970 |
| y（左） | −1.035 | −0.565 | +0.084 | −1.173 … +0.409 |
| z（上） | +0.680 | +1.338 | +1.990 | +0.385 … +2.290 |

*表 1：右臂 TCP 位置的分布（m，本站实测，种子 0；约 11 秒，按进程显存 2785 MiB）。*

再把空间划成 10 cm 的体素，找一个在机器人前方、每个体素都至少有 10 个样本的长方体。结果是 **x ∈ [0.25, 0.85]，y ∈ [−0.65, −0.15]，z ∈ [1.10, 1.50] m（相对根）**，作为 6.4.1 目标位置采样范围的建议。这个判据只看位置能否到达，没有考虑末端姿态，也没有考虑自碰撞（脚本关掉了自碰撞）；6.4.1 若同时约束姿态，范围要相应缩小。

## env_spacing 与环境之间的碰撞

这一节回答：环境之间隔多远？

同一次采样里，所有刚体离机器人根的最大水平距离是 1.14 m，TCP 是 1.17 m。两台相邻机器人的手臂同时朝对方伸出，最坏要 2 × 1.17 ≈ 2.35 m 才不重叠，所以取 **`env_spacing = 2.5`**。

Isaac Lab 默认让各环境互不碰撞（`filter_collisions=True`[^filter]）；在 CPU 上碰撞过滤总会开启，关不掉（[4.5](../../4-isaaclab/4.5-interactive-scene.md) 的实测）。所以间距小了，机器人也不会互相碰到，只是画面上重叠、难以分辨。间距不影响仿真结果，2.5 m 是"看得清"的取值，取再大也只是让场景更散。

## 目标标记

这一节回答：怎么在画面里看到目标？

`scene_bench.py` 用 `VisualizationMarkers` 在每个环境的 TCP 处和它前方 0.1 m 处各画一个坐标轴：

```python
frame_cfg = FRAME_MARKER_CFG.replace(prim_path="/Visuals/ee_and_goal")
markers = VisualizationMarkers(frame_cfg)
markers.visualize(positions, orientations)   # 每帧调用，传入世界系位姿
```

标记建在 `/Visuals` 下，不在 `/World/envs` 里，也没有碰撞与刚体属性，不参与物理。6.4.1 用命令项（command term）生成目标时，打开它自带的 `debug_vis` 即可看到同样的标记，不需要自己写。

## 规模、吞吐与显存

这一节回答：环境数变多时，开销怎么变？

```bash
python scripts/scene_bench.py --headless --num_envs 16
python scripts/scene_bench.py --headless --num_envs 256
python scripts/scene_bench.py --headless --num_envs 1024
```

| 环境数 | /World/envs 下的 Prim | 构建 + reset | 每秒物理步 | 每秒环境步 | 按进程显存 |
|---|---|---|---|---|---|
| 16 | 16 | 1.6–1.7 s | 104–105 | 约 1 670 | 2315 MiB |
| 256 | 256 | 2.5–3.0 s | 90 | 约 23 000 | 2455 MiB |
| 1024 | 1024 | 5.6–5.8 s | 74 | 约 76 000 | 2987 MiB |

*表 2：场景规模与开销（本站实测，RTX 5070，dt = 1/120 s，不渲染，机器人保持默认姿态；求解器迭代为项目配置的 16 / 1，见 [6.1.6](../1-asset/6.1.6-articulation-cfg.md)；每档 3 次，每秒物理步在 3 次间相差约 1%，校验方在另一时间复测的结果相差约 2%；每次运行总长 19–30 秒）。每秒环境步 = 每秒物理步 × 环境数，是物理步，不是 RL step。*

- **环境步随环境数近似线性增长**：环境数从 16 增加到 1024（64 倍），每秒环境步增加约 45 倍；每个物理步的耗时从 9.6 ms 只增加到 13.4 ms，可见大部分开销是与环境数无关的固定成本。
- **显存增长很慢**：1024 个环境只比 16 个多约 670 MiB，大部分显存是 Isaac Sim 启动本身占用的（与 [5.4](../../5-rl/5.4-parallel-envs.md) 的观察一致）。主线机器的 12 GB 远未用满。
- **求解器迭代次数影响很大**：沿用资产里的 32 / 1 时，同样的三档只有 60 / 52 / 44 物理步每秒（本站与校验方各测 3 次）。项目配置改为 16 / 1 的依据见 6.1.6 表 2。

## 常见坑

:::{admonition} 坑一：把末端当成 right_arm_link7 的原点
:class: warning

合并固定关节后，`right_arm_link7` 的原点在腕部，离 TCP 有 0.256 m。直接用它当末端，目标采样范围、奖励里的距离都会差出 25 cm。要加上本页给出的偏移。
:::

:::{admonition} 坑二：全局物体写进了 {ENV_REGEX_NS}
:class: warning

地面、灯光写成 `{ENV_REGEX_NS}/Ground`，会被克隆 N 份，白白增加 Prim 与碰撞体（[4.5](../../4-isaaclab/4.5-interactive-scene.md)）。桌面则相反，每个环境要一份，写在 `{ENV_REGEX_NS}` 下。
:::

:::{admonition} 坑三：用最远可达距离定目标范围
:class: warning

表 1 的"范围"一列是极值，只有少数关节组合能到。目标若在那里采样，很多回合根本完成不了。按样本密度选一个保守的长方体，再在 6.4.1 的训练中看成功率是否正常。
:::

:::{admonition} 坑四：场景的 keys 里多出一个 terrain
:class: warning

`scene.keys()` 中会出现 `terrain`，即使场景里没有地形。`InteractiveScene.keys()` 总是先放入 `terrain`[^keys]，不是配置写错。
:::
