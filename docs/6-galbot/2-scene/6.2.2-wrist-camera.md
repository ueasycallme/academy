# 挂载腕部相机与传感器

:::{admonition} 学习目标
:class: lead-goals

- 把 Galbot 的右腕相机、TCP→方块的 FrameTransformer、指尖接触传感器装进 lift 场景，读出数据
- 用可复现的方法核对三处坐标系：相机朝向、FrameTransformer 的源与目标、接触传感器的刚体
- 知道每种传感器对耗时、显存、主机内存的代价，以及主线训练为什么不开相机
:::

## URDF 里已有什么

这一节回答：相机装在哪，转换成 USD 后还在不在？

描述仓库在 `right_arm_link7` 下挂了相机支架和 RealSense D405 的模型，两个固定关节[^urdf-cam]：

```xml
<joint name="right_arm_camera_stand_joint" type="fixed">   <!-- 无 origin：与 link7 重合 -->
<joint name="right_arm_camera_joint" type="fixed">
  <origin rpy="0 1.4807963267948965 3.141592653589793" xyz="-0.0822 0 -0.06842"/>
```

URDF 没有给相机内参，也没有单独的光学坐标系（optical frame）link。

[6.1.2](../1-asset/6.1.2-import-urdf.md) 转换时合并了固定关节（`merge_fixed_joints=True`），相机 link 的质量并进了 `right_arm_link7` 刚体。但本站用 usd-core 检查生成的 USD，同名 Xform 仍在：`right_arm_link7/right_arm_wrist_camera_stand/right_wrist_camera_link`，相对 link7 的位置是 (−0.0822, 0, −0.06842) m，与 URDF 一致。TCP 的 `right_gripper_tcp_link` 也是这样留下来的。

所以有两种挂法，本站都实测过，位姿差 < 0.001 mm：

- **挂在留下的 Xform 下**，偏移为零（项目采用，少抄一组数字）；
- **挂在 `right_arm_link7` 下**，偏移照抄上面的固定关节。

FrameTransformer 不能这样用：它只接受刚体，遇到 Xform 直接抛 `ValueError`[^ft-rigid]。所以 TCP 仍是"link7 + 固定偏移"（[6.2.1](6.2.1-workbench-scene.md#末端坐标系)）。

## 腕部相机

这一节回答：相机怎么配，朝向对不对？

```python
TiledCameraCfg(
    prim_path="{ENV_REGEX_NS}/Robot/right_arm_link7/right_arm_wrist_camera_stand/right_wrist_camera_link/wrist_cam",
    offset=TiledCameraCfg.OffsetCfg(convention="ros"),       # 与相机 link 重合
    data_types=["rgb", "depth"],
    spawn=sim_utils.PinholeCameraCfg(focal_length=24.0, horizontal_aperture=2 * 24.0 * math.tan(math.radians(87 / 2)),
                                     clipping_range=(0.01, 5.0)),
    width=64, height=64, update_period=0.0,
)
```

**朝向**：`convention="ros"` 表示把 `offset` 解释为 ROS 光学约定，+Z 朝前、−Y 朝上[^cam-conv]。选它的依据：D405 外壳碰撞网格在这个 link 里的范围是 z ∈ [−0.023, 0] m，即正面在 z = 0、机身朝 −Z 方向伸；而 +Z 指向夹爪前方。所以 +Z 是光轴（推断）。URDF 没有说明图像的上方对应哪个轴，本页按光学约定取 −Y。

**视场角**（field of view）：URDF 没有内参（intrinsics），本页取 RealSense 产品页的深度视场 87° × 58°（水平 × 垂直）中的水平值[^d405]。图像是正方形，垂直视场也就成了 87°，与真机不同；近裁剪面取 1 cm，比产品页的最佳工作距离下限 7 cm 更近，好让贴近夹爪的物体也能画出来。128×128 时，实测内参为 fx = fy = 67.44、cx = cy = 64（像素）。

**验证**（`check_sensors.py`，本站实测）：

1. 相机位姿与"link7 位姿 + URDF 固定关节"组合的结果相同，4 个环境的最大偏差为 0.000 mm；
2. 把方块钉在相机坐标系的已知点（右 5 cm、下 5 cm、前 30 cm），按内参投影到像素 (74.7, 73.7)；图中红色像素的重心是 (74.7, 73.0)，相差不到 1 像素。投影对得上，说明朝向和约定都没有写反；如果左右或上下写反了，重心会落到图像中心的另一侧。

:alt: 默认姿态下的腕部相机画面：左侧是夹爪，右下有一个红色方块，上方是地面网格；右边是同一帧的深度图
:width: 100%

图 1：默认姿态下的腕部相机（128×128，左 RGB，右深度，近黑远白；`scripts/plot_wrist_camera.py` 画出）。地面出现在图像上方：此时相机的"图像上方"指向世界 −z（`check_sensors.py` 打印为 (−0.26, 0.06, −0.96)），这是手腕姿态造成的，不是坐标系写反。

## FrameTransformer

这一节回答：TCP 与方块的相对位姿怎么拿，偏移对不对？

lift 场景已有 `ee_frame`：源是机器人根，目标是 TCP。本页再加一个 `tcp_to_cube`：源是 TCP（`source_frame_offset` 用同一组偏移），目标是方块，读 `target_pos_source` 就得到方块在 TCP 坐标系下的位置。

实测（默认姿态，重力下保持 1 s）：

- `ee_frame` 的 TCP 在根坐标系下为 (0.684, −0.071, 1.409) m，与 [6.2.1](6.2.1-workbench-scene.md#末端坐标系) 的"TCP 在根前方 0.67 m……在重力下保持 2 s 后下垂到约 1.41 m"一致；
- `tcp_to_cube` 读出的方块位置，与用两者的世界位姿手算的结果到毫米级相同，源原点与 `ee_frame` 的 TCP 相差 0.000 mm。

## ContactSensor

这一节回答：怎么知道指尖夹住了方块？

两处改动：

1. 机器人 spawn 的 `activate_contact_sensors` 改为 True。`galbot.py` 默认是 False（[6.1.6](../1-asset/6.1.6-articulation-cfg.md) 表 1），不开时建传感器会报错（[4.8](../../4-isaaclab/4.8-sensors.md)）。`make_sensor_scene_cfg(contact=True)` 用 `.replace()` 只改这一项。
2. 左右指尖各配一个传感器，`filter_prim_paths_expr` 指向方块。不能用一个正则同时匹配两个指尖，原因见坑一。

脚本化抓取复用 `check_grasp.py` 的做法：把方块钉在 TCP 处，闭合夹爪，再松开方块只靠夹持，最后张开。每个阶段末，两个指尖与方块的接触力如下（4 个环境平均）：

| 阶段 | 夹爪角 | 左指尖 | 右指尖 |
|---|---|---|---|
| 张开、钉住方块 1 s | 0.60 rad | 0.00 N | 0.00 N |
| 闭合、钉住方块 2 s | 1.61 rad | 8.88 N | 3.74 N |
| 松开方块、只靠夹持 1.5 s | 1.69 rad | 11.55 N | 9.34 N |
| 张开 2.5 s | 0.60 rad | 0.62 N | 0.00 N |

*表 1：指尖与方块的接触力（本站实测）。*

张开后左指尖仍有 0.62 N，并不是读数有误：这个姿态下夹爪侧着，左指尖在下方（高 1.358 m，右指尖 1.461 m），方块张开后落在它上面没掉下去。读数小于方块重力 0.98 N，其余的重量应是压在没装传感器的指节上（推断）。

## 代价

这一节回答：每种传感器要付出多少？

按 lift 环境的节奏计时：4 个物理步加 1 次渲染算一个环境步（只有带相机时才渲染），每步读一次传感器数据（数据是惰性计算的，不读就不算，[4.8](../../4-isaaclab/4.8-sensors.md)）。每次只加一种传感器：

```bash
python scripts/check_sensors.py --headless --bench contact --num_envs 1024
python scripts/check_sensors.py --headless --enable_cameras --bench cam64 --num_envs 1024
```

| 传感器 | 64 个环境 | 256 个环境 | 1024 个环境 |
|---|---|---|---|
| 无 | 44.3 ms · 2301 MiB · 3.2 GB | 45.5 ms · 2441 MiB · 3.6 GB | 56.7 ms · 3037 MiB · 5.0 GB |
| FrameTransformer（`ee_frame`） | 44.8 ms · 2301 MiB · 3.3 GB | 46.5 ms · 2441 MiB · 3.7 GB | 57.3 ms · 3037 MiB · 5.1 GB |
| ContactSensor（两个指尖） | 44.7 ms · 2365 MiB · 3.3 GB | 46.2 ms · 2505 MiB · 3.6 GB | 57.1 ms · 3103 MiB · 5.0 GB |
| 无，但带 `--enable_cameras` | 44.7 ms · 3291 MiB · 6.0 GB | 46.4 ms · 3433 MiB · 6.3 GB | 57.7 ms · 4131 MiB · 7.6 GB |
| TiledCamera 64×64 | 55.7 ms · 4862 MiB · 6.8 GB | 64.5 ms · 5038 MiB · 7.1 GB | 107.2 ms · 6937 MiB · 8.6 GB |
| TiledCamera 128×128 | 57.3 ms · 4965 MiB · 6.8 GB | 74.5 ms · 5986 MiB · 7.2 GB | 147.5 ms · 10329 MiB · 8.6 GB |

*表 2：每个环境步的耗时 · 按进程显存峰值 · 主机 RSS 峰值（本站实测，RTX 5070 12 GB，2026-10-09；每格 3 次，耗时取平均，3 次之间相差 ≤ 1.6%；显存、RSS 取 3 次中的最大值；相机为 rgb + depth）。*

从表 2 读出三点：

- **FrameTransformer、ContactSensor 几乎免费**：每步多 0.4–1.0 ms，显存多 64–66 MiB。开 `activate_contact_sensors` 也没有看得出的代价。
- **相机的代价分两块**：只带 `--enable_cameras` 加载渲染，就多出约 1 GB 显存、2.6–2.8 GB 主机内存，耗时不变；真正建了相机，每步再加渲染时间，并随环境数和分辨率增长。1024 个环境时，64×64 让每步从 57 ms 变成 107 ms（约 1.9 倍），128×128 变成 147 ms（约 2.6 倍），显存到 10.3 GB，离 12 GB 只剩不到 2 GB。
- **1024 个环境能跑**，两种分辨率都没有出错；但 6.4.3 训练用的是 2048 个环境，按这个趋势 128×128 放不下（推断）。

**主线 reach / lift 训练不开相机**，理由有三：

1. 策略用的是仿真里能直接读到的状态（关节角、方块位姿），不需要从图像里估计；
2. 1024 个环境时，开 64×64 相机每步慢近一倍，显存多出 3.9 GB；
3. 图像观测还要换成卷积网络，超参数也要重新调，超出这两个任务要讲的范围。

相机留给以后的视觉策略；接触力可以随时加进观测或奖励，代价可以忽略。

## 坐标系自查清单

- **相机朝向**：把一个显眼的物体放在相机坐标系的已知点（偏右、偏下），看它是否出现在图像的右下；只看"画面像不像"不可靠，因为默认姿态下画面本来就是倒的（图 1）。
- **FrameTransformer 的源与目标**：用两者的世界位姿手算一遍 `subtract_frame_transforms(源, 目标)`，与 `target_pos_source` 对照；写反时符号与坐标轴都会变。
- **接触传感器的刚体**：打印 `sensor.body_names`，确认是指尖而不是指节；再做一次"张开为零、夹住非零"的对照。

## 常见坑

:::{admonition} 坑一：一个带过滤的接触传感器匹配了两个指尖
:class: warning

`prim_path` 写成 `right_gripper_.*_finger_link` 时不报错，`body_names` 也是两个指尖，但夹住方块时 `force_matrix_w` 全为 0，`net_forces_w` 却正常（本站实测）。源码注释写明过滤只在每个环境匹配一个刚体时有效[^filter]。左右各配一个。
:::

:::{admonition} 坑二：相机的 pos_w 停在初始位置
:class: warning

`update_latest_camera_pose` 默认为 False，`pos_w`、`quat_w_*` 只在相机创建时读一次[^cam-pose]。本站第一次运行时，读到的位置与实际差了 1.17 m（那是 USD 零位时的位置）。图像本身是随手臂走的；要用相机位姿做计算时，把它设为 True。
:::

:::{admonition} 坑三：把 cam.data 存进变量后再读
:class: warning

传感器数据只在访问 `.data` 属性时才刷新（[4.8](../../4-isaaclab/4.8-sensors.md)）。`cd = cam.data` 之后又推进了几步，再读 `cd.output["rgb"]`，拿到的是旧画面：本站的投影检查因此第一次没找到方块。每次要用时重新访问 `cam.data`。
:::

:::{admonition} 坑四：忘了 --enable_cameras
:class: warning

带相机的场景必须加 `--enable_cameras`，否则建相机时抛 `RuntimeError`（[4.8](../../4-isaaclab/4.8-sensors.md)）。
:::
