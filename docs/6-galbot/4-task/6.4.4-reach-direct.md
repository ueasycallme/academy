**本页在项目中新增**：`tasks/direct/reach/`（`reach_env.py`、`reach_env_cfg.py`、`agents/`，注册 `Galbot-Reach-Direct-v0`）、`scripts/compare_direct_manager.py`。`eval_reach.py` 与 `profile_env.py` 加了对 Direct 版的支持，原有输出不变。

4.14 已经讲过两种写法的概念，本页只做对照。目标定得严格：Direct 版与 Manager 版逐步一致，不只是"大致相同"。

## 对照表

| 管理器 | Manager 版（写在哪） | 行数 | Direct 版（写在哪） | 行数 |
|---|---|---|---|---|
| 动作 ActionManager | `ActionsCfg` | 3 | `_pre_physics_step` + `_apply_action` | 6 |
| 观测 ObservationManager | `ObservationsCfg` | 12 | `_get_observations` | 15 |
| 命令 CommandManager | `CommandsCfg` + `TcpPoseCommand(Cfg)` | 40 | `_update_command` + `_resample_command` + `_command_w` | 23 |
| 奖励 RewardManager | `RewardsCfg` + `mdp/rewards.py` | 32 | `_get_rewards` + 项名表 | 27 |
| 终止 TerminationManager | `TerminationsCfg` | 3 | `_get_dones` | 3 |
| 事件 EventManager | `EventCfg` | 8 | `_reset_robot` | 20 |
| 课程 CurriculumManager | `CurriculumCfg` | 4 | 写在 `_reset_idx` 里 | — |
| 重置流程 | 基类完成 | 0 | `_reset_idx` | 16 |
| 总配置与初始化 | `GalbotReachEnvCfg` | 18 | `GalbotReachDirectEnvCfg` + `__init__` | 52 |
| 文件合计（含 import） | 3 个文件 | 154 | 2 个文件 | 186 |

*表 1：代码行数（不含空行、注释与 docstring，数法同 4.14 表 3），由 `compare_direct_manager.py lines` 统计。两版共用 `mdp/tcp.py`（TCP 位姿），不计入。*

行数差得不多，差别在"逻辑在谁那里"：

- **命令**：Manager 版继承 `UniformPoseCommand`，只改误差指标，采样逻辑在库里；Direct 版把采样、计时、误差都写出来，反而更短。
- **事件**：Manager 版两行配置调用库函数 `reset_scene_to_default`、`reset_joints_by_offset`；Direct 版把两个函数体抄进 `_reset_robot`，20 行。
- **初始化**：Direct 版要自己建缓冲（动作、命令、奖励权重、分项累计），还要自己写 `extras["log"]`，rsl_rl 的分项奖励曲线才有数据（4.14 表 4"调试"一行）。

## 语义等价的验证

一个进程里只能建一个 Isaac Lab 环境，所以分两次录、再离线比：

```bash
python scripts/compare_direct_manager.py record --headless --task Galbot-Reach-v0 --out m.npz
python scripts/compare_direct_manager.py record --headless --task Galbot-Reach-Direct-v0 --out d.npz
python scripts/compare_direct_manager.py diff m.npz d.npz
```

`record` 用同一种子 reset，喂同一串动作（numpy 种子固定，正态分布、标准差 0.5，与策略输出量级相近），64 个环境 × 400 步。400 步覆盖两次命令重采样（第 121、242 步；4 s 按 30 Hz 是 120 步；float32 下从 4.0 连减 120 次 1/30 还剩 2.47e-6，要到第 121 次才 ≤ 0）和一次超时重置（第 360 步）。阈值取 1e-5。

```text
[compare] 观测·关节位置：初始 0，全程最大 0；全程 ≤ 1e-05
...
[compare] 奖励：全程最大 0（奖励量级 0.00324）；全程 ≤ 1e-05
[compare] 超时：一致，发生在第 [360] 步
```

结果是**逐位相同**：四块观测、奖励、超时步全程差为 0。Manager 版自己录两次也是 0，说明这个场景在本机 GPU 上可复现。

要做到逐位相同，Direct 版照 Manager 版的流程排了三件事：

1. **随机数的消耗顺序**：重置时先采右臂关节扰动（事件），再采命令的重采样时间与目标位置（命令）。姿态范围上下限相同，Manager 版仍对 roll、pitch、yaw 各采一次，Direct 版照采。
2. **命令更新的位置**：Manager 版在"重置之后、算观测之前"调用 `command_manager.compute`[^step]。Direct 的 `step()` 在这个位置没有钩子，所以放在 `_get_observations` 开头。`reset()` 也会调用 `_get_observations`，用全局步数判断，只在 `step()` 里更新。
3. **奖励的求和**：按 `RewardsCfg` 的项序累加，每项乘控制周期 `step_dt`（4.14 坑二）。超时判断用 `>= max_episode_length`，与 `mdp.time_out` 相同。

`--perturb` 把其中一件故意做错，看差异从哪里冒出来（见常见坑）。

## 训练对照

同一 PPO 配置（`agents/rsl_rl_ppo_cfg.py` 只改了实验名）、1024 个环境、1000 次迭代、种子 42：

```bash
python scripts/rsl_rl/train.py --task Galbot-Reach-Direct-v0 --headless --seed 42 --run_name seed42
python scripts/eval_reach.py --headless --task Galbot-Reach-Direct-v0 --checkpoint logs/rsl_rl/galbot_reach_direct/<运行>/model_999.pt
```

| | 中位误差 | 90% 分位 | < 2 cm | < 5 cm | 姿态中位 | 停住但没到 |
|---|---|---|---|---|---|---|
| Manager 版（6.5.1，2026-10-10） | 2.73 cm | 6.31 cm | 32.2% | 80.9% | 0.068 rad | 7 / 768 |
| Direct 版（2026-10-11） | 2.73 cm | 6.31 cm | 32.2% | 80.9% | 0.068 rad | 7 / 768 |

*表 2：`eval_reach.py` 同口径评估（256 个环境 × 3 段目标，评估种子 0；本站实测，两个检查点同日各评一次）。*

两次训练不只是结果相同：1000 次迭代的日志里，每次迭代的平均奖励与价值函数损失逐项相同，`model_999.pt` 的全部权重差为 0。前提是同一台机器、同一软件版本（Isaac Sim 5.1.0 / Isaac Lab 2.3.2 / rsl_rl 3.1.2）、种子 42：环境逐位等价，而这台机器上的训练本身是确定的（[6.5.1 可复现性](../5-train/6.5.1-train-reach-rsl-rl.md#可复现性)），所以两次训练走了同一条路。

这只说明"两种写法在本项目里给出同一个策略"，不说明谁更好。换一个种子，结果会不同：6.5.1 中种子 43 的第 999 次是 2.91 cm / 83.7%（6.5.1 表 4）。两版在其他种子上是否同样逐位相同，本站没有测（推断会相同，理由同上）。

## 速度

按 [7.2](../../7-infra/7.2-profiling.md) 的口径，两版各跑 3 次，交替进行（`profile_env.py`，1024 个环境，零动作，热身 50 步后计 200 步）：

| | 每个环境步 | 其中物理（4 次 `sim.step`） | 其余（管理器或 Direct 方法、Python） |
|---|---|---|---|
| Manager 版 | 54.51–54.95 ms | 49.24–49.45 ms | 5.24–5.50 ms |
| Direct 版 | 53.90–54.30 ms | 49.27–49.39 ms | 4.62–4.91 ms |

*表 3：环境步耗时（本站实测，2026-10-11，同一时段交替运行）。*

物理两版相同；Direct 版在"其余"一项少约 0.7 ms，占整步的 1.2%。训练日志的 collection（每次迭代采 24 步）中位数：Manager 版 1.461 s，Direct 版 1.419 s；learning 都是 0.055 s 上下。collection 差 2.9%，比表 3 推出来的约 1%（0.7 ms × 24）大。两次训练隔了一天，差出来的部分可能是机器状态（推断，Manager 版那次的 90% 分位是 1.542 s，波动更大）。

少的那 0.7 ms 来自哪里：Manager 版每步按项调用十几个函数（5 项奖励、4 项观测、各管理器的循环与记账），Direct 版合在几个方法里（推断，没有逐函数计时）。这一步里物理占九成，写法能省的部分本来就小，与 4.14 表 5 的结论一致。

## 怎么选

4.14 的"怎么选"仍然适用。本项目的经验是：

- **主线继续用 Manager 版**。省下的约 1% 时间换不来什么，而 6.4.2 加域随机化、6.5.2 调奖励权重，都是在配置里加一项、改一个数，命令行也能直接覆盖。
- **Direct 版适合拿来读**。一个类里能看到全部计算，想知道"这一步到底算了什么"时，比在配置与库函数之间来回跳要快。
- **要改写，先定比对方法**。本页能逐位比对，是因为 Direct 版刻意照搬了 Manager 版的计算顺序。改写时把 `compare_direct_manager.py` 这类比对先写好，每改一处跑一次。

## 常见坑

### 坑一：命令在重置之前更新

把命令的定时更新挪到 `_get_rewards` 开头（`--perturb cmd_in_rewards`）。观测仍与 Manager 版完全相同，只有第 121、242 步的奖励不同：重采样发生在算奖励之前，这一步的奖励是按新目标算的，而策略这一步追的还是旧目标。观测比对通过不能说明奖励也对，两者都要比。

### 坑二：随机数的消耗顺序不同

重置时先采一次命令、再做关节扰动（`--perturb reset_order`）。第 0 步起关节位置差 0.39 rad、目标位姿差 0.30（全程最大 0.44 rad、0.33）；关节速度与奖励从第 1 步起也不同。两版统计上仍是同一个任务，但逐步比对从此无从做起：差异来自顺序，还是来自写错了，分不清。想逐步验证，就要先把顺序对齐。

### 坑三：奖励不乘 `step_dt`、超时早一步

官方 Direct Cartpole 两处都与 Manager 版不同（4.14）。照它改写 Manager 任务，奖励尺度差 30 倍（1 / step_dt），超时也会提前一步。PPO 的超参数是按 Manager 版的奖励尺度调的。

### 坑四：忘了写 `extras["log"]`

Manager 版的分项奖励与 `Metrics/ee_pose/position_error` 由各管理器的 `reset` 返回，基类写进 `extras["log"]`。Direct 版不写，训练照样能跑，只是 TensorBoard 里少了这些曲线，6.5.1 的诊断方法用不上。
