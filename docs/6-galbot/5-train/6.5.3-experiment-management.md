## 一次训练留下什么

这一节回答：日志目录里每样东西回答什么问题？

6.5.1 种子 42 的那次训练目录（本站实测）：

```text
logs/rsl_rl/galbot_reach/2026-10-08_15-12-57_seed42/
├── events.out.tfevents.…        1.4 MB   每次迭代的标量：回报、误差、学习率……
├── model_0.pt … model_999.pt    各 163 KB，共 21 个（每 50 次存一个，外加最后一次）
├── params/
│   ├── agent.yaml               976 B    PPO 配置的最终值
│   └── env.yaml                 21 KB    环境配置的最终值（794 行）
└── git/                                  （本例为空，见下文）
```

| 文件 | 回答的问题 | 由谁写 |
|---|---|---|
| `params/agent.yaml`、`env.yaml` | 这次训练**实际**用的配置是什么（命令行覆盖之后） | `train.py` 用 `dump_yaml` 写入[^train] |
| `model_<迭代>.pt` | 第 N 次迭代时的网络参数与优化器状态 | rsl_rl 每 `save_interval` 次存一个，结束时再存一个[^runner] |
| `events.out.tfevents.*` | 训练过程中各指标怎么变化 | rsl_rl 的 TensorBoard 记录器[^runner] |
| `git/<仓库名>.diff` | 训练时代码有哪些未提交的改动 | rsl_rl 的 `store_code_state`[^codestate] |

*表 1：一次训练的产物（v2.3.2 `train.py` 与 rsl_rl 3.1.2）。v2.3.2 的 rsl_rl 训练脚本只写 yaml，不写 `.pkl`[^train]。*

检查点里存的是 `model_state_dict`、`optimizer_state_dict`、迭代次数与附加信息[^runner]，不含环境配置，所以检查点必须和同目录下的 `params/` 一起保留。

## 三件决定可复现的事

这一节回答：要复现一次训练，需要记下什么？

**1. 代码版本。** rsl_rl 只为"登记过的仓库"写 git 状态：默认是 rsl_rl 自己，`train.py` 再把它自己所在的仓库加进去[^train][^runner]。它们必须是 git 仓库才会写，否则跳过[^codestate]。所以：

| 版本 | 自动记录？ | 补救 |
|---|---|---|
| 本项目的代码 | 项目是 git 仓库时，写 `git/<仓库名>.diff`（status + 相对 HEAD 的 diff） | 训练前提交，diff 就只剩"未提交改动"；本站 scratch 副本不是 git 仓库，所以 `git/` 为空 |
| Isaac Lab | **否**：项目的 `train.py` 只登记它自己所在的仓库 | 在记录表里写 Isaac Lab 的 tag / commit |
| rsl_rl | pip 安装时不是 git 仓库，跳过 | 记 `pip show rsl-rl-lib` 的版本 |
| Isaac Sim | 否 | 记版本号（5.1.0） |

*表 2：代码版本的记录情况（源码 + 本站实测）。*

**2. 配置。** `params/*.yaml` 是覆盖之后的最终值，Hydra 命令行覆盖（如 `env.actions.arm_action.scale=0.25`）已经体现在里面。但**命令行本身没有记录**：要从 yaml 里看出"相对默认改了什么"，需要和基线的 yaml 做 diff（第 4 节）。

**3. 随机种子。** `--seed` 写进 agent 配置，再赋给环境配置[^train]；环境用它调用 `configure_seed`，同时设定 Python、NumPy、PyTorch（CPU 与 CUDA）与 Warp 的随机数；Replicator 的种子在环境的 `seed()` 里另外设[^seed]。`configure_seed` 有一个 `torch_deterministic` 参数，为 True 时开启 PyTorch 的确定性算法，代价是变慢；但环境调用它时用的是默认值 False，训练脚本也没有开关可以打开它[^seed]。

本站实测：同一台机器、同一种子，两次训练的日志与评估**逐位相同**（6.5.1 校验报告）。换显卡、驱动或 Isaac Sim 版本后，只能期待统计上一致（经验性）：用两个以上种子，比较均值与离散程度，不要比较单条曲线。

## 命名与目录规范

这一节回答：本站怎么给训练起名、放文件？

| 项 | 本站约定 | 例子 |
|---|---|---|
| `experiment_name` | 一个任务一个，写在 agent 配置里；换任务才换 | `galbot_reach` |
| `--run_name` | `<相对基线的改动>_s<种子>`，基线写 `base` | `scale025_s42`、`base_s43` |
| `logs/` | 训练输出，不进 git（项目 `.gitignore` 已列） | `logs/rsl_rl/galbot_reach/…` |
| `generated/` | 转换得到的 USD 等派生资产，也不进 git，可由脚本重新生成 | `generated/galbot_fixed_base/` |
| 检查点 | reach 的检查点很小（每个 163 KB），全部保留；大模型至少保留评估选中的那个和最后一个 | 6.5.1 比较过 300 / 600 / 999 |

*表 3：本站约定。目录名里的时间戳由 `train.py` 自动加在 `run_name` 前面[^train]。*

## 实验记录表

这一节回答：几十次训练怎么汇总？

[6.5.2](6.5.2-hyperparameters.md) 表 8 给了手写的记录模板。运行一多，"相对基线改了什么"这一栏可以从 `params/*.yaml` 自动算出来：

```bash
python scripts/collect_runs.py logs/rsl_rl/galbot_reach --base <基线运行目录名> --filter hp_
```

```text
| 运行 | 种子 | 迭代 | 检查点数 | 相对基线的改动 | 末段位置误差 |
| …_hp_base       | 42 | 500 | 11 | 无                                | 3.62 cm |
| …_hp_scale025   | 42 | 500 | 11 | actions.arm_action.scale=0.25      | 14.90 cm |
| …_hp_ent001     | 42 | 500 | 11 | algorithm.entropy_coef=0.01        | 1.86 cm |
| …_hp_dr         | 42 | 500 | 11 | +events.arm_armature；+events.arm_gains；+events.arm_mass；…；observations.policy.enable_corruption=True；+observations.policy.joint_pos.noise；+observations.policy.joint_vel.noise | 3.44 cm |
| …_hp_ent001_s43 | 43 | 500 | 11 | algorithm.entropy_coef=0.01；seed=43 | 2.11 cm |
```

*6.5.2 那批对照的汇总（本站实测，节选）。`+` 后面是基线里不存在（或原本只是一个值，如 `None`）、本次新增的最短配置路径：例如基线的 `joint_pos.noise` 是 `None`，域随机化把它设成了一整块噪声配置。*

- "相对基线的改动"是两份 yaml 逐项比较的结果，所以命令行覆盖也能查出来，不依赖人记得自己敲过什么；
- "末段位置误差"取训练日志最后 20 次的平均，即重置时刻的值（[4.13](../../4-isaaclab/4.13-command-manager.md)），只用于粗看。它比 `eval_reach.py` 的评估偏大（如基线 3.62 cm 对 2.87 cm）。可能的原因有两个：训练时动作带探索噪声，评估取动作均值；日志取平均，会被少数大误差拉高，评估看的是中位数（[6.5.1](6.5.1-train-reach-rsl-rl.md) 坑二）。两者各占多少，本站没有分开测（推断）。正式结论仍以评估为准；
- 评估结果、代码版本、一句话结论，按 6.5.2 表 8 手工补齐。

这批运行名用的是 `hp_<改动>`，早于表 3 的约定，不带种子后缀，所以种子要从"种子"一栏看。这正说明命名约定要在第一次训练前定下来。

## TensorBoard 之外

这一节回答：想把曲线放到网上共享怎么办？

agent 配置的 `logger` 字段可选 `tensorboard`（默认）、`wandb`、`neptune`，另有 `wandb_project`、`neptune_project` 两个字段[^rlcfg]：

| 记录器 | 需要的环境变量 | 本站 |
|---|---|---|
| TensorBoard | 无 | 实测，`tensorboard --logdir logs/rsl_rl/galbot_reach` |
| Weights & Biases | `WANDB_USERNAME`；账号登录方式见 W&B 官方文档 | 未验证 |
| Neptune | `NEPTUNE_API_TOKEN`、`NEPTUNE_USERNAME` | 未验证 |

*表 4：三种记录器（环境变量取自 rsl_rl 3.1.2 源码[^loggers]）。用 W&B 或 Neptune 时，rsl_rl 还会把检查点与 git diff 上传[^runner]。*

多次运行的曲线对比，用 6.5.1 的 `scripts/plot_training.py`，把几个运行目录一起传进去即可。

## 常见坑

:::{admonition} 坑一：只留最后一个检查点
:class: warning

最后一个不一定最好：6.5.1 原样配置第 300 次是 4.71 cm，第 999 次反而是 8.61 cm（6.5.2 表 1）。按 `save_interval` 存下的中间检查点要一并保留，至少保留到评估选定为止。
:::

:::{admonition} 坑二：以为 git/ 记下了所有代码版本
:class: warning

`git/` 只记登记过、而且是 git 仓库的那几个（表 2）。项目不是 git 仓库时它是空的；Isaac Lab 与 Isaac Sim 的版本从来不记。换 Isaac Lab 版本后，旧检查点能否加载、行为是否一致都没有保证（经验性），所以要在记录表里手写版本。
:::

:::{admonition} 坑三：在没提交的代码上训练
:class: warning

本站 6.5.2 那批对照就是在未提交的工作区上跑的：`git/` 里即使有 diff，也只能还原到"HEAD 加上一大段改动"。训练前先提交，记录表里写 commit。
:::

:::{admonition} 坑四：把 logs/ 提交进 git
:class: warning

一次 reach 训练的目录约 5 MB，几十次就是几百 MB，大任务的检查点更大。项目的 `.gitignore` 已经排除 `logs/`、`outputs/`、`generated/`。要分享结果，提交记录表和评估输出，检查点另外存放。
:::
