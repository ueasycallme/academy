## 机制

官方文档的说法是：每张 GPU 一个进程，每个进程各跑一份完整的训练脚本、各建一份环境、各有一份策略网络，只在梯度更新时同步[^doc]。先说三个词：world size 是参与训练的进程总数；rank 是进程在全体中的编号（从 0 起）；local rank 是它在本机上的编号，也就是用第几张卡。按源码拆开来看（依据源码，未验证）：

**Isaac Lab 这一侧**（`--distributed` 打开时）：

- `AppLauncher` 从 torchrun 设的环境变量读 `LOCAL_RANK`、`RANK`，把设备设成 `cuda:<LOCAL_RANK>`，并按 `WORLD_SIZE` 平分 CPU 线程[^launcher]；
- `train.py` 把环境与算法的设备都设成 `cuda:<local_rank>`，种子改成 `seed + local_rank`，让各卡的环境不一样[^train]。

**rsl_rl 这一侧**只看 `WORLD_SIZE`：大于 1 才算分布式[^runner]。这时它会：

- 用 NCCL 初始化进程组（process group），并检查设备必须是 `cuda:<LOCAL_RANK>`[^runner]；
- 开训前由 rank 0 把网络参数广播给其他进程[^bcast]；
- 每次反向传播后，把所有梯度拼成一个张量做 all-reduce 再取平均；自适应学习率用到的 KL 也做 all-reduce，学习率由 rank 0 广播[^reduce]；
- 只有 rank 0 写 TensorBoard 与检查点（`disable_logs`）[^runner]。

官方文档说"Torchrun uses the DistributedDataParallel module"[^doc]。rsl_rl 3.1.2 实际没有用 DDP，而是如上自己做 all-reduce，效果都是"梯度取平均"。

```{mermaid}

  subgraph G0["GPU 0：rank 0"]
```

*图 1：两卡时每张卡上有什么、同步什么（依据源码整理，未验证）。箭头为"数据流向"。环境、观测、经验都不跨卡，跨卡的只有梯度、KL 与学习率。*

**`num_envs` 是每张卡的**：每个进程用同一份配置建自己的环境，rsl_rl 统计每次迭代的样本量时乘上了 `WORLD_SIZE`[^runner]。4 张卡、`num_envs=1024` 等于总共 4096 个环境，每次迭代的样本数也是单卡的 4 倍。官方基准表里，单卡与多卡的"环境数"一列相同，与此一致[^bench]（依据源码与官方基准表，未验证）。

## 命令

官方文档给的写法[^doc]，换成本项目的任务：

```bash
# 单机多卡：每张卡一个进程（未验证，本机单卡）
python -m torch.distributed.run --nnodes=1 --nproc_per_node=2 \
    scripts/rsl_rl/train.py --task Galbot-Reach-v0 --headless --distributed

# 多节点：主节点 node_rank=0，其他节点改成 1、2…（未验证）
python -m torch.distributed.run --nproc_per_node=2 --nnodes=2 --node_rank=0 \
    --master_addr=<主节点 IP> --master_port=5555 \
    scripts/rsl_rl/train.py --task Galbot-Reach-v0 --headless --distributed
```

本站实测的是 `nproc_per_node=1`，并与不加 `--distributed` 的同一配置对照（reach，1024 个环境，种子 42，20 次迭代）：

| 启动方式 | 每次迭代 | 20 次迭代 | 按进程显存 | 主机 RSS 峰值 | 检查点 `model_19.pt` |
|---|---|---|---|---|---|
| `torchrun --nproc_per_node=1 … --distributed` | 1.51 s | 31 s | 3041 MiB | 6.4 GB | sha256 `adc1b0916f11…` |
| `python … `（不加） | 1.51 s | 31 s | 3041 MiB | 5.9 GB | 同上，逐字节相同 |

*表 1：本站实测（2026-10-12，RTX 5070）。RSS 含 torchrun 自己的进程。*

两者逐字节相同，说明单卡上这条路径只换了个启动器：`WORLD_SIZE=1` 时 rsl_rl 不进分布式分支，`seed + 0` 也等于原种子。所以这次实测只验证了命令与 Isaac Lab 这一侧的代码路径。梯度同步那一侧，单卡验证不了。

## 能快多少，要多少

官方基准（Ubuntu 22.04，L40；G1 用 rsl_rl，其余用 RL-Games）[^bench]：

| 任务（环境数 / 卡） | 1 × L40 | 4 × L40（单机） | 16 × L40（4 节点） |
|---|---|---|---|
| Cartpole-Direct（4096） | 26 万 | 95 万（3.7 倍） | 350 万（13.5 倍） |
| Velocity-Rough-G1（4096） | 6.2 万 | 25 万（4.0 倍） | 96 万（15.5 倍） |
| Repose-Cube-Shadow（8192） | 12 万 | 39 万（3.3 倍） | 180 万（15 倍） |

*表 2：每秒环境步数（含推理与训练）。倍数为本站按表计算。*

吞吐接近线性，是因为每张卡的环境数不变，总样本量跟着卡数涨。为什么又不是完全线性（推断）：每次更新都要等最慢的那张卡，并做一次 all-reduce；多节点时还要走网络，官方文档也提醒节点间延迟高时可能比单节点更慢[^doc]。另外要注意，这是吞吐，不是"训到同样效果的时间"：总批量变大以后，学习率等超参数可能要重调（推断；超参数的影响见 [6.5.2](6.5.2-hyperparameters.md)）。

**主机内存**：每个进程都起一份 Kit。本站一个 reach 训练进程的 RSS 峰值是 5.9 GB，N 张卡大约就是 5.9 × N GB（估算）。本机 16 GB，跑 2 个进程就已经很紧。

## 常见坑

### 坑一：单卡上起第二个 rank

设备按 `LOCAL_RANK` 分配，单卡上 rank 1 会去要 `cuda:1`。本站没有真的起两个进程（本机一次只跑一个 Kit 进程），而是只起一个进程，手动给它设 `LOCAL_RANK=1 RANK=1 WORLD_SIZE=2`，模拟 rank 1 的处境。5 s 内报错：`The chosen activeGpu index 1 is higher than the available GPUs`，最后是 `RuntimeError: CUDA error: invalid device ordinal`（本站实测）。想在单卡上"试试多卡"是做不到的。

### 坑二：多节点时种子按 `local_rank` 偏移

`train.py` 用的是 `seed + local_rank`，不是全局 rank[^train]。两个节点上 `local_rank` 相同的进程，种子也相同，环境的随机序列就一样（依据源码，未验证）。在意这一点的，可以在自己的 `train.py` 里改用 `app_launcher.global_rank`。

### 坑三：只有 rank 0 的日志

TensorBoard 与检查点只有 rank 0 写[^runner]，日志里的回报、误差也只是 rank 0 那份环境的统计，不是所有卡的平均。不过 `train.py` 建日志目录、写 `params/` 时没有判断 rank，每个进程都会做一遍；目录名是精确到秒的时间戳，各进程同一秒启动就共用一个目录，否则会多出只有 `params/` 的目录（依据源码，未验证）。

### 坑四：用 `--device cpu` 或忘了 `--headless`

`--distributed` 配 CPU 设备，`train.py` 会直接报错退出[^train]。多卡机器一般没有显示器，不加 `--headless` 的话，每个进程都会试图打开窗口（推断，7.1）。官方说明也只支持 Linux：NCCL 在 Windows 上有限制[^doc]。
