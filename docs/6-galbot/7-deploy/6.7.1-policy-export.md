## 检查点 → 部署件

```{mermaid}
%%{init: {"flowchart": {"rankSpacing": 30, "nodeSpacing": 22, "padding": 6}}}%%
flowchart LR
    CK["model_999.pt<br/>actor + critic + 优化器"] --> AC["ActorCritic<br/>按 agent.yaml 重建"]
    AC --> EX["导出器<br/>actor + 归一化"]
    EX --> PT["policy.pt<br/>TorchScript"]
    EX --> OX["policy.onnx<br/>ONNX"]
    ENV["环境配置"] --> SP["policy_spec.json"]
    PT --> D["deploy/"]
    OX --> D
    SP --> D
```

*图 1：一个检查点变成部署件的过程（流程，左→右）。下面一行是本页新增的接口说明，模型文件之外必须一起交付。*

检查点里有 actor、critic、动作噪声和优化器状态。`play.py` 载入检查点后，把 actor 与观测归一化模块交给 Isaac Lab 的导出器[^play]；导出器只复制这两样，critic 不要[^exporter]。导出的网络就是 actor(归一化(观测))，输出动作的均值，不再采样（[5.2](../../5-rl/5.2-policy-value.md)"策略"）。本项目 reach 没开观测归一化，归一化模块是恒等映射（identity）。

`play.py` 要先建环境才能导出。`export_policy.py` 只读检查点和同目录的 `params/agent.yaml`，按配置重建 rsl_rl 的 `ActorCritic`，再调用同一个导出器类，不需要 Isaac Sim 和 GPU。默认参数导出的 ONNX 与 `play.py` 导出的计算图（computation graph）相同（序列化（serialization）后的哈希一致），TorchScript 的输出差为 0。

## 动态批维度

Isaac Lab 2.3.2 的导出器写死 `dynamic_axes={}`，示例输入是 `[1, 28]`，所以模型只接受批大小 1（6.7.2 坑三）[^exporter]。`--dynamic-batch` 把输入 `obs`、输出 `actions` 的第 0 维命名为 `batch`：

```bash
python scripts/export_policy.py logs/rsl_rl/galbot_reach/<运行>/model_999.pt --dynamic-batch
# 写到 <运行>/deploy/：policy.pt、policy.onnx（opset 18，输入 ['batch', 28]）
```

实测：`[1, 28]`、`[64, 28]` 都能推理；`play.py` 导出的固定版喂 `[64, 28]` 时报 `Got: 64 Expected: 1`。把评估轨迹的 718 个观测逐个喂固定版、一次性喂动态版，两边输出完全相同（差为 0）。

opset 保持 18，与 Isaac Lab 的导出器相同。源码注释说，以前的 11 在 linux-aarch 上出过问题，18 在各平台上都正常[^exporter]。坑二是本站对更高 opset 的实测。

## 三种加载方式是否一致

参照是检查点 actor：在 CPU 上用 rsl_rl 的 `act_inference`，也就是 `play.py` 用的推理策略。拿它对照两个部署件。真实轨迹来自 `eval_reach.py --num_envs 2 --record_obs`：2 个环境各跑一个完整回合，共 2 × 359 步。

| 输入 | TorchScript vs 检查点 | ONNX（onnxruntime）vs 检查点 |
|---|---|---|
| 随机观测 1000 个（标准正态，种子 0；动作最大 25.5） | 0 / 0 | 5.72 × 10⁻⁶ / 4.65 × 10⁻⁷ |
| 评估轨迹 718 步（动作最大 3.19） | 0 / 0 | 1.43 × 10⁻⁶ / 1.11 × 10⁻⁷ |

*表 1：输出的最大差 / 平均差（`bench_policy.py consistency`，2026-10-11）。同一条轨迹上，仿真里 GPU 算出的动作与 CPU 参照也只差 1.31 × 10⁻⁶。*

怎么读：

- **TorchScript 差 0**：它和参照用的是同一套 PyTorch CPU 算子。
- **ONNX 有 10⁻⁶ 级的差**：onnxruntime 的矩阵乘按自己的顺序累加。float32 的相对精度约 1.2 × 10⁻⁷，动作在 1–25 之间，这里只差几个末位，不影响控制。
- **差到 10⁻³ 以上才要查**：多半是归一化、观测顺序或模型版本错了。6.7.2 坑一对调两块观测时，差到了 17.2。

## 推理要多久

| 方式 | 批 1：中位数 / 99% 分位 | 批 64：中位数 / 99% 分位 |
|---|---|---|
| torch CPU，1 线程 | 9.0 / 10.9 | 20.4 / 22.4 |
| torch CPU，20 线程（默认） | 9.1 / 10.7 | 63.8 / 68.7 |
| torch GPU（结果拷回 CPU） | 29.4 / 31.8 | 41.7 / 47.9 |
| onnxruntime CPU，1 线程 | 3.4 / 3.7 | 22.9 / 26.6 |
| onnxruntime CPU，4 线程 | 3.5 / 3.7 | 23.4 / 27.3 |

*表 2：每次调用的延迟，单位 μs（`bench_policy.py latency`：预热 1000 次后计时 10000 次；torch 用部署件 `policy.pt`）。2026-10-11 实测：i7-14700KF（20 核 28 线程）、RTX 5070；主机上同时开着用户的图形界面 Chrome 与远程桌面。连跑 5 遍，各格中位数的变化都在 5% 以内；torch 20 线程批 64 这一格是例外，偶发约 20 μs，见坑三。*

- **小网络在 CPU 上最快**：两层 64 单元的 MLP 计算量很小，GPU 的时间几乎都花在启动计算内核（kernel launch）和拷回结果上。
- **onnxruntime 批 1 只要 3.4 μs**：6.7.2 的往返延迟中位数是 0.48 ms，推理只占其中不到 1%。其余时间花在 ROS 2 的序列化、DDS 传输、执行器调度和仿真端的等待上（推断：本页没有逐段拆分）。所以在这台机器上，想缩短往返，优化推理没有用。

## 接口说明文件

模型文件只说"输入 28 个 float32，输出 7 个"。6.7.2 坑一已经演示过：观测顺序错了不会报错，手臂照样乱动。所以要和模型一起交付一份说明。`make_policy_spec.py` 建一个环境（不跑仿真步），从 ObservationManager 和动作项里读出这些内容，写进 `deploy/policy_spec.json`：

- **观测**：四项的顺序、起止下标与维度（`joint_pos` 0–6、`joint_vel` 7–13、`pose_command` 14–20、`actions` 21–27），关节名，各项的缩放与裁剪（都没有）；
- **归一化**：是否已经折进模型（本例为否）；
- **动作**：7 个关节名、`scale` 0.5、`offset`（即默认关节位置），以及换算式"目标 = offset + scale × 动作"；
- **控制**：物理步 1/120 s、`decimation` 4、30 Hz；
- **出处**：检查点与两个模型文件的 sha256、opset、输入输出形状、生成日期。

这些值都从运行中的环境读出，不手抄源码。改了任务配置，重新生成一次就同步了。

节点一侧，`ros2/policy_spec.py` 在启动时核对三件事：

- sha256 与 ONNX 文件一致；
- 观测顺序与节点拼接的顺序一致；
- 维度一致。

`reach_policy_node.py` 新增 `-p spec:=` 参数来调用它。离线测试的结果：

- 配套的说明文件通过；
- 把前两项对调后，拒绝并报出两种顺序；
- 拿 `play.py` 的 `exported/policy.onnx` 配 `deploy/` 的说明文件，拒绝（sha256 不同）。

这些都是直接运行 `policy_spec.py` 得到的。带 `-p spec:=` 在 ROS 2 下启动节点：未验证（本站 session 未在 ROS 2 下实跑）。

## 常见坑

### 坑一：重新导出动态批维度后，节点的形状检查也要改

6.7.2 的节点启动时断言输入形状是 `[1, 28]`。换成 `deploy/policy.onnx` 后，它的形状是 `['batch', 28]`，断言失败：`AssertionError: ONNX 输入形状 ['batch', 28]，期望 [1, 28]`。本页把检查改为"第 0 维是 1 或 `batch`"，放在 `policy_spec.py` 的 `check_input_shape` 里。说明：这一条是用 onnxruntime 读出形状、执行原断言得到的，没有在 ROS 2 下启动节点。

### 坑二：opset 不是越新越好

用同一个模型试 opset 11–23：

- PyTorch 2.7 默认的导出器（TorchScript 路线）最高只支持 20，指定 21 时报 `Unsupported ONNX opset version: 21`；
- 改用 `dynamo=True` 能导出 22、23，但 onnxruntime 1.20.1 只认到 21，加载 22 时报 `Opset 22 is under development and support for this is limited`；
- 11–21 都能加载。

机器人侧的 onnxruntime 往往更旧。导出时按部署端的版本选 opset，不要按导出端选。

### 坑三：多线程不一定更快

表 2 中，torch 默认 20 线程跑批 64 用了 63.8 μs，1 线程只要 20.4 μs。这一格偶发地很快：同一脚本多次运行时，有时约 20 μs，有时 63–65 μs。本站 8 遍里有 1 遍是 20.8 μs，校验方复跑 3 遍是 63.3、64.2、20.7 μs。这么小的网络，线程同步的开销比计算本身还大；这颗 CPU 又是大小核（P-core / E-core）混合，调度到哪种核上会影响结果（推断）。部署时把线程数固定下来（`torch.set_num_threads`，或 onnxruntime 的 `intra_op_num_threads`），再在目标机器上测一遍。

### 坑四：动作换算漏了一项

动作是"相对默认姿态的偏移、再乘 0.5"。用评估轨迹上的 718 个动作算两种错误换算，与正确的关节目标对比：

- 漏了 offset：差的中位数 0.24 rad，最大 1.57 rad；
- 漏了 scale：差的中位数 0.41 rad，最大 1.59 rad。

两种错误都能让手臂偏出几十度，但模型本身不会报错。`policy_spec.json` 里 `action.formula` 一项就是为此写的。
