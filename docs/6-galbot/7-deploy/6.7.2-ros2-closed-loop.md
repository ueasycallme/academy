## 先定一件事：rclpy 放在哪一边

3.10 实测过：在 source 了系统 Humble 的终端里，Isaac Sim 5.1 进程里的 `rclpy` 无法导入，因为系统 Humble 的 `rclpy` 是给 Python 3.10 编译的，Isaac Sim 用的是 3.11（[3.10](../../3-isaacsim/3.10-ros2-bridge.md)"坑二"）。仿真端有两种选择：

- 用 3.10 的 Action Graph 桥：关节状态、目标位姿各发一个话题，由外部节点自己拼观测；
- 用 Isaac Sim 自带的 ROS 2 库启动 Isaac Lab：这样进程里的 `rclpy` 可用（3.10 表 1），可以直接在 `env.step()` 循环里收发消息。

本页选第二种。观测必须和训练时**逐项一致**，而训练时的观测由 ObservationManager 计算：关节量减默认值、目标位姿换到机器人根坐标系、上一步动作取未缩放的原始值（[6.4.1](../4-task/6.4.1-reach.md)"Observation：只取右臂"）。直接把 `env.step()` 返回的观测发出去，就由同一段代码保证一致。若在外部节点里重写一遍，每一项都可能写错。真机上没有 ObservationManager，那时外部节点就得自己拼，那是 [6.7.3](6.7.3-sim2real-checklist.md) 的话题。

策略节点则在系统 Humble 下运行。它只依赖 `rclpy`、`numpy` 和 `onnxruntime`，与 Isaac 无关，可以原样搬到机器人的电脑上。

## 接口：观测与动作怎么变成消息

| 下标 | 内容 | 训练时的观测项 | 单位 |
|---|---|---|---|
| 0 | 控制步序号 | 不是观测，由仿真端计数 | — |
| 1–7 | 右臂 7 个关节的位置 − 默认位置 | `joint_pos_rel` | rad |
| 8–14 | 右臂 7 个关节的速度 − 默认速度（0） | `joint_vel_rel` | rad/s |
| 15–21 | 目标位姿：位置 xyz + 四元数 wxyz，机器人根坐标系 | `generated_commands("ee_pose")` | m / — |
| 22–28 | 上一步动作 | `last_action` | 未缩放 |

*表 1：观测消息 `/galbot/reach/obs` 的约定（`std_msgs/Float32MultiArray`，29 个数）。顺序就是 ObservationManager 按声明顺序拼接的顺序[^obs]。动作消息 `/galbot/reach/action` 也是 `Float32MultiArray`：data[0] 原样回传步序号，data[1:8] 是 7 个未缩放的动作；仿真端的 `JointPositionAction` 按训练时的规则换算，关节目标 = 默认位置 + 0.5 × 动作。*

用 `Float32MultiArray` 加约定，而不定义自己的消息类型，是为了不用建 ROS 2 包、编译接口，两边各一个 Python 文件就能跑。代价是字段名只写在文档和代码里，消息本身不带。所以策略节点要检查长度：不是 29 就丢弃并报错；ONNX 的输入形状不是 [1, 28] 就拒绝启动。

步序号放在 data[0]，是为了让仿真端确认"这个动作是对哪一步观测算的"。正常运行时用不到，做延迟实验、排查丢包时就离不开它。float32 能精确表示 2²⁴ 以内的整数，本页最长一次运行约 2.3 万步，足够。

控制频率与训练相同：物理步 1/120 s，`decimation` 4，即每 1/30 s 仿真时间交换一次观测和动作（6.4.1"时间参数"）。

## 谁驱动仿真：同步方式（synchronous）

本页让**仿真等动作**：每个控制步，仿真端发出观测，然后阻塞等待同一步序号的动作，收到后才调用 `env.step()`。等待超过 1 s（墙上时间）就保持上一步动作，并记一次超时。这样不管策略节点慢多少，仿真时间里的控制周期都严格是 1/30 s，结果可复现。

真机上没有"等"：机器人按自己的节拍运动，策略算得慢，动作就晚到。这叫异步方式（asynchronous）。要在仿真里模拟它，就得让仿真按墙上时间推进，节点用 `use_sim_time` 读 `/clock`（3.10"时序与频率"），这时结果会受机器负载影响。本页不做异步方式，而是用"人为延迟 N 个控制步"来近似：第 k 步执行的是第 k − N 步观测算出的动作。

策略节点本身是纯响应式的：收到观测就算、算完就发，不读时钟，所以 `use_sim_time` 对它没有影响。节点里一旦用到定时器、TF 查询或消息时间戳，就要像 3.10 那样打开它，仿真端也要发布 `/clock`。

## 前处理：节点里还要不要做归一化

训练时如果开了观测归一化，策略输入的是"减均值、除标准差"之后的观测（[5.2](../../5-rl/5.2-policy-value.md)"观测归一化"）。导出的 ONNX 会把归一化层和 actor 一起带上（[6.6.1](../6-eval/6.6.1-play-replay.md)"导出策略"），所以节点直接喂原始观测即可，不能自己再归一化一遍。本项目 reach 的 `actor_obs_normalization=False`[^norm]，没有这一层。

是否"一致"不靠读代码判断，而是逐步比对：仿真端加 `--checkpoint` 后，每一步都用进程内的 torch 策略对同一个观测再算一次，并记录与节点回传动作的最大差。下面四种情况里这个数都是 1.91 × 10⁻⁶，在 float32 舍入的量级内，说明从观测拼接到 ONNX 推理，整条链路与训练时一致。6.6.1 当时没有装 onnxruntime，只检查了 ONNX 的结构，这里补上了数值比对。

## 闭环实测

开两个终端：一个 source 系统 Humble，启动策略节点；另一个设好 Isaac Sim 自带 ROS 2 库的环境变量（3.10 表 1），启动仿真端。两者先后顺序不限，仿真端会等节点 60 s（坑四）。完整命令见项目 README 的"6.7.2"一节：

```bash
RUN=logs/rsl_rl/galbot_reach/<运行目录>
# 终端 A：策略节点（系统 Humble + onnxruntime 1.20.1）
python ros2/reach_policy_node.py --ros-args -p onnx:=$RUN/exported/policy.onnx
# 终端 B：仿真端（Bridge 自带的 Humble 库）
python scripts/run_ros2_sim.py --headless --mode ros2 --episodes 64 --delay 1 --checkpoint $RUN/model_999.pt
```

四种方式都用同一个检查点，跑 1 个环境、64 个回合，每回合 12 s、3 段目标，共 192 个样本，种子 0。评估口径与 `eval_reach.py` 相同。延迟以控制步计，1 步 = 1/30 s。

| 运行方式 | 位置误差中位数 | 90% 分位 | < 2 cm | < 5 cm | 姿态误差中位数 | 停住但没到 | 往返延迟（round-trip latency）中位数 / 99% 分位；超时 |
|---|---|---|---|---|---|---|---|
| 进程内（torch） | 3.27 cm | 6.27 cm | 24.0% | 80.7% | 0.073 rad | 1 / 192 | — |
| ROS 2，无延迟 | 3.34 cm | 6.30 cm | 24.0% | 79.2% | 0.071 rad | 0 / 192 | 0.48 / 0.84 ms；0 / 23040 步 |
| ROS 2，延迟 1 步 | 4.39 cm | 7.67 cm | 6.8% | 60.4% | 0.112 rad | 0 / 192 | 0.48 / 0.82 ms；0 / 23040 步 |
| ROS 2，延迟 3 步 | 7.57 cm | 11.64 cm | 0.5% | 19.3% | 0.252 rad | 0 / 192 | 0.48 / 0.78 ms；0 / 23040 步 |

*表 2：同一检查点在四种运行方式下的 reach 精度（2026-10-10 实测，RTX 5070；每行墙上时间 808–827 s，仿真端进程显存 2327 MiB（进程内）或 5058 MiB（ROS 2））。延迟队列跨回合不清空。*

几点读法：

- **四行用的是同一批目标。** 目标由命令项按固定时间重采样，不受动作影响。为确认这一点，用零动作和随机动作各跑 2 个回合，记录每段的目标位姿：8 行完全相同。所以表 2 是配对比较（paired comparison），差别只来自运行方式。
- **ROS 2 本身不改变结果。** 无延迟时与进程内只差 0.07 cm（中位数），达标比例差 1.5 个百分点。两边动作最大只差 1.91 × 10⁻⁶，在另一套同版本环境里把两种方式各复跑一次，结果与表 2 逐位相同，可见差异不是 GPU 物理的随机性。它更可能是这约 10⁻⁶ 的动作差别在闭环中被后续状态继承、逐步放大的结果（推断）。同机往返中位数 0.48 ms，远小于控制周期 33 ms。
- **延迟才是主要因素。** 延迟 1 步（33 ms），中位数增加 1.05 cm，< 5 cm 从 79.2% 降到 60.4%；延迟 3 步（100 ms），中位数是无延迟的 2.3 倍，< 5 cm 只剩 19.3%。策略是按"动作立即生效"训练的，延迟后它看到的状态已经过时，修正容易过头（推断）。这个结论只来自一个检查点、一个种子，没有重复多个种子；但它在 192 个配对样本上随延迟单调变化，幅度是 ROS 2 本身带来差别的 15 倍以上。
- **误差大，但手臂没停。** 延迟 3 步时 < 5 cm 只有 19.3%，"停住但没到"却是 0。也就是说，在每段末尾 0.5 s 内，没到位的手臂关节都还在动（超过 0.01 rad）。它是在目标附近来回修正，而不是卡住了（推断，本页没有逐帧记录轨迹）。
- **第一行与 6.6.1 的数字不同，是样本不同。** 6.6.1 用 256 个并行环境，共 768 个样本，中位数 2.73 cm；这里是 1 个环境连续跑 64 个回合，是另一批目标。两组数字不能直接比，表 2 只做行与行之间的比较。

真机上，ROS 2 的传输延迟通常不是瓶颈，瓶颈是控制器周期、传感器延迟和节点调度。要让策略耐受延迟，一般在训练时就把延迟加进环境。本站没有实测这一点，留给 [6.7.3](6.7.3-sim2real-checklist.md) 讨论。

## 常见坑

### 坑一：观测顺序错了，不会报错

为了模拟接口约定错位，在节点里把关节位置、关节速度两块（各 7 维）对调，长度仍是 29，节点照常运行，0 次超时。2 个回合的结果：位置误差中位数 86.26 cm，节点动作与进程内策略最大差 17.2，手臂明显乱动。长度检查查不出顺序错误，只有逐步比对能查出来：调试时始终加 `--checkpoint`，确认"最大差"在 10⁻⁵ 以下，再去看误差。

### 坑二：节点中途退出，仿真端只能保持上一步动作

让节点发完 360 个动作（一个回合）后退出，并把 `--timeout` 设为 0.05 s：后 360 步全部超时，6 个样本里有 3 个"停住但没到"（正常运行时 192 个里 0 个）。手臂停在最后一个关节目标上，不再跟随新目标。默认 `--timeout 1.0` 下，一个回合要卡 6 分钟，所以要看日志里的超时计数，不要只看结果。保持上一步动作对位置控制相对安全，但这是仿真端的选择。真机上应该在连续超时后切到安全姿态或停机（6.7.3）。

### 坑三：ONNX 只接受形状 [1, 28]、类型 float32

6.6.1 导出的模型批大小固定为 1。喂 [2, 28] 时 onnxruntime 报 `Got invalid dimensions for input: obs ... Got: 2 Expected: 1`；喂 float64 时报 `Unexpected input data type. Actual: (tensor(double)) , expected: (tensor(float))`。节点里统一用 `np.asarray(..., dtype=np.float32).reshape(1, 28)`。需要批量推理时（多台机器人共用一个节点），要重新导出动态批维度（dynamic batch axis），本页没有做。消息选 `Float32MultiArray` 而不是 `Float64MultiArray`，也是为了和模型的输入类型一致，省掉一次转换。

### 坑四：仿真端只等节点 60 s

仿真端会等待 `/galbot/reach/obs` 出现订阅者，60 s 内没有就报错退出：`RuntimeError: 60 s 内没有策略节点订阅 /galbot/reach/obs`。两个终端的环境也不能混用：仿真端终端不要 source 系统 Humble（3.10"坑二"），节点终端要 source。
