# 性能分析

:::{admonition} 学习目标
:class: lead-goals

- 遇到"训练太慢"，先用已有的数字算一笔账，判断时间大概花在哪一层
- 会用 rsl_rl 日志、py-spy、cProfile、Kit 的 CPU profiler、`nvidia-smi` 分别看 Python、物理、GPU 和主机
- 知道这些工具在 Isaac 进程里的几个限制，以及它们本身会不会拖慢训练
:::

:::{admonition} 前置知识
:class: lead-prereq

- [6.2.3 批量克隆与性能](../6-galbot/2-scene/6.2.3-cloning-performance.md)（纯仿真的耗时与内存）
- [6.5.1 用 rsl_rl 训练 reach](../6-galbot/5-train/6.5.1-train-reach-rsl-rl.md)
:::

本页的例子都是主线的 Galbot-Reach-v0：1024 个环境，每次迭代 24 步，种子 42，训练 10–30 次迭代。机器是 RTX 5070 12 GB、16 GB 主机内存，测于 2026-10-10。项目里新增两个脚本：`scripts/profile_env.py`（`env.step` 计时与内存读数）和 `scripts/summarize_trace.py`（汇总 Kit 的 trace）。

## 先算账再测

这一节回答：一次迭代的 1.5 s 都花在哪？

rsl_rl 每次迭代分两段计时[^runner]：

- **collection**：采 24 步，每步包括策略前向（`alg.act`）、`env.step`、存入 rollout 缓冲和记账；
- **learning**：算回报，再做 PPO 更新。

日志里的 `Computation: … steps/s (collection: …, learning …)`，以及 TensorBoard 里的 `Perf/collection time`、`Perf/learning_time`，都来自这两段[^runner-log]。本站的实测：collection 1.50–1.52 s，learning 0.058 s。6.5.1 测得 1.47 s 与 0.06 s。

按控制步摊开：

| 层 | 每个控制步 | 来源 |
|---|---|---|
| 4 个物理步（decimation = 4） | 约 55 ms | 6.2.3 表 1：每个物理步 13.8 ms |
| `env.step` 整体（加上各管理器） | 57.3 ms | 6.2.3 的 `debug_vis` 对照 |
| 采集一步（加上策略前向与记账） | 62.5–63.3 ms | collection ÷ 24 |
| PPO 更新，摊到每步 | 约 2.4 ms | learning ÷ 24 |

*表 1：一个控制步的时间构成（1024 个环境）。第一行的 13.8 ms 来自 6.2.3，已含写入与更新；`profile_env.py` 打印的"物理"只计 `sim.step`（4 次共约 52.3 ms），写入与更新（约 3 ms）被算进了它的"其余"，两处口径不同。*

账算下来：物理约占 84%，管理器约 3%，策略前向、记账与 PPO 更新合计约 12%。所以对这个任务，"训练慢"首先是物理慢，优化应先看 6.2.3 的那几个开关，而不是 Python 代码。下面用工具逐层验证这笔账。

## Python 层

这一节回答：Python 侧的时间怎么看？

**py-spy**（采样式分析器，sampling profiler；不改代码，`pip install py-spy`，本站 0.4.2）让它直接启动训练：

```bash
py-spy record --idle -r 50 -o flame.svg -- python scripts/rsl_rl/train.py --task Galbot-Reach-v0 --headless --max_iterations 30
```

本站用 `--format raw` 导出折叠栈，只统计落在 `OnPolicyRunner.learn()` 里的样本：

- `env.step` 占 94%；其中 79% 落在 `physics_context.py` 第 565 行，也就是 `fetch_results()`[^fetch]，Python 在这里等 GPU 上的物理算完；
- PPO 更新占 4%，策略前向占 0.6%，奖励计算占 2.3%。

这与表 1 一致。火焰图（flame graph，`flame.svg`）里最宽的就是这条等待。

**cProfile**（确定性，标准库）在 Isaac 进程里要包在脚本内部用（原因见坑一）。`profile_env.py --cprofile` 对 200 个环境步做了一次：

```text
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
      800   10.373    0.013   10.374    0.013 {built-in method omni.physx.bindings._physx.fetch_results}
      800    0.053    0.000    0.053    0.000 {built-in method omni.physx.bindings._physx.simulate}
```

11.7 s 中有 10.4 s（88%）在 `fetch_results`。cProfile 只计 Python 函数调用，C 扩展内部是一个黑盒，所以它适合回答"Python 侧有没有意外的热点"，不适合看物理内部。

## 物理层

这一节回答：PhysX 内部的时间怎么看？

Kit 自带 CPU profiler，可以把 trace 写成 Chrome trace 格式[^kit-prof]。Isaac Lab 的脚本用 `--kit_args` 传设置：

```bash
python scripts/rsl_rl/train.py --task Galbot-Reach-v0 --headless --max_iterations 10 --kit_args \
  "--/app/profilerBackend=cpu --/app/profileFromStart=1 --/plugins/carb.profiler-cpu.plugin/saveProfile=1 \
   --/plugins/carb.profiler-cpu.plugin/compressProfile=0 --/plugins/carb.profiler-cpu.plugin/filePath=/tmp/kit_trace.json"
python scripts/summarize_trace.py /tmp/kit_trace.json --top 20
```

10 次迭代的 trace 有 157 MB、约 66 万个事件，可以在 Chrome 的 `chrome://tracing` 中打开，也可以用 `summarize_trace.py` 按区段名累计：

```text
  累计 s     次数    平均 ms  区段（线程）
   13.14      962    13.662  PhysX simulate（3196585）
   12.99      961    13.520  fetchResults::waitForCompletion（python (3196281)）
    9.93      962    10.326  PxgPostSolveTask（3196586）
    1.52      962     1.580  ScScene.postBroadPhase（3196586）
```

`PhysX simulate` 平均 13.7 ms，与 6.2.3 的每个物理步 13.8 ms 一致；Python 主线程的大部分时间在 `waitForCompletion`。区段是嵌套的，各行不能相加。启动阶段（扩展加载、`PhysXReplicator::replicate` 等）也在同一个 trace 里。

物理的开销主要由求解器迭代次数和物理步数决定。前者的实测见 [6.1.6](../6-galbot/1-asset/6.1.6-articulation-cfg.md) 表 2：1024 个环境时，位置 / 速度迭代为 32 / 1、16 / 1、8 / 0 时，分别是每秒 44、74–75、118–120 个物理步。后者由 `dt` 与 `decimation` 决定，属于任务参数（[4.4](../4-isaaclab/4.4-simulation-context.md)）。

## 渲染层

这一节回答：开了渲染会怎样？

无头且不建相机时，训练根本不渲染（[7.1](7.1-headless-remote.md)）。只要加 `--enable_cameras`，即使不建相机，进程也多占约 1 GB 显存、2.6–2.8 GB 主机内存；建了相机，每步还要加上渲染时间。1024 个环境时，64×64 的相机让每步多 50 ms，128×128 多 90 ms：像素是 4 倍，时间不到 2 倍，并不是简单的线性关系（[6.2.2](../6-galbot/2-scene/6.2.2-wrist-camera.md) 表 2）。

## GPU 与主机

这一节回答：怎么确认不是别的东西在拖慢？

- **`nvidia-smi dmon -s um`**：每秒打印 SM 与显存带宽的利用率。本站训练时 SM 为 85–89%，显存（整卡）约 3580 MB，其中约 510 MB 是桌面本来就占着的。
- **按进程显存**：用 `nvidia-smi --query-compute-apps=pid,used_memory`，不要用整卡读数。`torch.cuda` 的统计只是其中很小一部分：`profile_env.py` 测得 `memory_allocated` 只有 9 MiB、`max_memory_allocated` 11 MiB，而按进程是 2977 MiB，其余是 PhysX、Kit 与 CUDA 上下文。
- **主机内存**：按进程看 RSS，按整机看 `free -m` 的 available（6.2.3 表 4）。
- **被别的进程抢占**：6.4.3 的一次 lift 训练（2048 个环境），第 841–1164 次迭代期间，桌面上的 rviz2 与 Chrome 也在用 GPU，`Perf/collection time` 的中位数从 3.32 s 涨到 6.04 s，之后回到 3.50 s（本站从 TensorBoard 日志读出）。判断方法：TensorBoard 里这条曲线出现台阶，同时 `nvidia-smi` 的进程列表里有别的进程。

## 一套顺序

| 症状 | 先看哪个数 | 用哪个工具 |
|---|---|---|
| 每次迭代比平时慢 | `Perf/collection time` 是否突然出现台阶 | TensorBoard；`nvidia-smi` 进程列表 |
| collection 一直偏慢 | 物理占多少（表 1） | `profile_env.py`；6.2.3 的 `scene_bench.py` |
| 怀疑 Python 侧有热点 | `learn()` 内的样本分布 | `py-spy record --idle`；脚本内 cProfile |
| 想看 PhysX 内部 | 各区段的平均耗时 | Kit CPU profiler + `summarize_trace.py` |
| learning 偏慢 | mini-batch 数、网络规模 | rsl_rl 日志（[6.5.2](../6-galbot/5-train/6.5.2-hyperparameters.md)） |
| 内存不够、进程被停 | 分阶段 RSS、MemAvailable | 6.2.3 表 4；`free -m` |

*表 2：症状 → 数字 → 工具（与 [7.3](7.3-debugging.md) 的调试顺序配合使用）。*

## 常见坑

:::{admonition} 坑一：python -m cProfile 包住训练脚本，什么也没得到
:class: warning

`SimulationApp.close()` 最后调用 `shutdown_and_release_framework()`，源码注释说此时 Python 进程即将被终止[^close]。`python -m cProfile -o out.prof train.py …` 因此来不及写结果：本站实测训练正常结束，`out.prof` 不存在。要在脚本里用 `cProfile.Profile()` 包住关心的部分，在 `close()` 之前 `dump_stats`（`profile_env.py --cprofile`）。
:::

:::{admonition} 坑二：py-spy 附加到正在跑的进程被拒
:class: warning

`py-spy dump --pid <训练进程>` 报 `Permission Denied: Try running again with elevated permissions by going 'sudo env "PATH=$PATH" !!'`（本站实测，同一用户）。原因是本机 `kernel.yama.ptrace_scope = 1`，只允许追踪自己的子进程。要附加，得用 sudo 或者改 ptrace_scope，本站未验证，也没有改这个系统设置。用 `py-spy record -- python …` 直接启动目标，就没有这个问题。
:::

:::{admonition} 坑三：py-spy 不加 --idle，看不到等 GPU 的时间
:class: warning

py-spy 默认只采正在跑的线程；在 `fetch_results` 里等待 GPU 的线程算作空闲，不会出现在火焰图里[^pyspy]。本站不加 `--idle` 的那次，火焰图里看不到这段等待，大头反而成了启动阶段。看训练时要加 `--idle`，并且只看 `learn()` 下面的样本。
:::

:::{admonition} 坑四：开着渲染测物理
:class: warning

带 `--enable_cameras` 或开着 GUI 时测得的每步耗时，含有渲染时间。比较物理参数前，先确认是无头、没有相机。
:::

工具本身的开销：本站观察到，Kit CPU profiler 开着时 collection 是 1.50 s，与不开相同；py-spy（每秒 50 次采样）时，本站两次为 1.53–1.59 s，校验方复跑为 1.544–1.659 s，多几个百分点（2–9%）；脚本内 cProfile 包住 `env.step` 时，每步 58.68 ms，不开时 58.64 ms。另外，基线 base1 运行期间本站跑过一次文档构建，所以基线取的是 base2 的数（collection 1.50–1.52 s）。
