# 仿真代码的测试与 CI

:::{admonition} 学习目标
:class: lead-goals

- 把一个 Isaac Lab 项目的检查分成三层：不需要 GPU 的、要起 Kit 的、训练回归
- 在 Kit 里写 pytest：一个进程只起一次 Kit，用例之间不互相影响
- 给训练回归定阈值，分清"逐位相同"和"落在区间里"两种口径
- 用 GitHub Actions 跑不需要 GPU 的那一层
:::

**本页在项目中新增**：`tests/`（`unit/`、`gpu/`、`regression/` 三个目录，共 18 个用例）、`pytest.ini`、`tests/requirements-ci.txt`；本站仓库新增 `.github/workflows/examples-tests.yml`。`ros2/policy_spec.py` 把 `import onnxruntime` 挪进命令行入口，两个检查函数因此能在没装 onnxruntime 的环境里测试。

## 三层测试

| 层 | 测什么 | 需要什么 | 本站耗时与资源 |
|---|---|---|---|
| ① 无 GPU（`tests/unit/`，13 个） | 转换参数（6.1.2）；资产清单能报出参数与文件差异（6.1.7）；`policy_spec` 接受配套的、拒绝顺序错 / 维度错 / 模型不配套的（6.7.1）；`sim2real_report` 的越限计数（6.7.3）；Wilson 区间与 6.6.2 表 3 一致 | 系统 python3 + pytest、numpy、matplotlib | 0.3 s；不占显存 |
| ② 冒烟（`tests/gpu/test_smoke.py`，3 个） | 所有 Galbot 任务的配置能构造；reach 的 Manager 版与 Direct 版各建 4 个环境，走 30 步，观测形状 (4, 28)、观测与奖励都是有限值 | Isaac Lab 的 Python、GPU | 12 s（含起 Kit）；按进程显存 2315 MiB，主机 RSS 3.5 GB |
| ③ 训练回归（`slow` 标记，2 个） | 种子 42 短训 3 次迭代，权重指纹与记录逐位相同；换评估种子，成功率落在 6.6.2 的区间里 | 同上；区间那个还要 6.5.1 的检查点 | 7.8 s 与 26 s |

*表 1：三层测试（本站实测，2026-10-11）。冒烟层更深入的环境自检用 7.3 的 `check_env.py`。*

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest tests -q   # 系统 Python：13 passed, 1 skipped（之后的页面会加用例：7.6 后为 16，6.3.2 后为 19；变量见坑五）
$PY -m pytest tests/gpu -m "not slow" -q                # Isaac 的 Python：②，3 passed
$PY -m pytest tests/gpu -m slow -q                      # ③ 的确定性部分
GALBOT_REACH_CKPT=<model_999.pt> $PY -m pytest tests/regression -q   # ③ 的区间部分，单独跑
```

`tests/conftest.py` 判断当前 Python 里有没有 `isaaclab`，没有就不收集 `tests/gpu/`。所以同一条 `pytest tests`，在系统 Python 里只跑第一层，在 Isaac 的 Python 里跑前两层与确定性回归；区间回归要另起评估进程，发现本进程已经起了 Kit 就跳过，必须单独一次 `pytest tests/regression`（坑四）。

## 在 Kit 里写 pytest

Kit 一个进程只能起一次，而且必须在导入任何 `isaaclab`、`omni` 模块之前起。Isaac Lab v2.3.2 自己的测试是这样写的：每个测试文件开头就创建 `AppLauncher(headless=True)`，文件里的用例共用它[^lab-test]；`./isaaclab.sh --test` 的测试入口再让每个测试文件单独跑在一个子进程里[^lab-runner]。

本项目把这一步放进 `tests/gpu/conftest.py`，整个 pytest 进程只起一次 Kit，目录里所有文件共用它。环境由一个 fixture 来建：

```python
@pytest.fixture
def make_env():
    envs = []
    def _make(task, num_envs, seed=0):
        omni.usd.get_context().new_stage()   # 每个环境一个新 stage
        cfg = parse_env_cfg(task, device="cuda:0", num_envs=num_envs)
        cfg.seed = seed
        envs.append(env := gym.make(task, cfg=cfg))
        return env
    yield _make
    for env in envs:
        env.close()                          # 用例结束一定关掉
```

每建一个环境之前换一个新 stage，用例结束时关掉环境。这两步与 Isaac Lab 自己的测试相同[^lab-stage]，少了第一步就会卡住（坑三）。

共用 Kit 能省多少：冒烟层 3 个用例放在一个进程里，墙上时间 12 s；每个用例单独起一个进程，合计 22 s（本站实测，秒级精度）。本机 Kit 的热启动只要几秒，所以差别不大。用例越多、首次启动越慢（如重建着色器缓存），差得越多。

## 回归阈值怎么定

同一台机器、同一套软件版本、同一个种子，训练是逐位确定的：6.5.1 训两次，日志与评估完全相同；6.4.4 的 Direct 版与 Manager 版训出的权重差为 0。由此有两种口径：

- **逐位相同（确定性回归）**：`test_ppo_deterministic` 用种子 42、256 个环境训 3 次迭代，把所有权重的 sha256 与记录在 `tests/gpu/golden_ppo.json` 里的比。记录时带上"torch 版本 / GPU 型号"，换了机器或版本就跳过，不报失败。**会误报的情况**：任何改变数值的改动，即使是有意的（改奖励权重、改观测、换环境数），都会让指纹变化。这正是它的用途：指纹变了，说明行为变了，确认无误后用 `GALBOT_RECORD_GOLDEN=1` 重新记录。
- **落在区间里**：`test_eval_success_rate_in_interval` 用评估种子 1 跑 `eval_reach.py`，要求 < 5 cm 的比例落在 6.6.2 表 3 种子 0 的 Wilson 区间 77.9–83.5% 里（本站实测通过；6.6.2 中种子 1、2 分别是 81.0%、82.0%）。换机器、换种子都可以用。**会误报的情况**：95% 区间本身就允许约 5% 的偶然落在区间外；评估分布变了（6.6.2"评估分布要写进结论"），区间也就不再适用。

## CI：GitHub Actions 只跑无 GPU 层

`.github/workflows/examples-tests.yml` 的要点：

- **触发**：只在 `examples/isaaclab-2.3/6-galbot-project/**` 或本文件改动时跑（`paths` 过滤[^gh-syntax]），改网站正文不触发；
- **环境**：`ubuntu-22.04` + Python 3.10，不装 Isaac Sim，只装 `tests/requirements-ci.txt` 里钉死版本的 pytest 8.3.3、numpy 1.26.4、matplotlib 3.8.4；
- **命令**：`python -m pytest tests -m "not gpu" -q`。

本站在一个干净的 Python 3.10 venv 里装同样三个包，跑出 `13 passed, 1 deselected`。workflow 文件在合并前只做了 YAML 解析与路径核对；它第一次在 GitHub 上实际运行的结果，由校验方在合并后补记。

要在 CI 里跑第二、三层，需要一台装好驱动与 Isaac Sim 的自托管 runner（self-hosted runner），在 workflow 里用 `runs-on: [self-hosted, gpu]` 这类标签选中它[^gh-runner]。本站没有这样的 runner，这部分**未验证**。

## 常见坑

### 坑一：只看返回码

Kit 出错时，进程返回码仍可能是 0：Galbot 的 MJCF 导入失败时就是这样（[3.5](../3-isaacsim/3.5-urdf-mjcf-import.md)）。区间回归另起进程跑评估脚本，断言的是输出里的数，找不到就失败，并把返回码与输出末尾一起报出来。

### 坑二：pytest 的参数传进了 Kit

`pytest -m slow` 时，Kit 启动会读 `sys.argv`，报 `Ill formed parameter: -m` 后段错误（本站实测）。AppLauncher 只会清掉 `-m pytest` 这一种[^lab-argv]。所以 `conftest.py` 起 Kit 前把 `sys.argv` 换成只剩程序名，起完再换回来。

### 坑三：同一进程里建第二个环境会卡住

第一个环境 `close()` 后不换新 stage，直接建第二个环境，本站等了 10 分钟仍没有结束，CPU 一直占满。加上 `omni.usd.get_context().new_stage()` 后，三个冒烟用例 7 s 跑完。

### 坑四：两个 Isaac 进程同时在跑

`pytest -m slow` 会同时收集 `tests/gpu/` 和 `tests/regression/`：前者让 pytest 进程起了 Kit，后者又起一个评估子进程，两个 Kit 并存。本站第一次这样跑时，显存峰值 4956 MiB、主机 RSS 8.7 GB，16 GB 的机器只剩一半，再开别的程序就可能被 OOM 杀掉；本机的规则也是一次只跑一个 Kit 长进程。现在区间回归发现本进程已起 Kit（`omni.kit.app` 已导入）就跳过，要单独一次 `pytest tests/regression`。

### 坑五：本机环境里的 pytest 插件

本机系统自带的 pytest 6.2.5 会自动加载用户目录下一个新版插件，启动就报 `No module named '_pytest.scope'`；shell 里 source 过 ROS 2 Humble 时，`PYTHONPATH` 还会带进 ROS 的 pytest 插件，报缺 `yaml`。本地用 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` 或干净的 venv；CI 是干净环境，又钉死了版本，不受影响。
