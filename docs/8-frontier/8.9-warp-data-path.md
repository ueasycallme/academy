## ProxyArray：一份数据，两个入口

这一节回答：`robot.data.xxx` 拿到的到底是什么，什么时候会拷贝？

3.0 里资产和传感器的数据属性返回 `ProxyArray`[^howto]。它里面只有一个 Warp 数组 `wp.array`，对外给出两个入口：

- `.warp` 原样返回这个 Warp 数组[^proxy-acc]；
- `.torch` 第一次访问时用 `wp.to_torch` 包成一个 Torch 张量，并缓存起来，之后都返回同一个张量。两者共用同一块显存，改一边，另一边也变[^proxy-acc]。

`ProxyArray` 本身还实现了 `__cuda_array_interface__`，所以可以直接作为参数传给 `wp.launch`，不用先取 `.warp`[^proxy-cai]。

| 操作 | 拷贝吗 | 说明 |
|---|---|---|
| `data.x.torch` | 不拷贝 | 缓存的零拷贝视图；第一次访问时才创建 |
| `data.x.warp` | 不拷贝 | 就是底层的 `wp.array` |
| `wp.launch(k, inputs=[data.x, …])` | 不拷贝 | 经 `__cuda_array_interface__` |
| `wp.from_torch(t)` / `wp.to_torch(a)` | 不拷贝 | 互相包装，共用显存 |
| `data.x.torch[:, i]`、`.torch + 1` 等 Torch 运算 | 结果是新张量 | 普通的 Torch 语义：切片是视图，算术运算产生新张量 |
| `data.x[0, 3]`、`torch.sum(data.x)` 这类旧写法 | 同上，另发一次弃用警告 | 弃用桥，会在之后的版本删除[^howto] |
| 跨重置保留 `.torch` 的结果 | — | 不要这样做：Newton 在完整重置时可能重建缓冲，旧张量会指向过时或已释放的显存[^howto] |

*表 1：`ProxyArray` 的操作与拷贝（v3.0.0-EA，依据文档与源码）。"不拷贝"指不复制数据，只是换一种方式看同一块显存。*

数据的四元数顺序是 (x, y, z, w)，与 Warp 的 `wp.quatf` 相同，内核里可以直接用 `wp.quat_rotate`，不用换顺序。2.3 的 Torch 代码按 (w, x, y, z) 写，迁移时要改（[8.4](8.4-migration-23-30.md#四元数-wxyz--xyzw)）。设环境变量 `WARN_ON_TORCH_QUATF_ACCESS=1` 后，每次对四元数数据取 `.torch` 都会发警告，可以用来找漏改的地方[^proxy-acc]。

## 同一个奖励，两种写法

这一节回答：把一个奖励项改写成 Warp 内核，代码长什么样？

以 Galbot reach 的末端位置误差为例（8.5 的 `tcp_position_error`）。它要算：

- 目标（世界系）= 根位置 + 根姿态 ⊗ 指令位置；
- TCP（世界系）= 末端刚体位置 + 刚体姿态 ⊗ TCP 偏移；
- 误差 = ‖TCP − 目标‖。

torch 版先对每个数据取 `.torch`，再调两次 `combine_frame_transforms`（每次是几个批量的四元数运算），最后求范数。Warp 版把整件事写成一个内核，每个环境一个线程：

```python
@wp.kernel
def _tcp_position_error_kernel(
    root_pos: wp.array(dtype=wp.vec3f), root_quat: wp.array(dtype=wp.quatf),
    body_pos: wp.array2d(dtype=wp.vec3f), body_quat: wp.array2d(dtype=wp.quatf),
    command: wp.array2d(dtype=wp.float32), body_idx: int, offset_pos: wp.vec3f,
    out: wp.array(dtype=wp.float32),
):
    i = wp.tid()
    cmd_pos = wp.vec3f(command[i, 0], command[i, 1], command[i, 2])
    target = root_pos[i] + wp.quat_rotate(root_quat[i], cmd_pos)
    tcp = body_pos[i, body_idx] + wp.quat_rotate(body_quat[i, body_idx], offset_pos)
    out[i] = wp.length(tcp - target)
```

调用时，资产数据以 `ProxyArray` 原样传入，指令（Torch 张量）用 `wp.from_torch` 包一层，输出缓冲只分配一次，最后用 `wp.to_torch` 交回给奖励管理器，因为奖励管理器要的是 Torch 张量。全程没有数据拷贝。完整代码在 8.5 项目的 `tasks/reach/mdp/rewards_warp.py`，函数签名与 torch 版相同，可以直接在 `RewardsCfg` 里替换。

**两版的结果一致吗**：`scripts/bench_reward_warp.py` 加载 8.8 训练的 Galbot 检查点，用策略推进 200 步，每步在同一个状态上调用两版：

| 环境数 | 最大绝对误差 | 最大相对误差 | 逐位相同的步数 |
|---|---|---|---|
| 1024 | 3.8×10⁻⁶ / 4.1×10⁻⁶ m | 2.5×10⁻³ / 4.1×10⁻³ | 0 / 200 |
| 4096 | 7.6×10⁻⁶ / 7.6×10⁻⁶ m | 5.4×10⁻³ / 5.8×10⁻³ | 0 / 200 |

*表 2：torch 版与 Warp 版的逐步比对（本站实测，各 2 次，每格前后为两次）。相对误差 = 绝对误差 ÷ torch 版的值，误差本身很小（接近目标）时会被放大。*

两版没有一步是逐位相同的，但绝对误差在 10⁻⁵ m 以内，相当于 float32 在米级数值上的舍入（推断：两版的运算顺序不同）。对于以厘米计的奖励，这个差别可以忽略。本站的判据是绝对误差 < 10⁻⁵ m。

## 值不值得

这一节回答：Warp 版快多少，占一步的多少？

在比对之后的状态上，两版各调用 200 次（每次前后 `torch.cuda.synchronize`），再推进 200 步测整个 `env.step`：

| 环境数 | torch 版单次 | Warp 版单次 | env.step | torch 版占一步 | Warp 版占一步 |
|---|---|---|---|---|---|
| 1024 | 0.139 / 0.137 ms | 0.047 / 0.048 ms | 11.0 / 11.0 ms | 1.26% / 1.24% | 0.43% / 0.43% |
| 4096 | 0.137 / 0.138 ms | 0.048 / 0.048 ms | 21.3 / 21.2 ms | 0.64% / 0.65% | 0.22% / 0.22% |

*表 3：单个奖励项的耗时（本站实测，RTX 5090，独占 GPU，2026-10-12；每格两次，各 200 次取中位）。`env.step` 含 Newton 物理（decimation 4）与全部 MDP 项。*

三点结论：

- **Warp 版快约 3 倍，但省下的只有约 0.09 ms**，不到一步的 1%。只为这一个奖励项改写，不值得。
- **两版的耗时都不随环境数变化**：4 倍的环境数，单次时间几乎不变。说明这里的时间主要花在 Python 与每次启动内核的固定开销上，不在计算本身（推断）。所以环境数再多，单个项的比例也只会更小。
- **值得的情形是整条路径都换成 Warp**：许多小项各省一点固定开销，再把整步录成 CUDA graph。官方的实验性 Warp 环境（`--frontend warp`，见 [8.7](8.7-isaaclab-cli.md#train--play参数分三层)）报告的每步时间，Cartpole、Ant 这类小任务少了一半左右，计算重的任务少得多[^warp-env]。本站没有测这一项。

## 常见坑

:::{admonition} 坑一：Warp 版的返回值留到下一步就变了
:class: warning

为了不每步分配显存，Warp 版把输出写进一个固定缓冲，返回的是它的零拷贝视图（`wp.to_torch`）。本站实测：把上一步的返回值留着，再算一次，两次返回的张量共用同一块显存，旧值已被覆盖。奖励管理器每步当场累加，不受影响；自己写的日志、统计如果要保存，先 `.clone()`。这和 [`ProxyArray` 不要跨重置保留](#proxyarray一份数据两个入口)是同一类问题。
:::

:::{admonition} 坑二：dtype 不对，内核在启动时就报错
:class: warning

内核参数写的是 `wp.array(dtype=wp.vec3f)`，传入 `(N, 3)` 的 `float32` 数组不会自动转换。本站实测报错原文是 `RuntimeError: Error launching kernel '_tcp_position_error_kernel', argument 'root_pos' expects an array with dtype=<class 'warp._src.types.vec3f'> but passed array has dtype=<class 'warp._src.types.float32'>.`。把 float64 的 Torch 张量经 `wp.from_torch` 传入也一样报错。先看清数据的 dtype：资产数据的位置是 `vec3f`，姿态是 `quatf`，`body_pos_w` 是 `(环境数, 刚体数)` 的 `vec3f` 二维数组（本站读回）。
:::

:::{admonition} 坑三：把 CPU 上的数组传给 GPU 内核，不报错
:class: warning

本站实测：指令数组放在 CPU 上，内核在 `cuda:0` 上启动，没有报错，结果也正确。原因在 Warp 的默认设置：`wp.config.launch_array_access_mode` 默认是 `RELAXED`，启动内核时不检查数组在哪个设备，指针原样交给硬件[^warp-access]。至于为什么 GPU 能读到这块主机内存，推断是驱动允许 GPU 直接访问主机内存，每次访问都走 PCIe：不报错，只会慢。调试时设 `wp.config.launch_array_access_mode = wp.config.LaunchArrayAccessMode.STRICT`，同样的调用会当场报 `input array for argument 'command' is on device=cpu`（校验方实测；`CHECKED` 也不报）。
:::

:::{admonition} 坑四：第一次调用要编译内核
:class: warning

Warp 内核第一次用到时才编译，结果缓存在 `~/.cache/warp`。本站用空的缓存目录（`WARP_CACHE_PATH` 指向新目录）实测：这个奖励内核第一次调用耗时 79 ms，有缓存时 0.8 ms。同一个缓存里还有 Newton、MJWarp 的所有内核，冷启动时这个目录长到 57 MB。容器或 CI 每次都从空缓存开始，要把这个目录挂载出来，或者在镜像里预热一次。
:::
