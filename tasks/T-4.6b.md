### 实现附记（isaac-academy-accomplish，2026-09-30）

**结论：原因已由源码证实，而且与我最初报告时的推断不同。** 最初推断是"`sim.forward()` 读回了尚未生效的速度"，这是错的。实际是速度在写入之前就被夹成了 0：

1. **两条路径的差别**：
   - `ManagerBasedEnv.reset()`（manager_based_env.py L372–L386）：`_reset_idx`（含 reset 事件）→ `scene.write_data_to_sim()` → `sim.forward()` → 计算观测。
   - `step()` 内的重置发生在本步的 decimation 循环之后；此前每个物理步都已调用过 `write_data_to_sim()`。
   - 差别不在读数，而在事件运行时 `data.soft_joint_vel_limits` 是否已被填充：
     - `_create_buffers` 把它建为全 0（articulation.py L1653–L1654）；
     - 只有 `write_data_to_sim()` → `_apply_actuator_model()`（L258 → L1903）才填入执行器的 `velocity_limit`；
     - `reset_joints_by_offset` / `_by_scale` 按它夹紧速度（events.py L1310–L1312、L1270–L1272）。
   - 第一次 `reset()` 时，事件运行在任何 `write_data_to_sim()` 之前，速度被夹成 0，并由 `write_joint_state_to_sim` 写进 PhysX。这一步同时更新 data 缓冲（`joint_vel` 带时间戳的惰性读取，写入时直接改缓存，articulation.py L642–L646）。
   - 实测：在 `write_joint_state_to_sim` 上加探针，传入的 velocity 已是 0 / −0.0；写入后 data 与 PhysX 读回一致，都是 0。
2. **范围**（实测，除注明外）：
   - GPU 与 CPU 管线相同。
   - 位置不受影响：`soft_joint_pos_limits` 在初始化时已设好。
   - 只影响各环境第一次 `reset()`；`step()` 内重置与第二次 `reset()` 正常。
   - `DirectRLEnv.reset()` 的调用顺序相同（direct_rl_env.py L313–L318），由源码推知同样受影响，未实测。
   - 训练中 RSL-RL 适配层创建时会调用一次 `reset()`（vecenv_wrapper.py L66），所以每个环境的第一个回合从零速度开始。
3. **探针脚本**：`examples/isaaclab-2.3/4.6-assets/first_reset_velocity.py` 遵守退出三步，输出 5 个时刻的对照表；README 已补充。GPU 与 CPU 各跑两次，逐字一致；按进程显存 GPU 2315 MiB、CPU 253 MiB。
