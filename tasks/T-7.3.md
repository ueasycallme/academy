## 目标

读者在"任务跑起来了但行为不对"时知道从哪下手：把环境缩到 1 个、把张量打印出来、把目标和末端画出来、在该停的地方停下。把第 6 部分零散用过的手段（check_env、check_reach_targets、hold_pose、eval_reach、workspace 可视化）收拢成一套顺序。

## 必须覆盖

1. **先缩小再看**：`--num_envs 1`（或 2）、固定种子、关掉随机化（DR 任务 vs 非 DR 任务的切换）、缩短 episode；哪些 bug 只在多环境下出现（索引错位、广播错误），给一个本站真实的例子（第 6 部分里有过的，引对应 notes / 卡片附记）。
2. **看张量**：在 `ManagerBasedRLEnv` 外面取 `env.obs_buf` / `env.reward_buf` / 各 Manager 的 term 值（`get_active_iterable_terms`，v2.3.2 permalink）；观测各项的均值/方差检查（归一化前后）；`print` 与 `torch.set_printoptions` 的实用设置；NaN 的定位顺序（回链 D-026 的经验：先查初始状态与接触，再查参数）。
3. **可视化 marker**：`VisualizationMarkers`（v2.3.2 源码）画目标点与末端位置；command 的 `debug_vis`（回链 4.13）；本站示例：给 reach 加 `debug_vis=True`，GUI 下截图一张（D-025 字号不适用于截图，但图说明要有）。
4. **断点与调试器**：`breakpoint()` / `pdb` 在 Kit 进程里可用的前提（headless、stdin 可用）；VS Code 的 attach（`debugpy`）最小配置，与 1.8 占位的分工（本页只给能跑的最小配置，IDE 细节留 1.8）；为什么断点停住后物理不会"继续走"（回链 3.1 的事件循环）。
5. **日志在哪**：Kit 日志路径（`~/.nvidia-omniverse/logs/...`，回链 1.7 表 4）、rsl_rl 日志、如何让警告不被淹没（`--verbose` / `carb` 日志级别一句话）。
6. **一套顺序**（一张表或流程图）：症状 → 先做什么 → 用哪个脚本；把 5.8"训练不收敛时看什么"的"训练前检查"部分链接过来，不重复。
7. 常见坑 ≥ 3（候选：在 GUI 下 `breakpoint()` 卡死界面；打印整个 4096×N 张量；忘了 `env.reset()` 后观测才有效；DR 没关导致"随机复现不了"）。
