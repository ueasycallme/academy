## 目标

把本站主线项目一路走来形成的约定写成一页团队规范：项目怎么分目录、配置怎么继承不出意外、任务 / 实验 / 检查点怎么命名、提交前检查什么。每条都指向项目里的真实例子，不写空泛原则。

## 必须覆盖

1. **项目结构**：以 4.18 模板为底的目录约定（`tasks/<manager_based|direct>/<task>/`、`assets/`、`scripts/`、`tests/`），本项目现状一张树（≤ 25 行）；什么放包内、什么放 `scripts/`。
2. **配置继承约定**：`@configclass` 的 `replace` / 子类 / `__post_init__` 三种方式各适合什么（4.3）；本项目的变体链（Reach → Play → DR → Direct）作例子；哪些字段改了必须重训（回链 6.3.1 结论一节）。
3. **命名**：任务 id（`Galbot-<Task>-<Variant>-v<N>`）、实验名与种子、检查点目录、数据文件；一张表给规则 + 本项目实例。
4. **提交前清单**（写成 `CONTRIBUTING.md`）：文件头验证版本 / 日期 / GPU（CONVENTIONS 第 5 节）、退出三步、显存按进程口径、`num_envs` 上限、无 GPU 测试通过（7.4）、README 小节、新配置的 `check_actuator_groups` 等兜底脚本。
5. **评审看什么**：仿真代码评审与普通 Python 评审的不同（随机性、设备、形状、单位、坐标系），每项一个本站真实 bug 作例（引对应 reviews / 卡片附记，不点名）。
6. **常见坑 ≥ 3**（候选：配置类可变默认值共享；注册 id 冲突；硬编码绝对路径；不同人用不同 Isaac 版本）。

## 验收标准

每条规则都有项目内实例；`CONTRIBUTING.md` 与页面一致；4.3、4.15、4.18、6.5.3、7.4、6.3.1 链接可达；不写与本站 WORKFLOW 相关的内容（那是站点协作，不是读者的团队）。
