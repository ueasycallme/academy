## 目标

读者把 0.6 的"一个 RL step 里发生了什么"落到 v2.3.2 `manager_based_rl_env.py` 的 `step()` 每一行：谁在什么时候被调用、数据在哪个张量里、为什么是这个顺序（4.13 发现的"奖励读旧目标、观测读新目标"是本页的典型案例）。

## 必须覆盖

1. **主线**：`ManagerBasedRLEnv.step()`（L153 起，permalink）按执行顺序分段：动作处理（ActionManager.process_action / apply_action）→ decimation 循环（`sim.step`、`scene.update`、渲染间隔）→ 时间推进 → termination → reward → 重置（`_reset_idx`）→ command 更新 → interval 事件 → 观测；每段 ≤ 15 行节选 + 3–6 句。
2. **与 0.6 图逐段对照**：每段标注对应 0.6 时序图的哪一步；0.6 图若有与源码不完全一致处，列出（本页只指出，修 0.6 另开微任务）。
3. **顺序为什么重要**：三个有后果的顺序——先 termination 后 reward（终止那一步的奖励怎么算）、先重置后 command 后观测（4.13 的案例）、interval 事件在观测之前（4.12）；各给一句"如果反过来会怎样"。
4. **父类部分**：`ManagerBasedEnv.step()` 与 `_reset_idx` 中各 Manager 的 reset 顺序（L380 附近），一张调用链图（D-017）。
5. **数据在哪**：`obs_buf`、`reward_buf`、`reset_buf`、`extras["log"]` 的形状与生命周期（回链 0.6"数据在哪里"、4.9）。
6. **实测可选**：用 7.3 的方法在 reach 环境打印一步里各段耗时（1 个环境即可），与 7.2 的拆分对照。
7. 常见误解 ≥ 3（候选：`step()` 每调一次物理走一步；重置发生在下一步开头；观测是物理步之前算的）。
